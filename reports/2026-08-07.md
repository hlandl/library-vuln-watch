## Findings

### CAMEL-24296 — `camel-support`: apply a JEP-290 deserialization filter on `CamelObjectInputStream` by default
- **Verdict: NEEDS REVIEW.** Severity: **MEDIUM** *(estimated)* — this is a **defense-in-depth hardening commit**, not a fix for a disclosed CVE; flagged `SUSPECTED` per the "silent fix" sweep of `apache/camel`.
- **Vulnerability:** `SUSPECTED` — no CVE/GHSA exists. The commit adds a JEP-290 `ObjectInputFilter` to `CamelObjectInputStream`, the shared `ObjectInputStream` subclass used by Camel's own raw-Java-object deserialization path. It resolves (in order): an explicit `deserializationFilter` pattern → the JVM-wide `jdk.serialFilter` → a new conservative default allow-list (`!java.net.**;java.**;javax.**;org.apache.camel.**;maxdepth=20;maxrefs=10000;maxbytes=10485760;!*`).
- **Affected range vs. our version:** Unreleased — only on `main` as of 2026-08-06 (commit `85ac83e`), targeting `4.22.0` (new upgrade-guide page `camel-4x-upgrade-guide-4_22.adoc`), not in any tagged release yet. Our pinned **4.8.8 has the identical unfiltered `CamelObjectInputStream`** (verified against the `camel-4.8.8` tag — no `ObjectInputFilter` at all, plain `resolveClass()` override only) → the underlying gap this hardens exists identically in our version. `UNCLEAR` whether this "affects us" in the CVE sense since it isn't remediating an active bug report, but it removes a real weak spot.
- **Component analysis:** `CamelObjectInputStream` lives in **camel-support** (in `used_components`). Its one production caller in the 4.8.8 tree is `HttpHelper.deserializeJavaObjectFromStream(InputStream, CamelContext)` in **camel-http-common** (also in `used_components`), invoked from `DefaultHttpBinding.readBody()` when the inbound HTTP request's `Content-Type` is `application/x-java-serialized-object`. That path is already gated in 4.8.8 by `allowJavaSerializedObject` (component/endpoint option, **defaults to `false`**) or `transferException`, mirroring the historical Camel HTTP-deserialization protection pattern — so under default configuration this is not independently exploitable today, but any route/endpoint that explicitly sets `allowJavaSerializedObject=true` or uses `transferException=true` on an HTTP consumer would have an **unfiltered** deserialization sink until this hardening is backported. → `USED`.
- **Sources:**
  - Commit: https://github.com/apache/camel/commit/85ac83ef56c64b45e1f2dc7debee3866a8b03e39
  - Jira: https://issues.apache.org/jira/browse/CAMEL-24296
  - PR (referenced by commit, "Closes #25378"): https://github.com/apache/camel/pull/25378
- **Official fix + backport assessment:** Two files change: `CamelObjectInputStream.java` gains a new 3-arg constructor `(InputStream, CamelContext, String deserializationFilter)` that calls `setObjectInputFilter(...)`, keeping the old 2-arg constructor as a delegating overload (so existing callers are source-compatible); a new self-contained helper class `DeserializationFilterHelper` (pure `java.io.ObjectInputFilter` + slf4j, no other Camel-internal dependencies) implements the resolution order and default patterns. `HttpHelper` is updated only to keep using the (unchanged-behavior) 2-arg constructor. **Backport assessment: clean, low risk.** Neither `CamelObjectInputStream.java` nor its caller in `camel-http-common` has drifted between `main` and the `camel-4.8.8` tag — the class body is byte-for-byte the same base to patch against. `DeserializationFilterHelper` has no dependency on newer Camel internals (just `java.io.ObjectInputFilter`, available since Java 9, and our baseline is Java 17+), so it can be ported verbatim. Recommend porting both files plus `CamelObjectInputStreamTest.java` (78 new lines) unmodified, and additionally auditing our own route configuration for any `allowJavaSerializedObject=true` / `transferException=true` HTTP consumer endpoints while this is being backported, since that's the one path in our used components that would actually exercise the filter.

### GHSA-vvjc-q5vr-52q6 — historical `camel-jackson`/`camel-jacksonxml` RCE (2018), newly indexed by this sweep
- **Verdict: NOT RELEVANT.** Severity: **HIGH** (CVSS 3.0 9.8, per the GitHub advisory).
- **Vulnerability:** `CONFIRMED` (GHSA-vvjc-q5vr-52q6, JIRA CAMEL-10567/CAMEL-10604, published 2018-10-16). `camel-jackson`/`camel-jacksonxml` allow specifying the unmarshal target type via the `CamelJacksonUnmarshalType` header, enabling deserialization gadget-chain RCE.
- **Affected range vs. our version:** `2.x < 2.16.5`, `>= 2.17.0 < 2.17.5`, `>= 2.18.0 < 2.18.2` — fixed in **2.16.5 / 2.17.5 / 2.18.2**. Our pinned **4.8.8 is many major versions past the fixed releases** → `NOT_AFFECTED`.
- **Component analysis:** `camel-jackson`/`camel-jacksonxml` are both in `used_components`, but irrelevant here since the version range excludes 4.8.8 outright.
- **Why it surfaced now:** this is a 2018-era advisory that had not previously appeared in any of this watch's sweeps (not present in `state/seen.json`); it turned up only because today's web-search-based sweep (see Source health) surfaced it incidentally while investigating `camel-jackson`. No evidence this indicates a gap specific to recent disclosures — recorded now purely so it isn't re-surfaced.
- **Sources:** https://github.com/advisories/GHSA-vvjc-q5vr-52q6
