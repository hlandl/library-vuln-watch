## Findings

### CVE-2026-40860 — camel-jms/camel-sjms: unguarded `ObjectMessage` deserialization
- **Is this a vulnerability?** CONFIRMED (CVE published; GHSA `GHSA-m5vh-3fw5-5wgh`, currently
  filed under the mirror's 2026/04 directory despite a 2026-07-05 oss-security post date —
  this explains why neither the 2026-07-15 nor 2026-07-22 sweep (which only checked July 2026
  in the mirror) found it).
- **Description:** `JmsBinding.extractBodyFromJms()` (camel-jms) and the equivalent class in
  camel-sjms call `jakarta.jms.ObjectMessage.getObject()` whenever `mapJmsMessage=true` (the
  default) with **no `ObjectInputFilter`, class allow-list, or deny-list of any kind**. An
  attacker able to publish a crafted `ObjectMessage` to a consumed queue/topic can achieve
  remote code execution if any deserialization gadget chain is present on the classpath.
  Reached transitively through camel-sjms2 and camel-amqp as well (neither used by us).
  This is the CVE that the fix history for `CVE-2026-42527` and `CVE-2026-43866` (both already
  known to this watch) presupposes: 4.14.7 is the release that *first introduces* the
  `ObjectInputFilter` mechanism those two CVEs later found bypassable in different ways.
- **Affected range vs. our version:** `org.apache.camel:camel-jms` "from 3.0.0 before 4.14.7,
  from 4.15.0 before 4.18.2, from 4.19.0 before 4.20.0" → **4.8.8 is AFFECTED** (falls in the
  first range, and is the *most* exposed case since it has no filter mechanism to bypass —
  the vulnerability is present in full, not as a corner-case bypass).
- **Component in use?** `camel-jms` is in `used_components` → **USED.**
- **Verdict: AFFECTS US.**
- **Severity:** The fetched GHSA/CVE record fields did not include a numeric CVSS vector for
  this specific advisory id in the data retrieved; given the description (unauthenticated
  attacker-controlled deserialization with no defense-in-depth at all, potential RCE via
  gadget chain), treat as **CRITICAL** *(estimated)* — worse than the two related, already-CVSS-scored
  follow-on CVEs (CVE-2026-42527 HIGH/GHSA-bucket, CVE-2026-43866 HIGH).
- **Sources:**
  - GHSA (mirror, filed under 2026/04 despite July disclosure date): https://github.com/advisories/GHSA-m5vh-3fw5-5wgh
  - CVE record: https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/40xxx/CVE-2026-40860.json
  - Vendor advisory (unreachable this run, link only): https://camel.apache.org/security/CVE-2026-40860.html
  - Pinned-version source (identical to 4.14.6, see diff below): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.8.8/components/camel-jms/src/main/java/org/apache/camel/component/jms/JmsBinding.java
  - Pre-fix comparison (4.14.6): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.6/components/camel-jms/src/main/java/org/apache/camel/component/jms/JmsBinding.java
  - Fixed-version source (4.14.7): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.7/components/camel-jms/src/main/java/org/apache/camel/component/jms/JmsBinding.java
- **Official fix:** 4.14.7 adds an `ObjectInputFilter` field (`deserializationFilter`),
  resolved from an endpoint/component-level `deserializationFilter` option or the JVM-wide
  `jdk.serialFilter`, defaulting to `java.**;javax.**;org.apache.camel.**;!*`; a new
  `checkDeserializedClass()` method runs the filter against the deserialized object's class
  and throws `SecurityException` on rejection, called right after `getObject()`.
- **Backport assessment: LOW effort, clean.** Byte-for-byte diff of `JmsBinding.java` between
  `camel-4.8.8` and the pre-fix `camel-4.14.6` tag is **zero** — no drift. **Recommend porting
  the 4.14.8 state directly rather than the 4.14.7 intermediate**: 4.14.7's filter alone was
  itself subsequently shown to be bypassable in two ways ((1) the `java.**` glob admits
  DNS-exfiltration side-channel classes — `CVE-2026-42527`, already `NEEDS_REVIEW` in this
  watch; (2) `DefaultExchangeHolder` lives in the allow-listed `org.apache.camel.**` namespace —
  `CVE-2026-43866`, new below). Porting straight to 4.14.8's version (tightened filter +
  opt-in `objectMessageEnabled` gate, default `false`) closes all three issues in one change.
  See `CVE-2026-43866` below for that diff.

### CVE-2026-43866 — camel-jms/camel-sjms: `CVE-2026-40860` fix bypass via `DefaultExchangeHolder`
- **Is this a vulnerability?** CONFIRMED (CVE + GHSA `GHSA-f755-xp6r-8q84`, published 2026-07-06,
  found via this run's widened July-2026 mirror sweep — 20 more Camel advisories were present
  in the mirror today than the 14 the 2026-07-22 run recorded, all from the same 2026-07-06/07
  batch and evidently backfilled into the "unreviewed" tree over the past several days).
- **Description:** `org.apache.camel.support.DefaultExchangeHolder` lives inside the
  `org.apache.camel.**` namespace that the (4.14.7-introduced) default deserialization filter
  allow-lists. An `ObjectMessage` whose payload is a `DefaultExchangeHolder` therefore passes
  the class-level filter check even where it exists; `DefaultExchangeHolder.unmarshal()` is
  then called on it **without requiring `transferExchange` to be enabled on the receiving
  side**, writing every field (body, IN/OUT headers, properties, variables, exchange id,
  exception) into the live Exchange. An attacker who can publish to a consumed queue/topic can
  inject arbitrary Exchange state — routing/header/property manipulation — using only
  universally-trusted `java.lang`/`java.util` types, no gadget chain required. Same code path
  in camel-sjms/camel-sjms2 and the JmsComponent/JmsBinding-based components (camel-amqp,
  camel-activemq, camel-activemq6) — none of those besides camel-jms are used by us.
- **Affected range vs. our version:** "from 3.0.0 before 4.14.8, from 4.15.0 before 4.18.3,
  from 4.19.0 before 4.21.0" → **4.8.8 is AFFECTED.** Note our 4.8.8 doesn't have the filter
  this CVE describes bypassing at all (see `CVE-2026-40860` above) — the *practical* exposure
  on 4.8.8 is a strict superset of this CVE's bypass (unrestricted deserialization, of which
  the `DefaultExchangeHolder` vector is only one instance), but the vendor's stated affected
  range already includes 4.8.8 directly, so no judgment call is needed here (unlike the
  already-recorded `CVE-2026-42527`).
- **Component in use?** `camel-jms` is in `used_components` → **USED** (camel-sjms is not used).
- **Verdict: AFFECTS US.**
- **Severity:** Published CVSS 3.1 `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N` — HIGH.
- **Sources:**
  - GHSA: https://github.com/advisories/GHSA-f755-xp6r-8q84
  - CVE record: https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/43xxx/CVE-2026-43866.json
  - Vendor advisory (unreachable this run, link only): https://camel.apache.org/security/CVE-2026-43866.html
  - Pinned-version source: https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.8.8/components/camel-jms/src/main/java/org/apache/camel/component/jms/JmsBinding.java
  - Pre-fix comparison (4.14.7): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.7/components/camel-jms/src/main/java/org/apache/camel/component/jms/JmsBinding.java
  - Fixed-version source (4.14.8): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.8/components/camel-jms/src/main/java/org/apache/camel/component/jms/JmsBinding.java
- **Official fix:** 4.14.8 tightens `DEFAULT_DESERIALIZATION_FILTER` to
  `"!java.net.**;java.**;javax.**;org.apache.camel.**;!*"` (unrelated to this specific CVE —
  that change addresses `CVE-2026-42527`) **and** adds a new `objectMessageEnabled` endpoint
  option, default `false`. When disabled (the new default), every `ObjectMessage` send/receive
  path throws `IllegalStateException` — "receiving ObjectMessage", "transferException reply",
  "transferExchange", "creating ObjectMessage" — four call sites gated in `JmsBinding.java`.
  This is what actually closes the `DefaultExchangeHolder` bypass: with the gate default-off,
  no `ObjectMessage` (of any class) is deserialized at all unless explicitly opted in.
- **Backport assessment: LOW effort, clean; recommend applying together with `CVE-2026-40860`'s
  fix as a single combined change** (see diff detail there) since 4.14.7's intermediate state
  is insufficient on its own. Diff `JmsBinding.java` 4.14.7→4.14.8: filter-string change (1
  line) + `isObjectMessageEnabled()`/`objectMessageDisabled()` helpers + 4 call-site guards.
  Zero structural drift from 4.8.8 (confirmed via the 4.8.8-vs-4.14.6 zero-diff above, and
  4.14.6→4.14.7→4.14.8 are themselves incremental, non-refactoring patches) — a mechanical
  port. Port the endpoint-option test and the `objectMessageEnabled=false`-by-default behavior
  test alongside.

### CVE-2026-46592 — camel-cxf-soap: non-Camel-prefixed operation-selection headers, confused-deputy SOAP redirection
- **Is this a vulnerability?** CONFIRMED (CVE + GHSA `GHSA-mrrp-9gjm-749v`, published
  2026-07-06; also found only via this run's widened July sweep).
- **Description:** `camel-cxf`'s producer selects which SOAP operation to invoke from the
  `operationName`/`operationNamespace` Exchange headers, whose constants (`CxfConstants` in
  the shared `camel-cxf-common` module) are the plain, non-`Camel`/`camel`-prefixed strings
  `"operationName"`/`"operationNamespace"`. `HttpHeaderFilterStrategy` blocks only the
  `Camel`/`camel` namespace at the HTTP boundary, so in a route bridging an HTTP consumer
  (e.g. `platform-http`) into a `cxf:` producer, any HTTP client can set the `operationName`
  header and redirect the invocation to a different WSDL operation than the route intended —
  e.g. substituting a destructive operation for a read operation — a confused-deputy attack,
  unauthenticated if the bridging consumer itself requires no auth. Same constants are shared
  by `camel-cxfrs` (not used by us).
- **Affected range vs. our version:** "from 4.0.0 before 4.14.8, from 4.15.0 before 4.18.3,
  from 4.19.0 before 4.21.0" → **4.8.8 is AFFECTED.**
- **Component in use?** `camel-cxf-soap` (and the shared `camel-cxf-common`) are in
  `used_components` → **USED.**
- **Verdict: AFFECTS US.**
- **Severity:** No numeric CVSS vector was present in the retrieved GHSA/CVE fields for this
  id; the CNA `database_specific.severity` bucket recorded in the GHSA mirror is HIGH.
  Treat as **HIGH**: exploitability depends on the route topology (only routes that bridge an
  untrusted HTTP consumer into a `cxf:` producer without setting/locking the operation from a
  trusted source are exposed), but the *impact* (invoking an unintended backend operation) can
  be severe depending on what operations the target SOAP service exposes.
- **Sources:**
  - GHSA: https://github.com/advisories/GHSA-mrrp-9gjm-749v
  - CVE record: https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/46xxx/CVE-2026-46592.json
  - Vendor advisory (unreachable this run, link only): https://camel.apache.org/security/CVE-2026-46592.html
  - Pinned-version source: https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.8.8/components/camel-cxf/camel-cxf-common/src/main/java/org/apache/camel/component/cxf/common/message/CxfConstants.java
  - Pre-fix comparison (4.14.7): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.7/components/camel-cxf/camel-cxf-common/src/main/java/org/apache/camel/component/cxf/common/message/CxfConstants.java
  - Fixed-version source (4.14.8): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.8/components/camel-cxf/camel-cxf-common/src/main/java/org/apache/camel/component/cxf/common/message/CxfConstants.java
- **Official fix:** 4.14.8 renames the two constants to `CamelCxfOperationName` /
  `CamelCxfOperationNamespace` so the existing `HttpHeaderFilterStrategy` Camel-namespace
  filter blocks them at the HTTP boundary by construction; per the CNA notes, cross-transport
  carrier-header handling was also documented in the 4.21 upgrade guide.
- **Backport assessment: LOW effort, clean.** Diff of `CxfConstants.java` between `camel-4.8.8`
  and the pre-fix `camel-4.14.7` tag is **zero** — no drift; the 2-line rename applies
  directly. Caveat for the human backport: renaming these constants is a **breaking change**
  for any of our routes that currently read/set the raw `operationName`/`operationNamespace`
  header names directly (as opposed to via the `CxfConstants` constant) — grep our routes for
  literal use of these header strings before applying, and port the corresponding
  header-filter test.

### CVE-2026-49098 — camel-kafka: non-Camel-prefixed `kafka.OVERRIDE_TOPIC` header, arbitrary topic redirection
- **Is this a vulnerability?** CONFIRMED (CVE + GHSA `GHSA-mm84-qvjh-hcj7`, published
  2026-07-06; found via this run's widened July sweep).
- **Description:** `camel-kafka`'s producer can override its configured target topic at
  runtime from the `kafka.OVERRIDE_TOPIC` Exchange header (`KafkaProducer.evaluateTopic()`
  prefers the header over the endpoint-configured topic). The header constants in
  `KafkaConstants` (`OVERRIDE_TOPIC`, `OVERRIDE_TIMESTAMP`, `PARTITION_KEY`, etc.) are the
  plain, non-`Camel`/`camel`-prefixed strings `"kafka.OVERRIDE_TOPIC"` etc. `camel-kafka`'s own
  `KafkaHeaderFilterStrategy` filters the `kafka.*` namespace only on the
  Kafka-record⇄Exchange serialization boundary, not on headers arriving from an *upstream*
  consumer in a multi-component route; an upstream HTTP consumer's `HttpHeaderFilterStrategy`
  blocks only `Camel`/`camel`, so `kafka.*` headers pass through unfiltered. In a route
  bridging an HTTP consumer into a `kafka:` producer, any HTTP client can set
  `kafka.OVERRIDE_TOPIC` to redirect the message to an arbitrary Kafka topic (e.g. a sensitive
  internal topic, or one consumed by a critical downstream service), and similarly abuse
  `kafka.OVERRIDE_TIMESTAMP`/`kafka.PARTITION_KEY`. No credentials required if the bridging
  consumer is unauthenticated.
- **Affected range vs. our version:** "from 4.0.0 before 4.14.8, from 4.15.0 before 4.18.3,
  from 4.19.0 before 4.21.0" → **4.8.8 is AFFECTED.**
- **Component in use?** `camel-kafka` is in `used_components` → **USED.**
- **Verdict: AFFECTS US.**
- **Severity:** No numeric CVSS vector present in the retrieved fields; GHSA mirror's
  `database_specific.severity` bucket is MODERATE. Given the potential for message
  redirection/injection into arbitrary internal Kafka topics from unauthenticated input where
  a route bridges HTTP→Kafka, treat as **HIGH** *(estimated, one tier above the vendor bucket)*
  pending confirmation of whether any of our routes have this bridging shape.
- **Sources:**
  - GHSA: https://github.com/advisories/GHSA-mm84-qvjh-hcj7
  - CVE record: https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/49xxx/CVE-2026-49098.json
  - Vendor advisory (unreachable this run, link only): https://camel.apache.org/security/CVE-2026-49098.html
  - Pinned-version source: https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.8.8/components/camel-kafka/src/main/java/org/apache/camel/component/kafka/KafkaConstants.java
  - Pre-fix comparison (4.14.7): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.7/components/camel-kafka/src/main/java/org/apache/camel/component/kafka/KafkaConstants.java
  - Fixed-version source (4.14.8): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.8/components/camel-kafka/src/main/java/org/apache/camel/component/kafka/KafkaConstants.java
- **Official fix:** 4.14.8 renames every affected constant to a `Camel`-prefixed form:
  `CamelKafkaPartitionKey`, `CamelKafkaPartition`, `CamelKafkaKey`, `CamelKafkaTopic`,
  `CamelKafkaOverrideTopic`, `CamelKafkaOffset`, `CamelKafkaHeaders`,
  `CamelKafkaLastRecordBeforeCommit`, `CamelKafkaLastPollRecord`, `CamelKafkaTimestamp`,
  `CamelKafkaOverrideTimestamp`, `CamelKafkaRecordMeta` (12 constants total in the diff).
- **Backport assessment: LOW effort, clean.** Diff of `KafkaConstants.java` between
  `camel-4.8.8` and the pre-fix `camel-4.14.7` tag is **zero** — no drift; the rename applies
  directly. Same breaking-change caveat as the CXF finding above: any of our routes/tests that
  read/write these headers by the raw `kafka.*` string (rather than via the `KafkaConstants`
  constant) will need updating in lock-step with the backport. Port the corresponding
  header-filter regression test.
