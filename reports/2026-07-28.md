## Findings

### CAMEL-24256 — `logMask` / `DefaultMaskingFormatter` misses value-shape secrets (URI userinfo passwords, PEM private keys)

- **Is this a vulnerability?** SUSPECTED — no CVE/GHSA assigned as of this run; a genuine
  security-hardening fix landed with no advisory (Jira/GitHub Search unavailable to confirm
  ticket labels).
- **Affected range vs. our version?** AFFECTED — confirmed directly: our pinned 4.8.8's
  `core/camel-util/.../SensitiveUtils.java` and `core/camel-support/.../DefaultMaskingFormatter.java`
  contain none of the value-shape masking logic added by the fix; masking is purely
  name/keyword-based (`key=value`, XML attribute, JSON key against a fixed `SENSITIVE_KEYS` set).
- **Component in use?** USED — both `camel-util` and `camel-support` are in `used_components`.
- **Severity:** MEDIUM *(estimated)* — information exposure through logs (CWE-532-adjacent).
  Requires `logMask` (or another `DefaultMaskingFormatter`/`SensitiveUtils` caller) to be enabled
  and a secret that has no matching "sensitive key name": a password embedded in a connection
  string's userinfo (`scheme://user:pass@host`) or a raw PEM private-key block appearing in a log
  line, stack trace, or config dump. Not remotely exploitable on its own — impact is disclosure to
  whoever can read log output (log aggregators, support bundles, shared log files).
- **Sources:** commit `b5bae007955ed6bf64e608affd4d383253e8b8d5` on `apache/camel` `main`
  (2026-07-27), PR https://github.com/apache/camel/pull/25113 ("Mask URI userinfo credentials and
  PEM private keys"), tracked as Jira CAMEL-24256 per the commit's "Closes #25113" / PR
  cross-reference (Jira itself unreachable this run to confirm ticket state/labels directly).
  Follow-up to an earlier related PR #25093 ("MCP redaction rework"), not independently reviewed
  this run.
- **Official fix / release status:** Landed on `main` only (2026-07-27); not present in any
  released Camel version yet, and not backported to the `camel-4.8.x` maintenance branch (branch
  head unchanged, per Source health).
- **Changed files:** `core/camel-util/src/main/java/org/apache/camel/util/SensitiveUtils.java`
  (+82 lines: two new `Pattern`s — `URI_USERINFO_PASSWORD_IN_TEXT`, `PEM_PRIVATE_KEY` — and three
  new public static methods, `maskUserInfoCredentials`/`maskPemPrivateKeyBlocks`/
  `maskSensitiveValueShapes`), `core/camel-support/.../DefaultMaskingFormatter.java` (`format()`
  restructured to call the new aggregate method unconditionally, plus a `Matcher.quoteReplacement`
  correctness fix for the existing keyword path), `SensitiveUtilsTest.java`,
  `DefaultMaskingFormatterTest.java`, two doc/upgrade-guide files.
- **Backport assessment:** Low-risk, additive. The 4.8.8 versions of both source files are
  structurally unchanged from pre-fix `main` at the diffed hunks (no renames/refactors) — the
  patch should apply with at most trivial context offsets. Port: the two new `Pattern`s and three
  new methods in `SensitiveUtils`; the `format()` restructuring plus the `maskSensitiveValueShapes`
  call in `DefaultMaskingFormatter`; and the `Matcher.quoteReplacement(maskString)` fix bundled in
  the same hunk (worth carrying even though unrelated, since it's a real — if minor — correctness
  fix for custom `maskString` values containing `$`/`\`). Port the corresponding new test cases
  from both test files (ignore unrelated test-numbering churn). No API-visibility or dependency
  changes; no interaction with the second finding below beyond both touching `SensitiveUtils.java`
  (apply together, same file).

### CAMEL-24210 — `URISupport.sanitizeUri` misses hyphenated `api-key` / bare `Authorization` parameter names

- **Is this a vulnerability?** SUSPECTED — no CVE/GHSA assigned.
- **Affected range vs. our version?** AFFECTED — confirmed: pinned 4.8.8's `SensitiveUtils.SENSITIVE_KEYS`
  contains `apikey` and `authorizationtoken` but neither hyphenated `api-key` nor bare
  `authorization`, so a URI parameter literally named (case-insensitively) `api-key` or
  `authorization` is written unredacted by `URISupport.sanitizeUri` today.
- **Component in use?** USED — `camel-util` (the shared sanitizer used by logs, JMX attributes,
  exception messages, and the dev console across every component, not just the one that motivated
  the fix).
- **Severity:** MEDIUM *(estimated)*, same disclosure class as above (CWE-532-adjacent). Upstream's
  own motivating case is `camel-openai`'s Azure OpenAI integration (`additionalHeader.api-key=...`,
  `additionalHeader.Authorization=...`) — `camel-openai` is **not** in our `used_components` — but
  the fix is in shared `camel-util` infrastructure, so any endpoint URI (from any component) with a
  parameter literally named `api-key` or `authorization` is equally affected in our version.
- **Sources:** commit `38ff66d5252d698f0d37ebe41f56609ffb6b5e62` on `apache/camel` `main`
  (2026-07-22), PR https://github.com/apache/camel/pull/24984 ("redact api-key and Authorization
  from sanitized URIs"), tracked as Jira CAMEL-24210 (same caveat: Jira unreachable to confirm
  directly).
- **Official fix / release status:** `main` only; not backported to `camel-4.8.x` (branch head
  unchanged).
- **Changed files:** `catalog/camel-catalog/.../sensitive-keys.json` and
  `core/camel-util/.../SensitiveUtils.java` (two-keyword addition — `api-key`, `authorization` — to
  the existing `SENSITIVE_KEYS` set and its generated regex alternation),
  `core/camel-util/src/test/.../URISupportTest.java` (two new test cases),
  `tooling/maven/camel-package-maven-plugin/.../UpdateSensitizeHelper.java` (build-time generator
  that produces the two files above), one upgrade-guide doc entry.
- **Backport assessment:** Trivial, additive. This is a two-string addition to an existing keyword
  set/regex alternation — no logic changes, no drift risk against our 4.8.8 code. The
  `UpdateSensitizeHelper.java` change is to a Maven code-generator used only at build time to
  regenerate `SensitiveUtils.java`/`sensitive-keys.json`; simplest backport path is to skip the
  generator and hand-add the same two keywords directly to our 4.8.8 `SensitiveUtils.java` and
  `sensitive-keys.json` rather than porting/re-running the generator itself. Port the two new
  `URISupportTest` cases. Upstream's own doc notes a cosmetic side effect worth carrying into our
  backport notes: any parameter name merely *containing* `authorization` as a substring (e.g.
  `adjustAuthorization`) will now also show as `xxxxxx` in sanitized output — intentional, broader
  redaction, not a behavior change to the endpoint itself. Apply together with CAMEL-24256 above
  (both touch `SensitiveUtils.java`, no overlapping lines).
