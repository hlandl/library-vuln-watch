### GHSA-6qw3-4796-5984 — alias of CVE-2026-40859 (Camel-Vertx-Http/Camel-Netty-Http unsafe deserialization)
- **Is this a vulnerability?** `CONFIRMED` — reviewed (GitHub) advisory, CVSS 8.1 (HIGH). `camel-vertx-http` (and `camel-netty-http`) deserialize HTTP response bodies carrying `Content-Type: application/x-java-serialized-object` via a raw `java.io.ObjectInputStream` with no `ObjectInputFilter` when `transferException` is enabled, enabling RCE via known gadget chains (e.g. CommonsCollections6).
- **Affected version range:** 4.15.0–4.18.0, fixed in 4.18.3 (per the public advisory/OpenCVE summary).
- **Component analysis:** `camel-vertx-http` is **not** in `used_components`, and `camel-netty-http` is likewise absent from the list.
- **Verdict: NOT RELEVANT** (component not used). This is the same underlying advisory already recorded in `state/seen.json` under `CVE-2026-40859` (seen since 2026-07-22, `NOT_RELEVANT`) — `GHSA-6qw3-4796-5984` is simply a GHSA id for the same CVE that surfaced in today's search sweep. No separate analysis needed; recorded as an alias for dedup completeness.
- Sources: [OpenCVE — CVE-2026-40859](https://app.opencve.io/cve/CVE-2026-40859), [exploit-intel.com — CVE-2026-40859](https://exploit-intel.com/vuln/CVE-2026-40859), [OSV — GHSA-6qw3-4796-5984](https://osv.dev/vulnerability/GHSA-6qw3-4796-5984).
- No backport assessment performed (component not used).

Read the actual diff (`components/camel-kafka/.../KafkaProducer.java`) rather than trusting the keyword match: the change reorders `startKafkaTransaction()` to run inside the existing `try` block (so a failed transaction-begin still completes the async callback instead of escaping `process()`), and reorders `kafkaProducer.beginTransaction()` before `uow.beginTransactedBy(...)` so a broker-side begin failure never leaves the unit-of-work flagged as transacted without a registered synchronization to commit/roll it back.
