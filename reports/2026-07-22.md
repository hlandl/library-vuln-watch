## Findings

### CVE-2026-46584 / GHSA-29vj-9mgp-mwp2 — camel-mail: attacker-controlled JavaMail session properties
- **Is this a vulnerability?** CONFIRMED (CVE + GHSA published 2026-07-06).
- **Same underlying issue as CAMEL-23522** (recorded in `state/seen.json` on 2026-07-15 as
  `NEEDS_REVIEW`, before it had a CVE) — the 4.14.8 fix commit's own explanatory comment cites
  `CAMEL-23522` directly (confirmed by diffing `MailProducer.java`, see below). This CVE
  fingerprint supersedes that Jira-key fingerprint per the fingerprint-preference rule
  (CVE > GHSA > Jira key); the old entry is left in place for history.
- **Description:** `MailProducer.getSender()` scans the outgoing `Exchange` for headers in
  the Camel-internal `mail.smtp.`/`mail.smtps.` namespace and applies any it finds as
  per-message JavaMail session properties, overriding the endpoint's configured values. No
  `HeaderFilterStrategy` blocks this namespace (it doesn't start with `Camel`/`camel`), so the
  values can arrive from any inbound protocol (HTTP query params/headers, JMS, Kafka, etc.)
  that feeds a route ending in an `smtp:`/`smtps:` producer without an intervening
  `removeHeaders(...)`.
  - **On our version specifically** (4.8.8, which is `< 4.19.0`): setting `mail.smtp.host`
    redirects the SMTP connection to an attacker-controlled server, and because the producer
    still authenticates with the endpoint's configured username/password, **those credentials
    are sent to the attacker**. This is the *worse* of the two impact tiers the advisory
    describes (post-4.19.0 the redirect is not possible, only transport-security weakening) —
    our exposure is at the high end even though GHSA's published CVSS/severity bucket (LOW)
    reflects the aggregate/lower-impact case, not specifically pre-4.19 deployments.
- **Affected range vs. our version:** advisory states "from 4.0.0 before 4.14.8" → **4.8.8 is
  AFFECTED.**
- **Component in use?** `camel-mail` is in `used_components` → **USED.**
- **Verdict: AFFECTS US.**
- **Severity:** Published CVSS 3.1 `AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N` (GHSA bucket: LOW).
  For our pinned version, treat as **at least MEDIUM** given the credential-exfiltration
  impact described above; a route that feeds untrusted input into an `smtp:`/`smtps:`
  producer without stripping `mail.smtp.*`/`mail.smtps.*` first should be treated as a
  priority to check.
- **Sources:**
  - GHSA: https://github.com/advisories/GHSA-29vj-9mgp-mwp2
  - CVE record: https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/46xxx/CVE-2026-46584.json (`cve.org`/NVD web UI unreachable this run)
  - Vendor advisory (unreachable this run, link only): https://camel.apache.org/security/CVE-2026-46584.html
  - Jira (unreachable this run, link only): https://issues.apache.org/jira/browse/CAMEL-23522
  - Pinned-version source checked directly: https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.8.8/components/camel-mail/src/main/java/org/apache/camel/component/mail/MailProducer.java
  - Fixed-version source: https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.8/components/camel-mail/src/main/java/org/apache/camel/component/mail/MailProducer.java
- **Official fix:** New opt-in `useJavaMailSessionPropertiesFromHeaders` endpoint option,
  defaulting to `false`; when `false`, `getSender()` returns the endpoint's `defaultSender`
  immediately instead of scanning headers at all. Shipped in 4.14.8 (4.14.x LTS), 4.18.3, and
  4.21.0.
- **Backport assessment: LOW effort, clean.** Byte-for-byte diff of `MailProducer.java`
  between the `camel-4.8.8` tag and the pre-fix `camel-4.14.7` tag shows **zero drift** — the
  method is identical, so the 4.14.8 patch (add the config flag + an early-return guard at the
  top of `getSender()`) applies with no adaptation. Recommend porting the flag's default
  (`false`) and the guard, plus the associated endpoint-option test.

### CVE-2026-42527 / GHSA-8h6p-jvhf-9hcr — permissive default ObjectInputFilter, DNS-exfiltration side channel
- **Is this a vulnerability?** CONFIRMED (CVE + GHSA published 2026-07-06).
- **Description:** Several Camel components ship a default-deny-ish `ObjectInputFilter`
  pattern (`java.**;javax.**;org.apache.camel.**;!*`) as defense-in-depth around Java
  deserialization. The `java.**` glob is recursive and admits `java.net.URL`/`InetAddress`,
  whose `hashCode()`/`equals()` perform DNS lookups; deserializing a `HashMap` containing a
  `java.net.URL` key passes the class-level check (its own class, `HashMap`, is allow-listed)
  but triggers an attacker-observable DNS query as a side effect during deserialization.
  Advisory names `camel-jms` as the highest-exposure component, because
  `JmsBinding.extractBodyFromJms` calls `ObjectMessage.getObject()` unconditionally when
  `mapJmsMessage=true` (the default). Also lists `camel-sjms`, `camel-amqp`, `camel-mina`,
  `camel-netty`, `camel-netty-http`, `camel-vertx-http`, `camel-infinispan`, and the
  aggregation-repository components `camel-leveldb`/`camel-cassandraql`/`camel-consul`/`camel-sql`
  — none of which except `camel-jms` are in `used_components`.
- **Affected range vs. our version — UNCLEAR, escalating rather than dropping:** the
  advisory's stated range is "from 4.14.0 before 4.14.8" (+ 4.15.0/4.19.0 lines), which
  **excludes 4.8.8 on paper**. But comparing `JmsBinding.java` directly:
  - At `camel-4.8.8` (our pinned tag): **no `ObjectInputFilter`, no
    `DEFAULT_DESERIALIZATION_FILTER` constant, no `deserializationFilter` field, and no
    `objectMessageEnabled` gate exist at all** — `extractBodyFromJms` calls
    `objectMessage.getObject()` completely unguarded whenever an `ObjectMessage` arrives.
  - At `camel-4.14.7` (the version immediately before this CVE's fix, i.e. what the CVE range
    is measured against): the filter mechanism *already exists* (added at some point in the
    4.14.x line, itself likely a fix for an earlier, unfiltered-deserialization report) — the
    flaw this CVE fixes is that the *existing* filter's `java.**` glob is too permissive.
  - **In short: our pinned 4.8.8 predates the introduction of this defense-in-depth mechanism
    entirely** — it has no filter to be "too permissive," it has *none*. Whether that makes
    4.8.8 "not affected" by this specific CVE (which is about a bypass of a mechanism we don't
    have) or "affected by a strictly worse variant of the same underlying weakness" is a
    judgment call outside this agent's remit to resolve unilaterally.
- **Component in use?** `camel-jms` is in `used_components` → **USED.**
- **Verdict: NEEDS REVIEW.** Recommend a human decide whether to treat this as in-scope for
  our EOL line and backport the 4.14.x hardening (opt-in `objectMessageEnabled` defaulting to
  `false`, plus the corrected non-recursive filter pattern), given `camel-jms` is in active
  use and the exposure (unauthenticated-gadget-chain RCE risk if `ObjectMessage` handling is
  reachable from untrusted input) is more severe on 4.8.8 than on any version this CVE
  formally covers.
- **Severity:** Published CVSS 3.1 `AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H` — GHSA bucket HIGH;
  the CNA's own textual severity field says "moderate" (these disagree; noting both).
  Requires a compatible gadget chain on the classpath and delivery of a crafted serialized
  object into an `ObjectMessage`-carrying JMS destination the route consumes from.
- **Sources:**
  - GHSA: https://github.com/advisories/GHSA-8h6p-jvhf-9hcr
  - CVE record: https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/42xxx/CVE-2026-42527.json
  - Vendor advisory (unreachable this run, link only): https://camel.apache.org/security/CVE-2026-42527.html
  - Pinned-version source checked directly: https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.8.8/components/camel-jms/src/main/java/org/apache/camel/component/jms/JmsBinding.java
  - Pre-fix comparison source (4.14.7): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.7/components/camel-jms/src/main/java/org/apache/camel/component/jms/JmsBinding.java
  - Fixed-version source (4.14.8): https://raw.githubusercontent.com/apache/camel/refs/tags/camel-4.14.8/components/camel-jms/src/main/java/org/apache/camel/component/jms/JmsBinding.java
- **Official fix:** In 4.14.8, `DEFAULT_DESERIALIZATION_FILTER` changes from
  `"java.**;javax.**;org.apache.camel.**;!*"` to `"!java.net.**;java.**;javax.**;org.apache.camel.**;!*"`
  (explicitly denies `java.net.**` ahead of the permissive `java.**`), and a new
  `objectMessageEnabled` endpoint option (default `false`) gates every `ObjectMessage`
  send/receive path, throwing `IllegalStateException` unless explicitly enabled.
- **Backport assessment: not a drop-in port — requires design input.** Because 4.8.8 has
  neither piece of this machinery, this is not "reapply this diff" but "port a whole
  feature" (the filter field, its resolution logic reading a configurable/JVM-wide/default
  filter, the `objectMessageEnabled` gate and its `IllegalStateException` guard at four call
  sites) onto older code. The class shape (`JmsBinding` constructor taking a `JmsEndpoint`,
  `extractBodyFromJms`, `createJmsMessage`) is otherwise unchanged between 4.8.8 and 4.14.7,
  so there's no renamed-symbol drift to fight, but this is meaningfully more work than the
  mail fix above and touches security-relevant defaults — recommend a human design review
  rather than a mechanical backport.
