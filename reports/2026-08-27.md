## Findings

### CAMEL-24416 — `XmlConverter` SAX parser factory did not disable external parameter entities / external DTD loading (XXE, CWE-611)

- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA attached to the commit; it is a
  self-described hardening fix. `XmlConverter.createDocumentBuilderFactory()` (the DOM path) has
  long disabled DOCTYPE declarations and external general entities. `createSAXParserFactory()` (the
  SAX path) in the very same class only set `FEATURE_SECURE_PROCESSING` and
  `external-general-entities=false` — it never set `external-parameter-entities=false` or
  `load-external-dtd=false`. A 2015-era CVE (Camel < 2.13.4 / 2.14.x < 2.14.2) already fixed the
  *general*-entity gap in this exact class; this run's commit closes the narrower
  *parameter*-entity / external-DTD gap that survived that earlier fix. Parameter-entity XXE is
  the class typically used for blind/out-of-band exfiltration and DTD-based denial of service, so
  this is a genuine (if narrower) attack-surface reduction, not cosmetic.
- **Affected range vs. our version?** `AFFECTED` — confirmed by direct code inspection, not
  pattern-matching. Checked out the `camel-4.8.8` tag: `core/camel-xml-jaxp/.../XmlConverter.java`
  `createSAXParserFactory()` sets exactly `FEATURE_SECURE_PROCESSING=true` and
  `external-general-entities=false`, and nothing else — identical to the pre-fix `main` code this
  commit changes. Neither `external-parameter-entities` nor
  `load-external-dtd` is disabled in 4.8.8's SAX factory.
- **Component in use?** `camel-core` and `camel-xml-jaxp` are both in `used_components` →
  **USED**. `XmlConverter` is a core type converter reachable from any route that converts a
  message body to/from XML via SAX (e.g. `toSAXSource`), so exposure depends on whether routes
  parse externally-sourced XML through that path — plausible given `camel-core`/`camel-xml-jaxp`
  are both listed as in use.
- **Severity:** Medium *(estimated)* — CWE-611 (XXE) via parameter entities / external DTD
  fetch. Typically enables blind/OOB data exfiltration or DoS (entity-expansion, DTD-fetch
  latency) rather than direct in-band file disclosure (`FEATURE_SECURE_PROCESSING` and the
  existing general-entity block already close the higher-severity direct-read vector). No CVE
  assigned upstream, consistent with a defense-in-depth classification rather than a directly
  exploitable critical bug — flagging Medium rather than High pending upstream's own
  classification.
- **Verdict: AFFECTS US.**
- Sources: [apache/camel@3defc6896](https://github.com/apache/camel/commit/3defc689649d0c324e2ec2af31fb1a37f3830550)
  ("CAMEL-24416", closes [#25594](https://github.com/apache/camel/pull/25594)), committed
  2026-08-26 09:00 UTC+2 by Andrea Cosentino. Not in any released version; `camel-4.8.x` branch
  head unchanged (`5a31b93`, confirmed again this run via `git ls-remote`).

**Backport assessment:** Small, low-risk cherry-pick. The fix adds two `try { sfactory.setFeature(...) } catch` blocks
to the existing `createSAXParserFactory()` method, following the exact same pattern already used
for `external-general-entities` two lines above — 4.8.8 has the identical method body up to that
point, so the patch should apply cleanly with no adaptation. Port the new
`core/camel-core/.../SaxParserFactoryHardeningTest.java` alongside it (asserts the SAX factory's
feature flags directly, and that they agree with the DOM factory's) — note the test lives under
`camel-core`'s test tree while the class under test is in the `camel-xml-jaxp` module, so mind the
module boundary when porting to 4.8.8's module layout (verify `camel-core`'s test classpath
already depends on `camel-xml-jaxp` there, as it does on `main`).

## Method notes

- **Lookback window:** incremental mode. `state/seen.json` `last_run` = `2026-08-26T04:09:00Z`;
  window swept = everything since `2026-08-24T04:09:00Z` (48h overlap per methodology step 1).
- **Commit sweep on `apache/camel` `main`:** shallow-cloned over the git protocol
  (`--shallow-since=2026-08-23`, single branch) — same substitute as recent runs, since GHSA/NVD/
  Jira/security-page access remains blocked (see Source health). 154 commits landed in the
  window; subjects and bodies were grep'd for `CVE-`/`security`/`vulnerab`/`CWE-`/`RCE`/`XXE`/
  `injection`/`traversal`/`bypass`/`deserializ` to catch security-flavored changes, then every
  `CAMEL-`-ticketed commit and every non-ticketed commit was individually read and assessed (not
  just keyword-matched — several keyword hits were false positives from substrings inside
  unrelated words, e.g. "resource"/"force" matching `RCE`, or `spring-security-version` matching
  `security`). Of the 154 commits, 3 duplicate already-seen fingerprints exactly
  (`CAMEL-24487` fix + its docs follow-up, and the `#25699` security-model docs commit — all
  already `AFFECTS_US`/`NOT_RELEVANT` in state from 2026-08-25/26) or resolve to an already-seen
  CVE (`CVE-2026-35563`, via the `org.apache.directory.api` pin commit) and were not re-assessed;
  `chore(deps)` dependency-bump commits with no `CAMEL-` ticket and no genuine security signal
  (~120 of the 154) were not treated as candidate findings, consistent with prior runs. 1 new
  finding (`CAMEL-24416`) and 12 new not-relevant tickets are assessed above.
- **`CAMEL-24416` verified by direct source inspection**, not just pattern matching: checked out
  the `camel-4.8.8` tag and confirmed `createSAXParserFactory()` there is missing exactly the two
  feature flags this commit adds.
- **`camel-4.8.x` maintenance branch:** head unchanged at `5a31b932322777b8eb5f091cf9c6f016a62fe896`
  (same as every run since 2026-07-23, confirmed via `git ls-remote`) — no backports landed there.
- **CVE/GHSA cross-check:** with NVD, the Camel security page, and Jira all blocked, `WebSearch`
  was used to check whether `CAMEL-24416` or the three still-`NEEDS_REVIEW` CVE IDs from the prior
  run (`CVE-2026-71300`, `CVE-2026-63621`, `CVE-2026-66908`) have any public CVE record yet — none
  do. `WebSearch` did surface a genuinely old (2015-era) Camel XXE CVE in this same
  `XmlConverter` class (general-entity gap, already fixed pre-4.8.8), which corroborates that the
  parameter-entity/external-DTD gap closed by `CAMEL-24416` is a distinct, previously-unfixed gap
  in the same file rather than a regression.
