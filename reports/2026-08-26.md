## Findings

### CAMEL-24487 — remote-file consumers never enforced `jailStartingDirectory` against server-reported names (path traversal, CWE-22)

- **Is this a vulnerability?** `SUSPECTED` at the commit level (no CVE/GHSA attached directly to the
  commit), but see the CVE-2026-66906/-60093/-66907 entries below — the same-day security-model
  docs update strongly suggests this class was just assigned CVE IDs.
  `GenericFileConsumer`/`RemoteFileConsumer` build the absolute remote path by concatenating the
  configured directory with the file name reported by the server's directory listing, then use
  that path directly for retrieve/delete/rename. No normalization or containment check was ever
  applied on that path for **remote** consumers — inconsistent with the file **producer** and the
  `localWorkDirectory` download path, which both already contain the resolved path (`CAMEL-23765`,
  `CAMEL-23868`). A malicious or compromised FTP/SFTP/Azure Files server (or a MITM on an
  unauthenticated/unverified transport) can return a listing entry containing `../` segments to
  make Camel operate on a file **outside** the configured directory.
- **Affected range vs. our version?** `AFFECTED` — **confirmed by direct code inspection**, not
  just by pattern-matching. I checked out the `camel-4.8.8` tag and found:
  - `jailStartingDirectory` defaults to `true` in `GenericFileEndpoint` (same as on `main`).
  - **4.8.8's `GenericFileConsumer.isValidFile()` has no containment check at all** — it only
    checks match filters and the in-progress repository. No producer-side check either (`grep` for
    `jailStartingDirectory` across 4.8.8 only turns up the field/getter/setter and generated
    endpoint configurers — never a place that actually consults it to reject a path).
  - **4.8.8's `GenericFileHelper.java` is 39 lines** and has no `isWithinDirectory` method of any
    kind — the entire containment mechanism this fix builds on (`CAMEL-23765`/`CAMEL-23868`)
    **postdates our pin**. In other words: in 4.8.8, `jailStartingDirectory` is a **dead option**
    for both the producer and the consumer — declared, documented, defaulting to `true`, but never
    enforced anywhere. This run's fix (CAMEL-24487) only closes the *last* of three gaps upstream;
    our version still has *all three* open.
- **Component in use?** `camel-ftp` and `camel-azure-files` are both in `used_components` →
  **USED**. (In 4.8.8, `camel-azure-files`'s `FilesConsumer` directly extends `camel-ftp`'s
  `RemoteFileConsumer` — confirmed by inspecting the 4.8.8 source — so both components share the
  same code path and the same gap.)
- **Severity:** High *(estimated)* — CWE-22/CWE-23 (path traversal). Impact depends on how much an
  operator trusts the remote FTP/Azure Files backend's directory listing; if that backend can be
  influenced by a lower-trust party (shared/multi-tenant storage, compromised credentials
  upstream, etc.), an attacker can cause file operations (read/delete/rename) outside the
  configured directory boundary. The August-2026 security-model rewrite (see below) explicitly
  reclassifies "names a remote store reports back" as attacker-controlled input, which supports
  a High rather than Medium estimate.
- **Verdict: AFFECTS US.**
- Sources: [apache/camel@177fb1fdff9](https://github.com/apache/camel/commit/177fb1fdff90632ebfd27772a625b720c1cab3e7)
  ("CAMEL-24487", PR [#25730](https://github.com/apache/camel/pull/25730)), merged 2026-08-25.
  Not in any released version; `camel-4.8.x` branch head unchanged (`5a31b93`, confirmed again
  this run via `git ls-remote`).

**Backport assessment:** Larger than a simple cherry-pick, because 4.8.8 predates the *whole*
jailing mechanism this fix extends, not just the consumer-side piece:
1. `components/camel-file/.../GenericFileHelper.java` — the fix adds a separator-aware
   `isWithinDirectory(String, String, char)` overload of an *existing* `isWithinDirectory(String,
   String)` method. **4.8.8 has neither method** — a human backport needs to add the base
   containment-check helper from scratch (logic is simple: compact both paths with
   `FileUtil.compactPath(path, sep)`, then check `target.equals(dir) || target.startsWith(dir +
   sep)`, with a leading `..`-escape guard), not just graft on the overload.
2. `GenericFileConsumer.java` — the fix adds an `isWithinStartingDirectory()` strategy method
   (no-op by default) and a call to it inside `isValidFile()`, gated on
   `endpoint.isJailStartingDirectory()`. 4.8.8's `isValidFile(GenericFile<T> file, boolean
   isDirectory, T[] files)` has a different (older, non-dynamic) signature than `main`'s
   Exchange/Supplier-based one, so the patch needs manual adaptation to the old signature rather
   than applying cleanly — conceptually trivial (same one `if` block, using
   `file.getAbsoluteFilePath()` directly instead of a passed-in string), but not a direct patch.
3. The module the override lives in changed: on `main` it's `camel-ftp-common`'s
   `RemoteFileConsumer.java` (a module extracted post-4.8.8); in 4.8.8 the equivalent file is
   `components/camel-ftp/src/main/java/org/apache/camel/component/file/remote/RemoteFileConsumer.java`.
   Confirmed `camel-azure-files`' `FilesConsumer` extends that same class in 4.8.8, so one override
   there covers both used components.
4. Tests to port: `GenericFileHelperTest`'s new cases for the separator-aware overload, and
   `RemoteFileConsumerStartingDirectoryJailTest` (FTP + SFTP coverage) — both would need
   rewriting against 4.8.8's test infrastructure since the helper/strategy being tested doesn't
   exist yet.

**Recommendation:** given 4.8.8 has *no* working `jailStartingDirectory` enforcement anywhere
(producer, `localWorkDirectory`, or remote consumer), treat this as "port `CAMEL-23765` +
`CAMEL-23868` + `CAMEL-24487`'s consumer-side check together" rather than a single-commit
backport, or write an equivalent standalone containment check directly against 4.8.8's existing
method signatures. A human should scope this properly rather than rely on this estimate.

### CVE-2026-78329 — `camel-undertow`: `headerFilterStrategy` silently overwritten, `CAMEL-23588` was inert since it shipped

- **Is this a vulnerability?** `CONFIRMED` per WebSearch (public advisory summary found; the
  primary Camel/NVD/GHSA pages themselves are blocked this session, so this is not independently
  re-verified against the authoritative source). `UndertowEndpoint` defaulted its
  `headerFilterStrategy` to the base `HttpHeaderFilterStrategy` and pushed that into the lazily
  created `UndertowHttpBinding`, overwriting the `UndertowHeaderFilterStrategy` that
  `DefaultUndertowHttpBinding` installs in its own constructor — so, absent a custom binding or an
  explicit `headerFilterStrategy`, Undertow-specific header filtering never ran. Reported affected
  range (per search summary): 4.11.0–4.14.9, 4.15.0–4.18.4, 4.19.0–4.22.0. Notably, this means
  **`CAMEL-24412`'s companion ticket `CAMEL-23588`** (already in `state/seen.json`, marked
  `NOT_RELEVANT` on 2026-08-13) was the fix that never actually took effect — the docs commit
  above states this outright ("the strategy was constructed and immediately overwritten so
  CAMEL-23588 had been inert since it shipped").
- **Affected range vs. our version?** Plausibly `AFFECTED` if 4.8.8 has the same construction-order
  bug (unverified — not investigated further given the component is unused, see below).
  Re-affirming the earlier `CAMEL-23588` verdict: that call was `NOT_RELEVANT` because
  `camel-undertow` is not a used component, and that reasoning is unaffected by this CVE (the fact
  that the fix was inert doesn't change which component it's in).
- **Component in use?** `camel-undertow` is **not** in `used_components` → **NOT-USED**.
- **Verdict: NOT RELEVANT** (component not used).
- Sources: WebSearch summary (no working primary link this run — `camel.apache.org`, `access.redhat.com`
  blocked); ties to already-tracked `CAMEL-23588` (2026-08-13) and `CAMEL-24412` (2026-08-23) in
  `state/seen.json`.
