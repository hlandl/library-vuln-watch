## Findings

No new vulnerability candidates (CONFIRMED or SUSPECTED) were found this run. Three new `CAMEL-` tickets landed in the lookback window; all three were read in full via `git show` and assessed `NOT-SECURITY`:

- **CAMEL-24514** — `camel-console`: adds a `DevConsole.isReadOnly()` SPI method (and a `@DevConsole(readOnly=...)` annotation attribute) so `ApiDevConsole` generates a `GET` operation (with query parameters) instead of always advertising `POST` for read-only dev consoles in the **generated OpenAPI spec**. This changes only the *documentation* of the `/q/dev` API surface — it does not add or remove any runtime access control, and does not change which HTTP methods the dev-console HTTP endpoint actually accepts or which consoles can mutate state (mutating consoles already required explicit console-name dispatch, not a bare route/verb check). No CWE class applies; this is an OpenAPI-accuracy fix, not a vulnerability fix. `camel-console` is a `used_component`, so this was inspected closely, but there is no behavior change to assess for backport. [apache/camel@53112be42](https://github.com/apache/camel/commit/53112be421e5f09140f53f468f14209cd0603130) (PR [#25883](https://github.com/apache/camel/pull/25883)).
- **CAMEL-24564** — `camel-tooling-model`: refactors the OpenAPI path/operation-building logic out of `ApiDevConsole` into a shared `DevConsoleOpenApiHelper`, and adds a build-time step that publishes a consolidated static `dev-consoles-openapi.json` into the `camel-catalog`, carrying forward the `readOnly` flag from CAMEL-24514. Explicitly described upstream as "behavior-preserving." `camel-tooling-model` is a `used_component`; no vulnerability, no runtime change. [apache/camel@78cc0bd0d](https://github.com/apache/camel/commit/78cc0bd0daa6c523c4435e819e952e6577e52b5e) (PR [#25885](https://github.com/apache/camel/pull/25885)).
- **CAMEL-24550** — documentation-only PR (`.adoc` files) describing which SDK exception types `camel-openai`/`camel-langchain4j-chat` propagate for `onException` handling. Neither component is in `used_components`. `NOT-SECURITY`, `NOT-USED`. [apache/camel@2e66cc233](https://github.com/apache/camel/commit/2e66cc2330c57ffc56590a63884b1d88ae94ae31) (PR [#25888](https://github.com/apache/camel/pull/25888)).

One additional commit was reviewed for security relevance despite carrying no `CAMEL-` ticket, because it touches the XPath/XQuery/XTokenize language stack (the same area as the `CAMEL-24475` XXE fix already tracked from the 2026-08-29 report): **"Add namespacesRef to XPath/XQuery/XTokenize expressions" ([#25843](https://github.com/apache/camel/pull/25843), [apache/camel@9a1f3883f](https://github.com/apache/camel/commit/9a1f3883f947936e56a1f7385d0790ad8be62dd4))**. It adds an option to reference a registry-bound `Namespaces` bean instead of inlining namespace-prefix mappings, purely a DSL convenience feature reusing the existing namespace-context mechanism — no new parser/entity-resolution surface, no change to document handling. Assessed `NOT-SECURITY`; not added to `state/seen.json` as a tracked fingerprint (no security-adjacent signal beyond topical proximity), consistent with how ordinary feature PRs have been handled in prior runs.

All 41 remaining non-ticketed commits in the window (dependency bumps, component removals, flaky-test fixes, doc/build chores) were grep'd for the standard security-keyword set (`CVE`, `security`, `vulnerab`, `CWE`) with no matches, and are the same categories excluded in every prior run.
