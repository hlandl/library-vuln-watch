## Findings

### CAMEL-24412 — camel-netty-http: security constraint evaluated against a different target than dispatch uses

- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA assigned yet. Upstream's own commit
  message describes it in security terms: an authentication/authorization bypass. Flagging per
  AGENT.md step 2 ("silent fixes... flag as SUSPECTED").
- **Source / evidence:**
  - Commit: [apache/camel@9c18465443a0df60179e6abf96f7794983cd0637](https://github.com/apache/camel/commit/9c18465443a0df60179e6abf96f7794983cd0637)
    ("CAMEL-24412: camel-netty-http - evaluate the security constraint against the same normalized
    target as dispatch (#25578)"), merged 2026-08-22.
  - Jira: [CAMEL-24412](https://issues.apache.org/jira/browse/CAMEL-24412) (not independently
    fetchable this run — issues.apache.org blocked; ticket key taken from the commit message).
  - No GHSA/CVE exists yet for this ticket (checked github.com/advisories query for
    `org.apache.camel` — most-recently-updated entry is GHSA-2c2h-2855-mf97 / CVE-2025-27636,
    unrelated and stale; nothing newer).
- **What it is:** `HttpServerChannelHandler.extractTarget()` strips the endpoint's configured
  context-path from the incoming request path before the security constraint is evaluated. The
  strip was guarded by a **case-sensitive** `target.startsWith(path)` check that wrapped an inner
  case-insensitive comparison — the inner comparison was dead code, since if the outer
  case-sensitive check failed, the strip was skipped entirely and the constraint was evaluated
  against the raw (unstripped) target. Request **dispatch**, however, uses
  `RestConsumerContextPathMatcher.matchPath()`, which matches the context-path
  case-insensitively. So a request path that differs from the configured endpoint path only in
  case (e.g. `/Foo/admin` vs. configured `/foo`) is routed to the endpoint (dispatch matched
  case-insensitively) but the security constraint sees the *unstripped* target and, if the
  constraint's inclusions are specific sub-paths rather than a catch-all `/*`, finds no matching
  inclusion — and an unmatched target is treated as unrestricted, so the request is let through
  with **HTTP 200 and no auth challenge** instead of a 401.
- **Does the affected range include our pinned version (4.8.8)?** `AFFECTED`. Verified directly —
  `git show camel-4.8.8:components/camel-netty-http/.../HttpServerChannelHandler.java` contains the
  identical case-sensitive-then-case-insensitive dead-code pattern that the fix removes — the bug
  predates 4.8.8 and is present in our pinned version unchanged.
- **Is an affected component in `used_components`?** `NOT-USED`. `config/libraries.yaml`'s
  `used_components` list (built from the deployed 4.8.8 jar list) contains no `camel-netty-http`,
  `camel-netty`, or `camel-jetty` entry — only `camel-http-base`/`camel-http-common`/`camel-rest`/
  `camel-servlet` for HTTP, none of which run through this Netty HTTP consumer path.
- **Severity:** No CVSS published (no CVE yet). Reasoned estimate: **HIGH** *(estimated)* — full
  authentication bypass on an HTTP consumer endpoint, CVSS-like vector roughly
  `AV:N/AC:L/PR:N/UI:N/C:H` — but conditional on a specific, non-default configuration
  (`securityConfiguration` with sub-path inclusions rather than a catch-all `/*`, and a request
  differing only in path case), which is why it likely hasn't been assigned a CVE/GHSA yet.
- **Verdict: NOT RELEVANT** — not affected in practice because `camel-netty-http` is not deployed.
- **Official fix / backport assessment:** Not applicable — we do not carry this component, so no
  backport is proposed. Recorded here only so that if `used_components` is ever updated to include
  `camel-netty-http` (or a Netty-HTTP-based component is introduced), this ticket is the one to
  check first. For reference, the fix itself is a 3-line change (see diff in the commit above:
  drops the outer case-sensitive guard, compares lower-cased target/path directly) plus a new test
  `NettyHttpBasicAuthConstraintCaseInsensitiveTest` — it would apply cleanly to 4.8.8's identical
  code.
