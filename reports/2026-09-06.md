## Findings

### CAMEL-24627 — symlink escape of `localWorkDirectory` containment in file-based download components

- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA is attached to this ticket as of this run (confirmed via `WebSearch`; only Jira/mailing-list mirrors and the upstream commit are indexed), but it was resolved as a security hardening fix and **backported to two maintenance branches** (`camel-4.18.x`, `camel-4.22.x`) in addition to `main` — a strong signal upstream treats it as security-relevant, not a routine bugfix.
  `GenericFileHelper.jailToLocalWorkDirectory(File, File)` — the method that constrains where a downloaded remote file is written locally — only ever performed a **lexical** string-prefix check on the target path (`isWithinDirectory`). It never resolved symbolic links. A symlink placed inside the configured `localWorkDirectory` (e.g. planted by an earlier malicious download, or present via misconfiguration) that points outside of it would pass the lexical check while the actual write landed outside the directory. The fix adds a second, filesystem-resolving check (`resolveExistingPathSegments`, walking to the nearest existing ancestor and calling `toRealPath()`) after the lexical one, and rejects the write if the resolved target escapes the resolved work directory. This brings `camel-file`, `camel-ftp`/`sftp`, `camel-smb`, `camel-mina-sftp` and `camel-azure-files` to parity with the symlink-aware hardening already done for cloud-storage downloads in `CAMEL-24548`/`CAMEL-24549` (see `state/seen.json`, both recorded 2026-09-02).
- **Does the affected range include our pinned version?** This is the subtle part. **Direct source read of the `camel-4.8.8` tag confirms `GenericFileHelper.java` is the original 39-line file with no `isWithinDirectory`/`jailToLocalWorkDirectory` method at all** — the entire containment mechanism this commit hardens (introduced by `CAMEL-23765`/`CAMEL-23868`, not individually tracked in `state/seen.json` but documented as part of the `CAMEL-24487` investigation on 2026-08-26) **postdates our pin**. So the *specific* defect this commit fixes (a lexical check bypassable via symlink) does not exist verbatim in 4.8.8's code, because 4.8.8 has **no containment check whatsoever** on `localWorkDirectory` writes — not even the weaker lexical one. That is already-known territory: `reports/2026-08-26.md` established (and `CAMEL-24487`, `AFFECTS_US`, is already in `state/seen.json`) that 4.8.8 has zero enforcement on all three containment points (producer, `localWorkDirectory`, remote consumer). A symlink-based escape trivially succeeds against "no check at all," same as a plain `../` escape does — so the underlying vulnerability class (arbitrary-location writes when downloading through `camel-file`/`camel-ftp`/`camel-azure-files`) is `AFFECTED`, unchanged from the existing `CAMEL-24487` verdict.
- **Component in use?** `camel-file`, `camel-ftp`, `camel-azure-files` are all `used_components` → **USED**. (`camel-smb`, `camel-mina-sftp` are not used_components, but that doesn't change the verdict since the used components share the same code path.)
- **Severity:** High *(estimated)* — same class and rationale as `CAMEL-24487` (CWE-22/CWE-59 — path traversal / improper link resolution).
- **Verdict: AFFECTS US.** Not a brand-new vulnerability class for us (the underlying gap was already reported 2026-08-26 under `CAMEL-24487` and remains `AFFECTS_US` in state), but material new information for the backport: **the human backport of `CAMEL-24487`/`CAMEL-23765`/`CAMEL-23868` should build the symlink-resolving check directly**, not the simpler lexical-only version, since upstream itself found the lexical-only version insufficient and had to re-patch it about six weeks after introducing it.

**Backport assessment:** No change to the substance of `CAMEL-24487`'s existing backport plan (`reports/2026-08-26.md`: port `CAMEL-23765` + `CAMEL-23868` + `CAMEL-24487`'s consumer-side check together, since 4.8.8 has none of the three enforcement points). This run's addition: when a human writes the from-scratch `localWorkDirectory` containment check for 4.8.8, **implement it as symlink-resolving from the start** — i.e. base the new code on this commit's `resolveExistingPathSegments` pattern (resolve to nearest existing ancestor via `Files.exists(..., LinkOption.NOFOLLOW_LINKS)`, then `toRealPath()`, then re-check containment) rather than on the simpler `isWithinDirectory` lexical check alone. The pattern is self-contained (~20 lines, no new dependencies) and its test (`GenericFileHelperTest.shouldRejectSymlinkEscapingLocalWorkDirectory`) is straightforward to port once the base method exists. Changed files: `components/camel-file/src/main/java/org/apache/camel/component/file/GenericFileHelper.java`, its test, and an upgrade-guide doc entry (doc not applicable to an internal backport).
