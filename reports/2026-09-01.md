## Findings

### CAMEL-23315 — `camel-exec`: no opt-in gate on control headers before Camel 4.20 (our pinned 4.8.8 predates it entirely)

- **Verdict: AFFECTS US.** Severity: **CRITICAL** *(estimated — CWE-78 OS command injection if any exchange header can be influenced by untrusted data; no independent CVE/GHSA has been assigned to this specific hardening ticket, but it is the same vulnerability class as the well-documented `CamelExecCommandArgs`-header-injection RCE pattern, e.g. the public writeups for CVE-2025-29891/CVE-2026-33454)*.
- **Vulnerability:** `SUSPECTED` — a security-hardening fix with no CVE/GHSA of its own, discovered via the `apache/camel` commit sweep (this run's substitute for the blocked Jira/GHSA/NVD sources; see Source health).
- **How it was found this run:** `CAMEL-24464` ("Clarify exec control headers require allowControlHeaders") is a new ticket in this run's lookback window — two commits, [`19e69f186f`](https://github.com/apache/camel/commit/19e69f186fb715e198b30d1876e83bca7941a66a) and [`8e3e3311b6`](https://github.com/apache/camel/commit/8e3e3311b6e1aec781f8600d3ab9283895edf9d0). Both are **documentation-only** for the upcoming 4.23 release (clarify docs, add a once-per-endpoint WARN log, annotate the existing `allowControlHeaders` option `security="insecure:dev"` so `camel.main.profile=prod` rejects it). They reference the actual security-relevant change, **`CAMEL-23315`** ("Add option to turn on|off control headers for camel-exec to make it more restricted by default"), which shipped in **Camel 4.20.0** (commit [`67ef42d8019`](https://github.com/apache/camel/commit/67ef42d8019d668a678f12c14e577c434f1987a5), PR #22586, 2026-04-13) — well before this run's lookback window, and never previously recorded in `state/seen.json`. This looks like a genuine backfill gap from the multi-week Jira/NVD/GHSA outage (see Source health / Method notes): the ticket carries no CVE/GHSA and no "security" Jira label our old JQL-based sweep would have caught even when Jira was reachable, so it was only surfaced now via the docs follow-up landing in-window.
- **Root cause (confirmed by reading the code):** Before `CAMEL-23315`, `DefaultExecBinding.getAndRemoveHeader()` unconditionally read `CamelExecCommandExecutable`, `CamelExecCommandArgs`, `CamelExecCommandWorkingDir`, `CamelExecCommandTimeout`, `CamelExecExitValues`, `CamelExecCommandOutFile`, `CamelExecUseStderrOnEmptyStdout`, and `CamelExecCommandLogLevel` from the in-message and used them to override the endpoint's URI-configured executable/args/etc. **Any code path that leaves one of these headers set on the exchange before it reaches a `camel-exec` producer — a forwarded/copied header from an upstream protocol, a processor that promotes a property to a header, or a header-filter gap elsewhere in the route — fully controls the command, arguments, and working directory `camel-exec` executes.** `CAMEL-23315` (Camel 4.20.0) closed this by adding an `allowControlHeaders` endpoint/component option, **defaulting to `false`**: when false, the control headers are ignored entirely (not even removed) and the exec executable/args must come from the URI.
- **Affected range vs. our version:** Our pinned **4.8.8 predates 4.20.0 by two years of releases and has no equivalent flag at all** — confirmed directly against the `camel-4.8.8` tag: `ExecEndpoint`/`ExecComponent` have no `allowControlHeaders` field, and `DefaultExecBinding.bindToArguments()` calls the old unconditional `getAndRemoveHeader(exchange.getIn(), EXEC_COMMAND_EXECUTABLE, ...)` for every one of the eight control headers, exactly matching the pre-fix code shown in the `67ef42d8019` diff → **AFFECTED**, with no way to disable it in 4.8.8 short of a custom `ExecBinding`.
- **Component analysis:** `camel-exec` **is** in `used_components` → `USED`.
- **Relationship to an existing tracked finding:** This compounds the already-tracked **`CVE-2026-40453`** (AFFECTS_US since 2026-08-06) — that advisory's own exploit-chain writeup calls out `camel-exec` (via `camel-jms`'s incomplete case-sensitive header filter) as a way to smuggle a forged `CAmelExecCommandExecutable`-style header into an exchange. `CAMEL-23315`/this finding is the independent, more fundamental gap: even without any header-filter bypass bug, `camel-exec` in 4.8.8 will honour those headers from **any** source that leaves them on the exchange, by design, with no opt-in required. It is being tracked as a separate finding (distinct root cause and distinct upstream fix commit) rather than folded into `CVE-2026-40453`.
- **Sources:**
  - New ticket surfaced this run: [`CAMEL-24464`](https://github.com/apache/camel/commit/19e69f186fb715e198b30d1876e83bca7941a66a) (docs/warning clarification, 4.23) and [sync commit](https://github.com/apache/camel/commit/8e3e3311b6e1aec781f8600d3ab9283895edf9d0)
  - Underlying fix: `CAMEL-23315`, commit [`67ef42d8019d668a678f12c14e577c434f1987a5`](https://github.com/apache/camel/commit/67ef42d8019d668a678f12c14e577c434f1987a5) (PR #22586), first released in **4.20.0**
  - Confirmed against pinned tag: `camel-4.8.8` (`components/camel-exec/src/main/java/org/apache/camel/component/exec/impl/DefaultExecBinding.java`, `ExecEndpoint.java`)
  - Related tracked finding: `CVE-2026-40453` (see `reports/2026-08-06.md`)
- **Official fix + backport assessment:** The `67ef42d8019` fix is small and self-contained: adds a `boolean allowControlHeaders` field (default `false`) to `ExecComponent`/`ExecEndpoint`, and gates every `getAndRemoveHeader()` call (plus the separate `EXEC_COMMAND_ARGS` read) in `DefaultExecBinding.bindToArguments()` behind `endpoint.isAllowControlHeaders()`. **The pinned 4.8.8 code has the identical pre-fix shape verified line-for-line against the diff's `-` lines (same method signature, same field layout, same constructor style) — the patch should apply cleanly with no drift.** Recommend backporting: (1) the `allowControlHeaders` field + getter/setter on `ExecComponent` and `ExecEndpoint` (default `false`, i.e. **secure-by-default**, which is a behavioural change from 4.8.8's current always-on default — flag this to the business as a deliberate breaking change, matching upstream's own approach), (2) the `getAndRemoveHeader(ExecEndpoint, Message, ...)` signature change gating all eight control headers, (3) port `ExecProducerTest`/`DefaultExecBindingTest` coverage for both the allowed and disallowed cases. The 4.23 `security="insecure:dev"` / `SecurityUtils` profile-blocking metadata from `CAMEL-24464` is optional polish (that profile mechanism likely doesn't exist in 4.8.8's `camel-main`) and can be skipped in the backport.
