### CAMEL-25106 — camel-kafka: configuring only `sslContextParameters` silently leaves the connection on PLAINTEXT
- **Verdict**: AFFECTS US — **Severity: HIGH (estimated)**, no CVE/GHSA yet (SUSPECTED, silent fix)
- `KafkaConfiguration.createProducerProperties()`/`createConsumerProperties()` applied `sslContextParameters`
  (setting `ssl.keystore.*`/`ssl.truststore.*`/etc.) but never touched `security.protocol`, which stays at its
  field default `CommonClientConfigs.DEFAULT_SECURITY_PROTOCOL = "PLAINTEXT"` unless `securityProtocol` is *also*
  explicitly set. Kafka's client ignores all `ssl.*` properties when `security.protocol=PLAINTEXT`, so an endpoint
  configured with only `sslContextParameters` — a very natural, common configuration pattern — silently opens a
  completely unencrypted, unauthenticated socket to the broker. No error, warning, or exception. CWE-319
  (cleartext transmission), effectively also CWE-295 (no certificate validation occurs at all under plaintext).
- Confirmed via direct source read of the **camel-4.8.8 tag** (`components/camel-kafka/.../KafkaConfiguration.java`
  lines 315, 410–417, and the consumer-side equivalent): the identical pattern is present unchanged.
  `camel-kafka` **is** a `used_component`.
- **Recommend an immediate configuration audit, independent of any code fix**: check whether any of our Kafka
  endpoint/component configs set `sslContextParameters` without also explicitly setting
  `securityProtocol=SSL`/`SASL_SSL` — if so, that traffic is unencrypted today.
- Source: [PR #27010](https://github.com/apache/camel/pull/27010), commit
  [apache/camel@7057526](https://github.com/apache/camel/commit/7057526605849e02dfc85b83ef3223abef238650), merged
  2026-09-28.
- **Official fix / backport assessment**: ships first in unreleased main (4.23.0). Backport PRs for camel-4.22.x
  and camel-4.18.x both exist but reportedly hit cherry-pick conflicts on the PR page; **no camel-4.8.x port
  exists or is planned upstream**. The upstream patch also reorders endpoint-option-vs-context SSL precedence
  (`addSslOption()` helper), a moderately invasive change — not a trivial cherry-pick. Recommended minimal
  in-house backport: add a `resolveSecurityProtocol()` that auto-upgrades `PLAINTEXT`→`SSL` whenever
  `sslContextParameters` is set and `securityProtocol` is still at its default, called immediately before the
  existing `addPropertyIfNotEmpty(SECURITY_PROTOCOL_CONFIG, ...)` line in both property-building methods. Port the
  new `KafkaSslContextParametersTest`.

### CAMEL-24451 — camel-xslt: runtime `document()` calls bypass `ACCESS_EXTERNAL_STYLESHEET` (SSRF / arbitrary file read)
- **Verdict**: AFFECTS US — **Severity: HIGH (estimated)**, no CVE/GHSA yet
- The XPath `document()` function inside an XSLT stylesheet fetches an arbitrary URI at transform time. JAXP's
  `ACCESS_EXTERNAL_STYLESHEET` `TransformerFactory` attribute is the standard defense, but per the JAXP spec it is
  **only enforced when no custom `URIResolver` returns a `Source`** — and `XsltBuilder` always installs its own
  `XsltUriResolver`, which resolved `http:`/`https:`/`ftp:`/`file:` URIs completely unconditionally (confirmed:
  the pre-fix `resolve()` has no access check anywhere). This silently defeats `ACCESS_EXTERNAL_STYLESHEET`
  hardening even on deployments (e.g. `camel-xslt-saxon`, or a custom `transformerFactory`) that explicitly set
  it to restrict external access. Compounding this, `XsltBuilder` binds **every inbound message header** as a
  stylesheet parameter (confirmed at line 480 of 4.8.8's `XsltBuilder.java`), so an attacker who controls any
  header on a route ending in an `xslt:` step, combined with a stylesheet parameter reaching `document()`, can
  direct the transform to fetch an internal URL (SSRF, CWE-918) or read a local file
  (`file:///etc/passwd`, CWE-73) and have the result merged into the transform output.
- Confirmed present verbatim in the **camel-4.8.8 tag**. `camel-xslt` **is** a `used_component`.
- **Caveat**: plain `camel-xslt` never itself sets `ACCESS_EXTERNAL_STYLESHEET`/secure-processing on the
  `TransformerFactory` (neither in 4.8.8 nor current main), so a fully-default JAXP `TransformerFactory` was
  already at risk of `document()`-based SSRF/file-read independent of this bug — this fix specifically closes the
  gap for deployments relying on hardening via `camel-xslt-saxon` or a custom `transformerFactory`.
- **Immediate mitigation, regardless of backport timing**: configure a hardened `TransformerFactory` (or the
  JVM-wide `javax.xml.accessExternalStylesheet`/`accessExternalDTD` system properties), and strip/allow-list
  headers before any `xslt:` step whose stylesheet uses `document()` with a parameter.
- Source: [PR #26904](https://github.com/apache/camel/pull/26904), commit
  [apache/camel@e65fd91](https://github.com/apache/camel/commit/e65fd915f6fd0be99da1186216a79a65104149cb), merged
  2026-09-28.
- **Backport assessment**: self-contained to `XsltBuilder.java`/`XsltUriResolver.java` in `components/camel-xslt`
  (+ the Saxon module). 4.8.8's constructor/`resolve()` signature is close enough that the new
  `checkExternalAccessAllowed`/`parseAllowedProtocols` logic should port with minor adaptation. Port
  `XsltUriResolverExternalAccessTest`. No camel-4.8.x backport label upstream.

### CAMEL-25017 — Claim Check EIP: parallel exchange copies share one (non-thread-safe) repository
- **Verdict**: AFFECTS US — **Severity: MEDIUM–HIGH (estimated)**, no CVE/GHSA yet
- `ClaimCheckProcessor.getClaimCheckRepository()` lazily creates a `DefaultClaimCheckRepository` (a plain
  `HashMap`/`Deque`, not thread-safe) and stores it as an ordinary exchange property. Camel's Splitter/Multicast/
  Recipient List/Wire Tap EIPs (and SEDA/Disruptor hand-off) shallow-copy the properties map when duplicating an
  Exchange, so every copy ends up holding a reference to the **same** repository object — with
  `parallelProcessing()`, concurrent split branches read/write the same map concurrently. Upstream's own
  upgrade-guide note: *"with parallel processing a Get or Pop could return the message of another part."* A
  realistic pattern: a `split().parallelProcessing()` route where each branch claim-checks a different
  record/customer payload under the same literal key — one branch's Get/Pop can retrieve a **different** branch's
  claimed-away exchange (headers + body). CWE-362 (race condition) → CWE-200 (information exposure) between
  concurrently processed parts of the same batch.
- Confirmed present verbatim in the **camel-4.8.8 tag** (`DefaultClaimCheckRepository`/`ClaimCheckProcessor` in
  `camel-core-processor`; `AbstractExchange.copy()`/`ExchangeHelper.copyExchangeWithProperties()` in
  `camel-support` only special-case `MESSAGE_HISTORY`, with zero claim-check handling).
  `camel-core`/`camel-core-processor` **are** `used_components` — this is our most heavily used module.
- Source: [PR #26882](https://github.com/apache/camel/pull/26882), commit
  [apache/camel@ab21f79](https://github.com/apache/camel/commit/ab21f790a87d3483f6be23dd4b8150a8dc62e3e4), merged
  2026-09-28.
- **Backport assessment**: applies cleanly — diffed all touch points (`AbstractExchange.copy()`, `ExchangeHelper`,
  `PooledProcessorExchangeFactory`, `DefaultClaimCheckRepository`/`ClaimCheckProcessor`) against 4.8.8 line-by-line;
  surrounding code matches exactly in every case, no drift. Port `ClaimCheckEipSplitParallelTest`,
  `ClaimCheckEipStoreCopyTest`, `PooledExchangeClaimCheckEipSplitParallelTest`. Recommend prioritizing.

### CAMEL-24650 — camel-http-common: multipart `fileNameExtWhitelist` is a substring check, not a whitelist match
- **Verdict**: AFFECTS US — **Severity: MEDIUM (estimated)**, no CVE/GHSA yet
- `DefaultHttpBinding.populateAttachments()` checked an uploaded file's extension via
  `!fileNameExtWhitelist.contains(ext)` — a substring match. With a whitelist like
  `"html,htm,txt,csv,pdf,doc,docx,xls,xlsx"`, a crafted short extension that happens to be a substring of any
  allowed entry (`ls`⊂`xls`, `oc`⊂`doc`, `ml`⊂`html`) is incorrectly **accepted** even though never actually
  whitelisted. CWE-434 (unrestricted upload of file with dangerous type). `camel-servlet`/`camel-jetty`'s own
  `AttachmentHttpBinding` already had a correct exact-match implementation from an earlier fix (CAMEL-24427); this
  bug is specific to `DefaultHttpBinding`'s own separate, older, buggy copy, used by any HTTP-server component
  built directly on `camel-http-common` without a jetty/servlet-specific override.
- Confirmed present verbatim in the **camel-4.8.8 tag**
  (`components/camel-http-common/.../DefaultHttpBinding.java` line 339); `HttpCommonEndpoint` instantiates
  `DefaultHttpBinding` directly as the default binding. `camel-http-common` **is** a `used_component`.
- Severity depends on which HTTP-server component(s) we run on the base `DefaultHttpBinding` (vs. a servlet/jetty
  override) and whether an explicit `fileNameExtWhitelist` is configured at all (default `"*"` is unaffected).
- Source: [PR #26872](https://github.com/apache/camel/pull/26872), commit
  [apache/camel@0099984](https://github.com/apache/camel/commit/0099984f836579b0ca53f95ff81f7870cd7e24eb), merged
  2026-09-28.
- **Backport assessment**: applies cleanly — self-contained method replacement (`isFileNameAccepted`) inside
  `DefaultHttpBinding.java`. Port `DefaultHttpBindingTest.testFileNameAcceptedDoesNotMatchSubstring`.

### CAMEL-25023 — camel-util: `IOHelper.copy` int-overflow silently disables decompression-size limits ≥ 2 GiB
- **Verdict**: AFFECTS US — **Severity: MEDIUM (estimated)**, no CVE/GHSA yet
- `IOHelper.copy(InputStream, OutputStream, int bufferSize, boolean flushOnEachWrite, long maxSize)` — the shared
  size-limit-enforcing copy routine behind decompression-bomb guards such as `camel-zipfile`'s
  `maxDecompressedSize` — accumulated the running byte count in an `int total` while comparing against the
  already-`long` `maxSize`. Once the cumulative sum overflows past `Integer.MAX_VALUE` (~2.147 GiB) via int
  arithmetic, `total` wraps negative, and a negative int compared against a large positive `maxSize` is always
  false — the size check silently stops firing forever above ~2 GiB, for any `maxDecompressedSize` configured at
  2 GiB or higher. CWE-190 (integer overflow) enabling CWE-409/CWE-400 (decompression bomb / resource exhaustion).
  The default `maxDecompressedSize` (1 GiB) is below the wrap point and unaffected — only deployments that have
  explicitly raised the limit lose protection above ~2 GiB.
- Confirmed present verbatim in the **camel-4.8.8 tag** (`core/camel-util/.../IOHelper.java` line 241
  `int total = 0;`, lines 260–261). `camel-util` and `camel-zipfile` **are both** `used_components`;
  `ZipFileDataFormat`/`ZipIterator` call this exact overload with `maxSize`.
- Exposure is currently theoretical unless our configuration sets `maxDecompressedSize` ≥ 2 GiB on
  `camel-zipfile`/`camel-tarfile` — recommend auditing this regardless of backport timing.
- Source: [PR #26892](https://github.com/apache/camel/pull/26892), commit
  [apache/camel@d51cc4c](https://github.com/apache/camel/commit/d51cc4c98a9fe98f2c5c7d148eea0d5526445fb3), merged
  2026-09-28.
- **Backport assessment**: applies cleanly — trivial, self-contained local-variable-type change (`int`→`long`
  accumulator, capped return), no signature change. Port `IOHelperTest.testCopyMaxSizeOfTwoGigabytesOrMore`/
  `testCopyMoreThanTwoGigabytes` (synthetic zero-input-stream, no multi-GB allocation needed). Cheap enough to
  backport proactively.

### CAMEL-25104 — camel-core: default TLS cipher/protocol filters don't exclude 3DES or TLSv1/TLSv1.1
- **Verdict**: AFFECTS US — **Severity: MEDIUM (estimated)**, no CVE/GHSA yet
- `BaseSSLContextParameters` ships two hard-coded default filters used whenever a user does not configure explicit
  cipher-suite/protocol filters. Pre-fix: `DEFAULT_CIPHER_SUITES_FILTER_EXCLUDE` had no `3DES` pattern (only
  NULL/anon/EXPORT/DES/MD5/RC4), and `DEFAULT_SECURE_SOCKET_PROTOCOLS_FILTER_EXCLUDE` was `"SSL.*"` only (doesn't
  exclude TLSv1/TLSv1.1). Separately, the `SSLServerSocket` configurer computed its "available values" from
  `socket.getSupportedCipherSuites()`/`getSupportedProtocols()` (the JDK's *full raw-supported* list, which
  includes suites/protocols the JVM's own `jdk.tls.disabledAlgorithms` policy already excludes from its *enabled*
  defaults) instead of the already-hardened `getSSLParameters()` form the `SSLEngine`/`SSLSocket` configurers
  correctly use. Net effect: Camel's own default filtering can silently re-widen the negotiable protocol/cipher
  set beyond what the JVM would otherwise enable by default — legacy TLSv1/TLSv1.1 and 3DES/Sweet32-vulnerable
  ciphers remain negotiable, purely from Camel's own filtering, with zero user configuration involved. CWE-757
  (selection of less-secure algorithm), CWE-327 (broken/risky crypto algorithm).
- Confirmed present in the **camel-4.8.8 tag** (`core/camel-api/.../jsse/BaseSSLContextParameters.java` lines
  61–68 for the filter lists; lines ~599–628 for the `SSLServerSocket` configurer — the `SSLEngine`/`SSLSocket`
  configurers in 4.8.8 already use `getSSLParameters()`, so the "supported vs enabled" defect is scoped only to
  the `SSLServerSocket` path in both versions). `camel-core` **is** a `used_component`.
- Source: [PR #27008](https://github.com/apache/camel/pull/27008), commit
  [apache/camel@3e7c7cd](https://github.com/apache/camel/commit/3e7c7cd0d997bd8c6e872e10aa704a60f79a55d9), merged
  2026-09-28.
- **Backport assessment**: applies cleanly — same file/package in both trees, identical surrounding code; the
  ~12-line upstream diff should apply with at most trivial offset. Port `SSLContextParametersDefaultProtocolsTest`.
  No camel-4.8.x backport label upstream (only 4.22.x/4.18.x requested).

### CAMEL-24756 — camel-base-engine: `http:`/`https:` resource resolution has no connect/read timeout
- **Verdict**: AFFECTS US — **Severity: LOW–MEDIUM (estimated)**, no CVE/GHSA yet
- `DefaultResourceResolvers.HttpResource` (used for `http:`/`https:` `resource:` locations — e.g. loading routes,
  schemas, or scripts from a remote URL) opened its `URLConnection` with neither `setConnectTimeout` nor

  consumption) / availability impact via unbounded hang; attacker relevance is scoped to deployments where the
  `http:` resource location is influenced by external/dynamic input rather than a fixed, operator-authored
  location.
- Confirmed present in the **camel-4.8.8 tag** — no timeout call exists anywhere in `HttpResource`.
  `camel-base-engine` **is** a `used_component`.
- Source: [PR #26734](https://github.com/apache/camel/pull/26734), commit
  [apache/camel@92f6f78](https://github.com/apache/camel/commit/92f6f789ff0cac3e05da3da710b8e26fb9d69325), merged
  2026-09-28.
- **Backport assessment**: applies cleanly — self-contained addition of timeouts (10s connect / 30s read
  defaults, overridable), no signature change to existing call sites beyond the internal `HttpResource`
  construction. Add a basic connect/read-timeout unit test if backporting.

### CAMEL-25089 — camel-cluster: `FileLockClusterView.doStop()` releases leadership without notifying the route policy first (NEEDS REVIEW)
- **Verdict**: NEEDS REVIEW — **Severity: LOW–MEDIUM (estimated)**, no CVE/GHSA yet
- `FileLockClusterView.doStop()` released the OS file lock (letting another cluster member become leader) without
  first firing a leadership-lost event to local listeners (notably `ClusteredRoutePolicy`, which starts/stops
  managed routes based on leadership). This opens a window during graceful shutdown/redeploy/scale-down where a
  new leader starts its managed routes while the old leader's routes haven't yet been told to stop — two members
  briefly both actively running the same clustered route (e.g. both reading/processing the same files), risking
  duplicate processing / data-integrity issues rather than a classic auth/injection vulnerability.
- Confirmed the same missing-notification defect class exists in the **camel-4.8.8 tag**
  (`FileLockClusterView.doStop()` calls only `closeInternal()`/`lock.release()`, no leadership-change event
  anywhere in the stop path). `camel-cluster` **is** a `used_component`.
- Marked NEEDS REVIEW rather than AFFECTS US because the practical blast radius depends on whether our deployment
  actually uses `camel-file`'s `FileLockClusterView` for clustering (vs. another cluster-service implementation)
  and on route idempotency under brief duplicate processing.
- Source: [PR #26990](https://github.com/apache/camel/pull/26990), commit
  [apache/camel@c7f696b](https://github.com/apache/camel/commit/c7f696b9e08f3699dd7c4ae7840e564f57573bd1), merged
  2026-09-28.
- If confirmed relevant: small, targeted backport (insert a `wasLeader`-gated leadership-lost notification before
  the lock/data-file release in `doStop()`).

### CAMEL-25063 — camel-management: MBean XML dumps don't escape `"`; `sourceLocation` unescaped entirely (NEEDS REVIEW)
- **Verdict**: NEEDS REVIEW — **Severity: LOW (estimated)**, no CVE/GHSA yet
- `ManagedCamelContext`/`ManagedRoute`'s `escapeXml()` helper (used when serializing route/context statistics to
  XML via `dumpRouteAsXml`/`dumpRoutesAsXml`/`dumpStepStatsAsXml`, reachable via JMX MBean operations) escaped
  `&`, `<`, `>` but **not** the double-quote character — and `sourceLocation` was not passed through `escapeXml`
  at all pre-fix, using the raw value directly interpolated into an XML **attribute** (`sourceLocation="%s"`). A

  additional XML structure into the dumped output (XML-injection-adjacent, CWE-91-ish). Exploitability is narrow:
  it requires control over a route id or source-location string (typically developer/deployment-controlled) and
  a downstream consumer that parses the dumped XML naively. Also fixed in the same commit: a JMX-wildcard
  route-id-matching bug in `reset(true)` that could reset stats of unrelated routes (blast-radius/correctness
  issue for an already-authorized JMX caller, not privilege escalation).
- Confirmed the **camel-4.8.8 tag** has an even less-escaped form: `ManagedRoute.java` interpolates the raw
  `getSourceLocation()` value into `sourceLocation="%s"` with **no** `escapeXml` call at all (lines 546, 615, 667,
  677). `camel-management` **is** a `used_component`.
- Source: [PR #26946](https://github.com/apache/camel/pull/26946), commit
  [apache/camel@80dd201](https://github.com/apache/camel/commit/80dd201302eaffde681e37b56b9f3a117c3cae12), merged
  2026-09-28.
- If confirmed relevant: straightforward backport (switch to a quote-escaping helper, apply to `sourceLocation`
  everywhere it's interpolated).

### CAMEL-25084 — camel-util: `FileUtil.compactPath` Windows-drive edge case in the camel-file jail-check path (NEEDS REVIEW)
- **Verdict**: NEEDS REVIEW — **Severity: LOW (estimated), exploitability unconfirmed**, no CVE/GHSA yet
- Among a broad batch of camel-util correctness fixes, one touches `FileUtil.compactPath()`'s `..`-collapsing
  stack logic: pre-fix, encountering `..` when the stack held only a single Windows drive-letter entry (e.g.
  `"C:"`) would pop that drive-letter entry too (no guard against popping below a drive root). `compactPath()` is
  the function `GenericFileProducer.jailedCheck()` — camel-file's core path-traversal containment check ("file
  must be within starting directory") — calls on **both** the candidate answer and the configured base directory
  before comparing them. On manual trace-through of a Windows-drive baseDir scenario, the over-popping appears to
  produce a compacted answer that no longer starts with the compacted baseDir — i.e. the containment check would
  likely still *reject* (fail closed) rather than being bypassed, so this looks more like a correctness/confusing-
  error-message bug than a proven jail-check bypass. This has **not** been proven safe with an actual reproduction
  on a Windows-path baseDir, and `jailedCheck` is the same defense class as the already-tracked CAMEL-24419
