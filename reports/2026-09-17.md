## Findings

### CAMEL-24734 — camel-spiffe: validate a JWT-SVID against every configured audience
- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA assigned; genuine security-relevant fix found via the GitHub repository sweep.
- **Detail:** `SpiffeProducer.validateJwtSvid` used `audiences[0]` and silently discarded the rest of the configured `audience` list, while the sibling `fetchJwtSvid` path honoured all of them — so the same `audience` option meant "list" for minting and "single value" for validating, silently enforcing a narrower check than the operator configured. Rebased onto `CAMEL-24730` (already tracked, 2026-09-15), which had removed the header-controlled `CamelSpiffeAudience` override from this same path. Fixed by trying each configured audience in turn against the Workload API (which validates one audience per call), accepting on the first match and only rethrowing the last failure once every audience has failed.
- **Affected range vs. our version:** N/A — `camel-spiffe` is new in the unreleased 4.23.0 line; does not exist in our pinned 4.8.8.
- **Component analysis:** `camel-spiffe` is **not** in `used_components`.
- **Severity:** MEDIUM *(estimated)* — a real audience-validation gap if it existed in our deployment, but the component isn't deployed.
- **Verdict: NOT RELEVANT** (component not used; also doesn't exist in our pinned version).
- Sources: [Jira CAMEL-24734](https://issues.apache.org/jira/browse/CAMEL-24734), [commit d887f25e2](https://github.com/apache/camel/commit/d887f25e22a8b0dccd2288e75daa3206eec8d4d7).

### CAMEL-24754 — camel-opa: a verdict claimed by an inbound message survives a failed evaluation
- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA assigned; this is the most severe-looking finding of the run. Caught by manual review (not by the standard keyword grep — "verdict"/"survives" aren't in the keyword set).
- **Detail:** The commit message is explicit: *"Clear the OPA verdict exchange property on entry so a verdict claimed by an inbound message cannot survive into the decision, and do not overwrite it on the throw paths."* Read plainly: if an inbound message could set/claim an OPA "allow" verdict on the exchange, and a later OPA evaluation for that same exchange then failed (threw), the previously-claimed verdict was not cleared — so the failure path could inherit an attacker-influenced "allow" instead of failing closed. This is authorization-bypass-shaped (CWE-290-adjacent: improper handling of a claimed/spoofed authorization result across an error path).
- **Affected range vs. our version:** N/A — `camel-opa` is new in the unreleased 4.23 line; does not exist in our pinned 4.8.8.
- **Component analysis:** `camel-opa` is **not** in `used_components`.
- **Severity:** HIGH *(estimated)* — would be a meaningful authorization bypass if this component were deployed; irrelevant to us since it isn't.
- **Verdict: NOT RELEVANT** (component not used; also doesn't exist in our pinned version).
- Sources: [Jira CAMEL-24754](https://issues.apache.org/jira/browse/CAMEL-24754), [commit 0ec549de9](https://github.com/apache/camel/commit/0ec549de9ab5faebdc6e78d3407eb9f357504318).
- No backport assessment performed (component not used, and does not exist in 4.8.8).

### CAMEL-24736, CAMEL-24737, CAMEL-24741 — camel-opa: readiness check, nested-verdict lookup, WASM evaluation mode
- **Is this a vulnerability?** `NOT-SECURITY` for all three — caught while triaging the `camel-opa` cluster (`CAMEL-24736` matched the keyword grep via "OpaSecurityPolicy"). On inspection:
  - `CAMEL-24736` adds a missing health-check probe for `OpaSecurityPolicy` (observability gap, not a vulnerability).
  - `CAMEL-24737` lets `allowKey` read a dotted path into a nested decision document, and raises an unreadable-decision log from DEBUG to WARN (usability/diagnostics fix — arguably reduces the risk of a silent misconfiguration going unnoticed, but is not itself a fix for an exploitable bug).
  - `CAMEL-24741` adds an optional in-process WASM evaluation mode alongside the existing REST client (new feature; the commit message notes both engines are made to fail closed identically, but this is new-feature design, not a fix to an existing flaw).
- **Component analysis:** `camel-opa` is **not** a `used_component` in any case.
- **Verdict: NOT RELEVANT** (not security findings; component not used regardless).
- Sources: [Jira CAMEL-24736](https://issues.apache.org/jira/browse/CAMEL-24736) / [commit 5220998ad](https://github.com/apache/camel/commit/5220998ad5750c2bd25900033106427d403184a8); [Jira CAMEL-24737](https://issues.apache.org/jira/browse/CAMEL-24737) / [commit 3a418da50](https://github.com/apache/camel/commit/3a418da50b27ff33760cc01927ab42017128088f); [Jira CAMEL-24741](https://issues.apache.org/jira/browse/CAMEL-24741) / [commit e373fa6c0](https://github.com/apache/camel/commit/e373fa6c035d38b4c48a6767b50b42372ec7707d).

### CAMEL-24748 — catalog metadata: operation lists match what producers actually handle
- **Is this a vulnerability?** `NOT-SECURITY` — caught because it touches `camel-azure-storage-blob` (a `used_component`) across three separate commits landing under this ticket in the window. Read the actual diff to `BlobConfiguration.java` rather than trusting the filename alone: the change removes a **stale hardcoded `enums=` catalog annotation** on the `operation` field (three operations — `listBlobVersions`, `setBlobLegalHold`, `setBlobImmutabilityPolicy` — were missing from the hardcoded list) so the JSON catalog/documentation is derived from the real `BlobOperationsDefinition` enum instead. No change to `BlobOperationsDefinition` itself, no change to runtime validation or request handling — this is catalog/documentation accuracy only (affects IDE completion and generated docs, not what operations are actually accepted at runtime). The companion commits in the same ticket touch `camel-git`, `jt400`, `xmpp`, `huggingface`, `salesforce`, `netty`/`netty-http`, `azure-storage-datalake`, `google-secret-manager`, `google-storage`, `web3j`, `grpc` — same pattern (catalog/schema metadata corrections), none of them `used_components` except the already-assessed blob case.
- **Affected range vs. our version:** N/A — no runtime behavior changed.
- **Component analysis:** `camel-azure-storage-blob` **is** a `used_component`, but the change is metadata-only (verified via direct diff read, per the hard rule against fabricating findings).
- **Verdict: NOT RELEVANT** (not a security fix; confirmed no behavioral change to a used component).
- Sources: [Jira CAMEL-24748](https://issues.apache.org/jira/browse/CAMEL-24748), [commit 5b141927e](https://github.com/apache/camel/commit/5b141927e1cba02f4dfccdf35084f22e8d41c137) (the `camel-azure-storage-blob`/`camel-git` commit; two sibling commits — [28d74a543](https://github.com/apache/camel/commit/28d74a543de3a3009f69668305029b872cb8ac19), [3a3f17ebc](https://github.com/apache/camel/commit/3a3f17ebc0ca9aad28bead0df35951379c783a20) — cover the other, non-used components under the same ticket).
