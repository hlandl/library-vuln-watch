## Findings

### CAMEL-24973 — camel-support/camel-util: sensitive values leaked in "Unknown parameters" exception messages

- **Is this a vulnerability?** `SUSPECTED` — a silent security-hardening fix found via the GitHub repo sweep (no CVE/GHSA assigned as of this run; the fix landed on `main` 2026-09-25T09:19:50Z, only hours before this run). Three call sites built an error message by directly string-concatenating the raw endpoint-options `Map` — `"Unknown parameters=[" + param + "]"` — with **zero masking**: `org.apache.camel.support.DefaultComponent` (endpoint construction), `org.apache.camel.support.ScheduledPollConsumer` (scheduler options), and `camel-jetty`'s `JettyHttpComponent12` (not a used_component). Any option name Camel doesn't recognise — a typo, wrong case, or a dash-case variant it fails to match — that also carries a secret value (`password`, `privateKeyPassphrase`, `accessKey`, etc.) has that value written straight into a thrown `ResolveEndpointFailedException`/`IllegalArgumentException` message: **CWE-532, insertion of sensitive information into a log file or exception trace**.
- **Does the affected version range include our pinned version?** `AFFECTED` — no public range is published (no CVE yet), but I fetched both used-component files at the `camel-4.8.8` tag directly and confirmed the pinned code is byte-for-byte the pre-fix pattern:
  - `core/camel-support/src/main/java/org/apache/camel/support/DefaultComponent.java:305` (4.8.8): `+ " Unknown parameters=[" + param + "]");` — identical to the vulnerable line the fix replaces.
  - `core/camel-support/src/main/java/org/apache/camel/support/ScheduledPollConsumer.java:660` (4.8.8): `+ " Unknown parameters=[" + copy + "]");` — identical.
  - 4.8.8's `URISupport` has **no** `sanitizeParameters(Map)` method at all (it's newly introduced by this fix) and its existing string-based sanitizer (`sanitizeUri`'s `ALL_SECRETS` regex) could not have masked this leak regardless: that regex requires a `?`/`&`-prefixed query-string key (`[?&][^=]*(...)[^=]*=value`), and a bare `Map.toString()` such as `{foo=bar, privateKeyPassphrase=secret}` has neither character, so it would never match.
- **Is an affected artifact in `used_components`?** `USED` — both `camel-support` (`DefaultComponent`, `ScheduledPollConsumer`) and `camel-util` (`URISupport`, `SensitiveUtils`, where the underlying masking logic lives) are explicitly listed in `config/libraries.yaml`. (`camel-base-engine`, also touched by this commit for an unrelated call-site, is likewise a used_component; `camel-jetty` is not.)
- **Severity:** No CVSS published. Estimated **MEDIUM** *(estimated)* — exploitability requires (a) an endpoint URI or scheduler config with a misspelled/unrecognised parameter name that (b) also carries a genuinely sensitive value, and (c) the resulting exception message to reach somewhere an attacker or unauthorized party can read it (application logs, a monitoring system, or — worse — an error response surfaced to a caller). No special privilege is needed to trigger the leak itself; whoever controls the endpoint URI (which may itself be attacker-influenced via property placeholders, or simply a misconfiguration) controls whether it fires.
- **Verdict: AFFECTS US.**
- **Sources:**
  - Fix commit: https://github.com/apache/camel/commit/84f265e8d1b3548fd03f0fd0474cf6c410e5e9e6
  - Fix PR: https://github.com/apache/camel/pull/26803 (merged 2026-09-25)
  - Backport (upstream, to their 4.22.x LTS line): https://github.com/apache/camel/pull/26895
  - Jira: https://issues.apache.org/jira/browse/CAMEL-24973 (not reachable this run — Jira REST/web both blocked, see Source health; ticket key taken from the commit message)
  - No CVE/GHSA record found for this ticket as of this run (checked via WebSearch).
- **Official fix + backport assessment:**
  - Changed files (mainline PR #26803): `components/camel-jetty/.../JettyHttpComponent12.java`, `core/camel-base-engine/.../DefaultCamelContextExtension.java`, `core/camel-support/.../DefaultComponent.java`, `core/camel-support/.../ScheduledPollConsumer.java`, `core/camel-util/.../SensitiveUtils.java` (~137 lines changed — new `maskUserInfo`/`maskPathUserInfo`/`passwordRange` engine), `core/camel-util/.../URISupport.java` (~152 lines changed — new `sanitizeParameters`, `isSensitiveKey`, `MASK`, rewritten `RAW(...)`/`RAW{...}` handling), plus new tests.
  - **Does NOT apply cleanly to 4.8.8.** The fix is bundled with a much larger refactor of `URISupport`/`SensitiveUtils` (a unified userinfo-masking engine, dash-insensitive key matching, `RAW(...)` boundary alignment) that 4.8.8's simpler regex-based `sanitizeUri`/`SensitiveUtils` implementation doesn't have the scaffolding for (`isSensitiveKey`, `MASK`, and `sanitizeParameters` do not exist in 4.8.8 at all). Porting the upstream commit verbatim would mean pulling in the whole refactor, which is a much bigger, riskier change than the leak itself warrants.
  - **Recommended minimal backport:** write a small standalone `sanitizeParameters(Map<String,Object>)` helper in our fork that reuses 4.8.8's **existing** `SensitiveUtils.getSensitivePattern()` (already present, used to build the `ALL_SECRETS` regex) to decide which keys to mask, and call it at the two used-component sites: `DefaultComponent.java:305` and `ScheduledPollConsumer.java:660`. This is a ~10-line, self-contained change with no dependency on the rest of the upstream rewrite.
  - **Tests to port:** `DefaultComponentTest.testUnknownParametersAreSanitized` (asserts the message contains the masked key and does not contain the raw secret) — directly portable once the helper exists; no fixture changes needed. The `ScheduledPollConsumer` side has no dedicated upstream test yet (not added in this PR) — worth adding one for the backport.
  - No backport to any Camel release branch older than 4.22.x exists upstream (4.8.8 is well past Camel's own support window).
