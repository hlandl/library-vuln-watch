## Findings

### CAMEL-23747 — camel-mail: unguarded header override of recipients/from/subject/reply-to

- **Is this a vulnerability?** SUSPECTED — Apache Camel's own PR description frames this explicitly as a
  security hardening ("New defaults err toward denied unless opted in", "prevents untrusted Exchange
  headers from overriding configured mail settings"), and it enables a concrete attack (email
  redirection / sender spoofing / reply interception / subject injection when untrusted headers reach
  a `smtp:`/`smtps:` producer). However, **no CVE or GHSA identifier has been published** for it (as
  opposed to its sibling ticket CAMEL-23522 / CVE-2026-46584, which covers a *different* code path —
  see "Relationship to existing findings" below) — so per this repo's rubric it stays `SUSPECTED`
  rather than `CONFIRMED`.
- **Does the affected version range include our pinned version?** `AFFECTED` — confirmed by direct
  source comparison (not just the advisory text):
  - **Pinned `camel-4.8.8`** (`MailBinding.java`): `populateMailMessage()` calls
    `setRecipientFromCamelMessage(...)` whenever `hasRecipientHeaders(exchange)` is true, with **no
    configuration guard at all** — there is no `useHeaderRecipients`/`useHeaderFrom`/`useHeaderSubject`/
    `useHeaderReplyTo` field anywhere in `MailConfiguration.java` at this tag (confirmed absent). The
    same applies to `appendHeadersFromCamelMessage()`'s handling of `subject`/`from`/`sender`/`Reply-To`
    headers — all applied unconditionally.
  - **Fixed `camel-4.21.0`** (`MailBinding.java`/`MailConfiguration.java`): the identical call sites are
    now each gated (`if (endpoint.getConfiguration().isUseHeaderRecipients() && hasRecipientHeaders(...))`,
    `if (configuration.isUseHeaderSubject()) { ... }`, etc.), with all four flags defaulting to `false`.
  - There is **no version at which this is *not* exploitable** before the fix — it is not a "range"
    issue like most tracked CVEs, it is "everything before 4.21.0, unconditionally".
- **Is an affected artifact in `used_components`?** `USED` — `camel-mail` is in
  `config/libraries.yaml`'s `used_components` list.
- **Severity:** No CVSS published. Estimated **HIGH** *(estimated)* — an attacker who can influence any
  inbound Camel message header reaching a route that ends in a mail producer (e.g. a header bridged in
  from an HTTP consumer, JMS, or Kafka, exactly the precondition already established for the sibling
  finding CVE-2026-46584) can fully redirect outbound mail to an address of their choosing, spoof the
  From/Sender address, rewrite the Subject, and redirect replies to an address they control — a
  complete compromise of the integrity of any outbound email the route sends. This is comparable to or
  worse than sibling header-override findings already tracked at HIGH (e.g. CVE-2026-46587
  camel-couchbase, CVE-2026-46585 camel-lucene), which involved a single overridable field rather than
  four.
- **Relationship to existing findings:** **Not a duplicate of CVE-2026-46584 / CAMEL-23522** (already
  tracked `AFFECTS_US`). That finding is about `MailProducer.getSender()` applying attacker-controlled
  `mail.smtp.*`/`mail.smtps.*` *JavaMail session properties* from headers (can redirect the SMTP
  *connection* and leak credentials). This finding (CAMEL-23747) is about `MailBinding` applying
  attacker-controlled values to the *message content* (recipients/from/subject/reply-to) — a distinct
  code path, distinct impact, distinct fix commit, confirmed by diffing both files independently. The
  originating PR (#24194) does link back to CAMEL-23522 as related prior art, which is why both surfaced
  from the same investigation thread, but they are separate vulnerabilities requiring separate backports.
- **Sources:**
  - Fix PR: https://github.com/apache/camel/pull/24194 (merged 2026-06-23, commit `e027f18`, base `main`)
  - Follow-up doc-fix PR (where this was rediscovered this run): https://github.com/apache/camel/pull/26628
    ("CAMEL-24848: Fix mail useHeader* option defaults" — corrects Javadoc/generated docs that wrongly
    said the new flags default to `true`; also references CAMEL-23747 directly)
  - Backport-in-flight for the doc fix only: https://github.com/apache/camel/pull/26676 (`camel-4.22.x`,
    still open) — note this backports the *documentation* correction, not the original 4.21.0 code fix,
    to the 4.22.x line (which already carries the code fix by inheritance from `main`).
  - Pinned-version source checked directly: `https://raw.githubusercontent.com/apache/camel/camel-4.8.8/components/camel-mail/src/main/java/org/apache/camel/component/mail/MailBinding.java` and `MailConfiguration.java`
  - Fixed-version source checked directly: `https://raw.githubusercontent.com/apache/camel/camel-4.21.0/components/camel-mail/src/main/java/org/apache/camel/component/mail/MailBinding.java`
  - No CVE/GHSA/NVD record found for this specific ticket as of this run.
- **Official fix:** PR #24194 (commit `e027f18`), first released in **4.21.0**. Adds four new
  `@UriParam(label = "producer")` boolean fields to `MailConfiguration`
  (`useHeaderRecipients`, `useHeaderFrom`, `useHeaderSubject`, `useHeaderReplyTo`, all default `false`),
  and guards the four corresponding call sites in `MailBinding.populateMailMessage()` /
  `appendHeadersFromCamelMessage()` behind the matching flag (the `sender` header reuses the
  `useHeaderFrom` flag).
- **Backport assessment: LOW effort, clean.** `MailBinding.java`'s method names and structure
  (`populateMailMessage`, `hasRecipientHeaders`/`isRecipientHeader`, `setRecipientFromCamelMessage`,
  `setRecipientFromEndpointConfiguration`, `appendHeadersFromCamelMessage`) are already present in
  4.8.8 essentially unchanged from 4.21.0 at these call sites — no renames or refactors observed at the
  relevant lines. Recommend porting: (1) the four new `MailConfiguration` fields + getters/setters
  (default `false`); (2) the four guard conditions at the identified call sites; (3) the endpoint-option
  tests that PR #24194 added (17 test files were touched upstream — a good coverage list to mine for
  the equivalent 4.8.8 test classes). No functional drift expected; recommend a human confirm no other
  in-house code path also calls the now-still-public unconditional helpers directly.

### CAMEL-24800 — camel-core: pooled-exchange clock-sharing causes cross-message property/variable leak (splitter, pooling mode only)

- **Is this a vulnerability?** `SUSPECTED` — not badged as a CVE or as "security" by upstream (PR labels
  it a correctness/data-isolation bug), but a bug that lets one message's exchange properties and
  exchange-scoped variables become visible on a *different* message's exchange has a real confidentiality
  angle if that data is sensitive (auth tokens, PII, tenant identifiers passed via properties/variables
  in a `split()`), so it is tracked here rather than dropped as `NOT-SECURITY`.
- **Does the affected version range include our pinned version?** `AFFECTED` — per the fix PR, the bug
  ("present since 4.4, CAMEL-20225") is a `DefaultPooledExchange(Exchange parent)` constructor defect
  that has existed unchanged since long before our 4.8.8 pin.
- **Is an affected artifact in `used_components`?** `UNCLEAR` — `camel-core` (and `camel-core-engine`)
  are in `used_components`, but the bug is **only reachable when Camel's exchange-pooling mode is
  explicitly enabled** (`PooledExchangeFactory` / pooled exchange configuration is opt-in, not the
  default `Exchange` implementation). This repository's config does not record whether our deployment
  enables exchange pooling — a human needs to check the running `CamelContext`'s exchange-factory
  configuration to resolve this to `USED`/`NOT-USED`.
- **Severity:** No CVSS. Estimated **MODERATE** *(estimated)*, conditional on pooling being enabled and
  on sensitive data being carried in split-child exchange properties/variables; **not exploitable at
  all** if pooling is off (the default).
- **Sources:**
  - Fix PR: https://github.com/apache/camel/pull/26553 ("CAMEL-24800: camel-core - pooled exchange
    copies must own their clock", merged 2026-09-17 to `main`)
  - Root-cause ticket referenced: CAMEL-20225 (introduced the shared-clock pattern in 4.4)
- **Official fix:** `DefaultPooledExchange(Exchange parent)` now creates its own `ResetableClock`
  instance instead of reusing the parent's, so releasing the parent back to the pool no longer corrupts
  a still-in-use child's `done()`/reset guard. **Not yet in any tagged release** as of this run (`main`
  only); no backport PR opened yet despite the author noting one "is worth considering."
- **Backport assessment: not yet applicable** — wait for either a tagged release or an LTS backport PR
  to confirm the fix is stable, then assess `DefaultPooledExchange` for drift against 4.8.8 (flagged for
  next run; recommend a human separately confirm whether our deployment enables exchange pooling, which
  would upgrade this to `AFFECTS_US` and justify an immediate in-house port ahead of upstream's own
  backport).
