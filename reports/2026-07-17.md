## Findings

### CAMEL-24098 — camel-ftp: SFTP cipher/KEX settings leak across endpoints via global JSch state
- **Is this a vulnerability?** SUSPECTED — a real, verified security-configuration-isolation
  bug; no CVE/GHSA has been published for it as of this run.
- **Description:** `SftpOperations.createSession()` configured the `ciphers` and
  `keyExchangeProtocols` endpoint options via the static `JSch.setConfig(...)` method, which
  is process-wide/JVM-global state in the JSch library, rather than the per-connection
  `Session.setConfig(...)`. In an application running multiple SFTP endpoints concurrently
  with different cipher/KEX requirements (e.g. one endpoint hardened to a restricted cipher
  suite for a compliance-sensitive partner, another left more permissive for a legacy one),
  whichever endpoint's session is created last silently overwrites the allowed
  ciphers/key-exchange algorithms for **every** SFTP session in the JVM — including ones
  already configured more strictly — with no error or warning. This is a configuration
  integrity/isolation problem with direct cryptographic consequences (can silently downgrade
  the effective cipher/KEX set used by unrelated endpoints).
- **Affected range vs. our version:** **AFFECTED — confirmed directly against our pinned
  source.** Fetched `SftpOperations.java` at the `camel-4.8.8` tag; `createSession()` there
  contains exactly the vulnerable pattern:
  ```java
  if (isNotEmpty(sftpConfig.getCiphers())) {
      Hashtable<String, String> ciphers = new Hashtable<>();
      ciphers.put("cipher.s2c", sftpConfig.getCiphers());
      ciphers.put("cipher.c2s", sftpConfig.getCiphers());
      JSch.setConfig(ciphers);
  }
  if (isNotEmpty(sftpConfig.getKeyExchangeProtocols())) {
      JSch.setConfig("kex", sftpConfig.getKeyExchangeProtocols());
  }
  ```
  called before the `Session` object even exists (setConfig calls happen right after `new
  JSch()`, ahead of `jsch.getSession(...)`).
- **Component in use?** `camel-ftp` is in `used_components` → **USED**.
- **Verdict: AFFECTS US.**
- **Severity:** Medium *(estimated — no CVSS published. Requires the application to run
  multiple concurrently-active SFTP endpoints with differing cipher/KEX policies in one JVM;
  impact is a silent downgrade of cryptographic transport parameters for unrelated
  connections, not a direct remote-exploit primitive by itself)*.
- **Sources:**
  - PR (fix): https://github.com/apache/camel/pull/24757
  - Commit: `87677c3` ("CAMEL-24098: camel-ftp - Use per-session config for SFTP ciphers and
    keyExchangeProtocols instead of mutating global JSch state")
  - Jira: CAMEL-24098 *(link only — `issues.apache.org` unreachable this run, not
    independently verified via Jira itself)*
  - Pinned-version source checked directly:
    https://github.com/apache/camel/blob/camel-4.8.8/components/camel-ftp/src/main/java/org/apache/camel/component/file/remote/SftpOperations.java
- **Official fix:** Replaces the two `JSch.setConfig(...)` (static) calls with
  `session.setConfig("cipher.s2c"/"cipher.c2s"/"kex", ...)` (per-session), executed after the
  `Session` object is obtained from `jsch.getSession(...)`. Adds a new integration test,
  `SftpCipherGlobalConfigIT`, asserting global JSch state is left untouched. No tagged Camel
  release contains this fix yet (merged to `main` 2026-07-16, targeted at the 4.22.0
  milestone); no backport PR to a maintenance branch exists as of this run.
- **Backport assessment:** Should apply with **moderate** effort, not a clean one-line patch.
  `createSession()` has the identical method name and the same `sftpConfig`/(soon-to-exist)
  `session` local variables in both the pinned 4.8.8 code and current `main`, so there is no
  structural drift to fight — but the fix also **reorders** the code: 4.8.8 calls
  `JSch.setConfig(...)` immediately after `new JSch()`, *before* the `Session` is created via
  `jsch.getSession(...)`; the fixed version moves this configuration to *after* session
  creation and switches the call target to `session.setConfig(...)`. A correct backport must
  move the cipher/KEX block down past the `jsch.getSession(...)` call, not just substitute the
  method call in place. Recommend porting `SftpCipherGlobalConfigIT` alongside.
