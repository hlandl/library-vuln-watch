## Findings

### CVE-2026-40453 — Incomplete fix for CVE-2025-27636: case-variant Camel header injection in non-HTTP `HeaderFilterStrategy`s
- **Verdict: AFFECTS US.** Severity: **CRITICAL** *(estimated — no official CVSS was retrievable from the sources reachable this run; classed RCE + arbitrary file write, CWE-20)*.
- **Vulnerability:** `CONFIRMED` (CVE assigned, Apache security advisory + oss-security disclosure exist).
- **Affected range vs. our version:** Advisory and an independent reproducer both give the range as `3.0.0` through `4.14.5`, `4.15.0` through `4.18.1`, `4.19.0` through `4.19.x`, fixed in `4.14.6` / `4.18.2` / `4.20.0`. Our pinned **4.8.8 falls inside the first (unfixed) segment → AFFECTED**.
- **Component analysis:** The five broken strategies are `JmsHeaderFilterStrategy`/`ClassicJmsHeaderFilterStrategy` (**camel-jms** — in `used_components`), `SjmsHeaderFilterStrategy` (camel-sjms — not used), `CoAPHeaderFilterStrategy` (camel-coap — not used), `GooglePubsubHeaderFilterStrategy` (camel-google-pubsub — not used). **camel-jms is in use** → `USED`. The injected headers are resolved by downstream header-driven components; both **camel-exec** and **camel-file**, which can turn header injection into command execution / arbitrary file write, are also in `used_components`, so the full exploit chain (JMS producer → forged `CAmelExecCommandExecutable`-style header → camel-exec/camel-file) is plausible in our deployment if any route forwards JMS message headers to those components.
- **Root cause:** `JmsHeaderFilterStrategy`/`ClassicJmsHeaderFilterStrategy` filter headers with a case-sensitive `startsWith("Camel"/"camel")` check but never call `setLowerCase(true)`, while the Camel `Exchange` header map is case-insensitive. An attacker with JMS producer access to the broker a Camel route consumes from can send a case-variant header (e.g. `CAmelExecCommandExecutable`) that slips past the filter but still resolves under its canonical name downstream.
- **Sources:**
  - Apache advisory: https://camel.apache.org/security/CVE-2026-40453.html
  - oss-security disclosure: https://seclists.org/oss-sec/2026/q2/224
  - Reproducer: https://github.com/oscerd/CVE-2026-40453
  - Jira: https://issues.apache.org/jira/browse/CAMEL-23313
- **Official fix + backport assessment:** Fix is `CAMEL-23313`, three one-line-per-class commits (main/`4.20.0`: `3d2efeed2f6ea757f0254a1d1cdeb9a4f28ca147`; `4.18.x`/`4.18.2`: `1e331daa4eea0a3f01d951e74cda8faee79495a2`; `4.14.x`/`4.14.6`: `301bb7401cd480895b94a28a8ad6cf04952d8125`). Each just adds `setLowerCase(true);` to the affected strategies' constructors. Verified against our pinned tag `camel-4.8.8`: `JmsHeaderFilterStrategy`/`ClassicJmsHeaderFilterStrategy` have the identical constructor shape at 4.8.8, and the base class `DefaultHeaderFilterStrategy.setLowerCase(...)` already exists and is already honored by the header-matching logic at that version — **the patch applies cleanly with no drift**. Recommend backporting the one-line change to `JmsHeaderFilterStrategy` and `ClassicJmsHeaderFilterStrategy` (camel-jms is our only in-use affected component); no test drift expected — the upstream unit tests for these two classes should port directly. Optionally also apply to camel-sjms/camel-coap/camel-google-pubsub if those are ever introduced later, though they are not currently in `used_components`.

### CAMEL-24298 — New opt-in `allowedSchemes` allow-list for the `toD`/`wireTap` dynamic-URI EIP
- **Verdict: NEEDS REVIEW.** Severity: **MEDIUM** *(estimated)* — this is a **defense-in-depth hardening feature**, not a fix for a disclosed CVE; flagged as `SUSPECTED` per the "silent fix" sweep.
- **Vulnerability:** `SUSPECTED` — no CVE/GHSA exists for this; it reads as upstream proactively hardening `toD`/`wireTap` against SSRF-style abuse when the dynamic URI is built from untrusted exchange data (adds `ToDynamicDefinition`/`SendDynamicProcessor` support for a configurable scheme allow-list).
- **Affected range vs. our version:** Unreleased — only on `main` as of 2026-08-05 (commit `0fe928c`), not yet in any tagged release. Our 4.8.8 obviously predates it and has **no equivalent control** — `UNCLEAR` whether this counts as "affects us" since it isn't a fix for an active bug, but the underlying gap (no scheme restriction on dynamic-URI EIPs) exists identically in our version.
- **Component analysis:** Lands in `camel-core` (`ToDynamicDefinition`, `SendDynamicProcessor`, `ToDynamicReifier`), which **is** in `used_components` → `USED`.
- **Sources:** commit https://github.com/apache/camel/commit/0fe928c5106277357dedc947335631b21372401c ; PR https://github.com/apache/camel/pull/25315 ; Jira https://issues.apache.org/jira/browse/CAMEL-24298
- **Official fix + backport assessment:** No backport needed in the "apply a patch" sense (nothing is broken); this is a hand-over for a human decision: if any of our routes build `toD`/`wireTap` target URIs from untrusted input (headers, message body, external config), consider whether adopting an equivalent allow-list makes sense as a proactive control. The upstream change touches `ToDynamicDefinition.java`, `SendDynamicProcessor.java`, `ToDynamicReifier.java`, plus DSL/schema/catalog metadata in the XML, YAML, and Java DSL layers — porting only the core Java logic (`ToDynamicDefinition` + `SendDynamicProcessor`) without the DSL/schema plumbing would be a much smaller, self-contained change if desired.
