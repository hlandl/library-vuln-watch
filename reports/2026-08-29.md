### CAMEL-24475 — camel-xpath: XXE when XPath document type is InputSource/SAXSource

- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA assigned yet (Jira ticket carries no security label at the time of this sweep), but this is a textbook CWE-611 (Improper Restriction of XML External Entity Reference): `XPathBuilder.evaluate*()` passed an `InputSource`/`SAXSource` document straight to `javax.xml.xpath.XPathExpression.evaluate(InputSource, ...)`, which builds its **own** `DocumentBuilder` internally using unmodified JDK defaults (DOCTYPE allowed, external general/parameter entities resolved) — while the default `documentType=Document` path already routed through Camel's hardened `DocumentBuilderFactory`. Upstream's own regression test (`docTypeIsAlsoDisallowedForAnInputSourceDocumentType`) demonstrates reading a local file (`file:///...`) via an XXE payload through this path before the fix.
- **Does the affected range include our pinned version?** `AFFECTED` — confirmed directly: pulled `components/camel-xpath/.../XPathBuilder.java` at git tag `camel-4.8.8` and it contains the identical unguarded `xpathExpression.evaluate(inputSource, ...)` / `evaluate(source.getInputSource(), ...)` calls at all three evaluation sites (NodeList, typed-result, and String-result overloads) that the fix changes.
- **Component in use?** `camel-xpath` is in `used_components` → **USED**.
- **Severity:** No CVSS published (no CVE yet). **Estimated HIGH** (CVSS-alike AV:N/AC:L/PR:N/UI:N/C:H/I:N/A:N ≈ 7.5) *when* a route uses `xpath(...)` (or the `XPathBuilder` API directly) with `documentType=InputSource` or `documentType=SAXSource` against attacker-influenced XML input — the default `documentType=Document` configuration was already safe. Exploitability therefore depends on route configuration; flagged HIGH here as a precaution pending an inventory of routes using non-default `documentType`.
- **Verdict: AFFECTS US.**
- Sources: [apache/camel@1ead256f1](https://github.com/apache/camel/commit/1ead256f1bfcef36c2572a88809bcd7547bdc111) (PR [#25683](https://github.com/apache/camel/pull/25683)), committed 2026-08-28T12:19:48+02:00 by Andrea Cosentino. Jira: `CAMEL-24475` (issues.apache.org unreachable this run, see Source health — URL by convention: `https://issues.apache.org/jira/browse/CAMEL-24475`).
- **Official fix:** Route all three `evaluate()` call sites for `InputSource`/`SAXSource` document types through a new `toHardenedDocument(Exchange, InputSource)` helper, which uses `exchange.getContext().getTypeConverter().convertTo(Document.class, exchange, inputSource)` — i.e. the same hardened `DocumentBuilderFactory` path (`FEATURE_SECURE_PROCESSING`, `disallow-doctype-decl=true`, `external-general-entities=false`) the default `Document` document type already uses. No new parse is added: the XPath engine was already building a full DOM internally either way. First fixed release: **not yet released** — present on `main` (targeting `4.23.0-SNAPSHOT`) only as of this sweep; no `camel-4.8.x` backport exists upstream.
  - Changed files: `components/camel-xpath/src/main/java/org/apache/camel/language/xpath/XPathBuilder.java`; test `core/camel-core/src/test/java/org/apache/camel/builder/xml/XPathFeatureTest.java`.
  - **Backport assessment:** Low risk / applies cleanly. `XPathBuilder.java` in 4.8.8 has the identical method bodies at the same call sites (no refactor/rename drift observed for this class between 4.8.8 and current `main`). The prerequisite the fix relies on — a hardened `DocumentBuilderFactory` already reachable via the `Document` type converter — is **already present** in 4.8.8's `core/camel-xml-jaxp/.../XmlConverter.java` (`disallow-doctype-decl`, `external-general-entities=false`, `FEATURE_SECURE_PROCESSING` all confirmed present at the pinned version). Port: the 3 call-site edits + the new `toHardenedDocument()` helper method, verbatim. Port test: `docTypeIsAlsoDisallowedForAnInputSourceDocumentType` (and its sibling `testXPathDocTypeDisallowed()` context) from `XPathFeatureTest.java` — check the 4.8.8 file for the same base test class/imports before porting (not verified further; test-only risk).

### CAMEL-24418 — HTTP producers resolve property placeholders in untrusted URI-override headers

- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA yet. CWE-917-adjacent (improper neutralization in expression-language-like resolution of externally-controlled input): a message header (`Exchange.HTTP_URI` / `CamelHttpUri`, and the equivalent REST header) is data that arrives with the exchange, not route-authoring text — the commit explicitly frames this as the same contract violation that `CAMEL-24282` fixed for `toD`/`enrich`. Resolving `{{...}}` placeholders in it means an upstream system (or a compromised prior processor) that controls this header can force resolution of arbitrary properties known to the `CamelContext` — including anything wired through the properties component (env vars, secrets refs, etc.) — and have the result folded into the outgoing request URI.
- **Does the affected range include our pinned version?** `AFFECTED` — confirmed: `components/camel-http-common/src/main/java/org/apache/camel/http/common/HttpHelper.java` at git tag `camel-4.8.8` contains both vulnerable call sites (`uri = exchange.getContext().resolvePropertyPlaceholders(uri)` in the URI-building method, and the equivalent for `uriString` built from the `HTTP_URI` header in the query-string method), byte-for-byte matching what the fix removes.
- **Component in use?** `camel-http-common` is in `used_components` → **USED**. (The other four modules the fix also touches — `camel-http`, `camel-netty-http`, `camel-undertow`, `camel-vertx-http` — are **not** in `used_components`; only the `camel-http-common` half of this fix is in scope for us.)
- **Severity:** No CVSS published. **Estimated MEDIUM** (information disclosure / config-injection primitive, gated behind an attacker's ability to set the `CamelHttpUri`/`HTTP_URI`/REST-URI header on an exchange before it reaches an HTTP producer — typically requires either a compromised upstream component or a route that copies untrusted input into that header).
- **Verdict: AFFECTS US.**
- Sources: [apache/camel@ba5aced7f](https://github.com/apache/camel/commit/ba5aced7f6a1c38a963020575676ad4c76b492cf) (closes [#25571](https://github.com/apache/camel/pull/25571)), committed 2026-08-28T10:51:45+02:00 by Andrea Cosentino. Jira: `CAMEL-24418` (`https://issues.apache.org/jira/browse/CAMEL-24418`, unreachable this run). Related prior fix referenced by the commit: `CAMEL-24282` (already in `state/seen.json`, verdict `NOT_RELEVANT` from the 2026-07-31 run — that ticket's `toD`/`enrich` scope did not touch a `used_components` module at the time; this new ticket does, via `camel-http-common`).
- **Official fix:** Stop calling `CamelContext.resolvePropertyPlaceholders()` on the header-sourced URI/query-string values in `HttpHelper` (and the sibling helpers in the other 4 modules); placeholders remain resolved only on the endpoint URI written in the route at build time. Adds `HttpUriHeaderPlaceholderTest`. First fixed release: **not yet released** — `main` only (`4.23.0-SNAPSHOT`); no `camel-4.8.x` backport upstream.
  - Changed files (in scope for us): `components/camel-http-common/src/main/java/org/apache/camel/http/common/HttpHelper.java` (2 call sites — both simple deletions of a `try { resolvePropertyPlaceholders(...) } catch {...}` block, replaced with a code comment).
  - **Backport assessment:** Low risk / applies cleanly. Both call sites in 4.8.8's `HttpHelper.java` are textually identical to the pre-fix `main` version (same surrounding code, same line numbers). Backport is a pure deletion — no logic to re-derive, no drift. No test to port from the `camel-http-common` side specifically (`HttpUriHeaderPlaceholderTest` lives in `camel-http`, not in scope, but the same test pattern could be adapted for `camel-http-common` if we want in-repo coverage).

### CAMEL-24553 — camel-api: TypeConversionException message-building can OOM on huge bodies

- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA. CWE-400 (Uncontrolled Resource Consumption): `TypeConversionException.createMessage()` unconditionally string-concatenates the failed conversion's source value (`... + value + ...`), which calls `toString()` on it. For a multi-GB message body that fails a type conversion (e.g. an oversized payload routed to a converter it cannot satisfy), this can materialize the entire body as a `String` merely to build an error message, risking `OutOfMemoryError`. Note the PR went through several review iterations (visible in the squashed commit body) and the final merged scope is **narrower** than the initial "OOM guard in `getMandatoryBody`" title suggests — the `camel-support`/`MessageSupport` guard was dropped per reviewer feedback; the merged fix is limited to `TypeConversionException` no longer calling `toString()` on the value.
- **Does the affected range include our pinned version?** `AFFECTED` — confirmed: `core/camel-api/src/main/java/org/apache/camel/TypeConversionException.java` at git tag `camel-4.8.8` has the identical `+ value +` concatenation in `createMessage()`.
- **Component in use?** `camel-api` is in `used_components` → **USED** (and `camel-core`, also used, is the primary caller of this exception class throughout the codebase).
- **Severity:** No CVSS published. **Estimated LOW/MEDIUM** — a DoS primitive, but narrow: requires an attacker-reachable route where a huge body both (a) reaches a type conversion that (b) fails, which is not the common case; most routes either succeed the conversion or fail on a small/already-materialized body.
- **Verdict: AFFECTS US.**
- Sources: [apache/camel@1012de47a](https://github.com/apache/camel/commit/1012de47aabf76f9bdfc161b7a68b5ee42142513) (PR [#25871](https://github.com/apache/camel/pull/25871)), committed 2026-08-28T21:49:24+05:30 by mayurbm. Jira: `CAMEL-24553` (`https://issues.apache.org/jira/browse/CAMEL-24553`, unreachable this run).
- **Official fix:** `TypeConversionException.createMessage()` no longer includes the failed value in the exception message text (the value stays available via `getValue()`). First fixed release: **not yet released** — `main` only (`4.23.0-SNAPSHOT`); no `camel-4.8.x` backport upstream.
  - Changed files (final merged scope): `core/camel-api/src/main/java/org/apache/camel/TypeConversionException.java`; tests `TypeConversionExceptionMessageTest.java`, `DefaultComponentTest.java` (message-format assertion update).
  - **Backport assessment:** Trivial / applies cleanly. One-line change (drop `" with value " + value` from the concatenation) in a small, stable file with no evidence of drift between 4.8.8 and `main`. Port `createMessage_doesNotCallToStringOnValue` from `TypeConversionExceptionMessageTest.java` as a regression test; check whether any code in 4.8.8 depends on the old "with value ..." message text before removing it (the upstream PR needed to update `DefaultComponentTest`'s assertion for exactly this reason).

### CAMEL-24477 — camel-cxf-soap: SOAP faults leak internal exception details for undeclared failures

- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA; this is a hardening-default gap rather than a newly introduced bug. CWE-209 (Generation of Error Message Containing Sensitive Information): `CxfConsumer` built the SOAP fault's `faultstring` directly from `Exchange.getException()`'s message (or its class name when absent), for *any* undeclared exception — the same class of issue `CAMEL-23651` addressed for the HTTP consumers (`camel-servlet`, `camel-jetty`, `camel-undertow`, `camel-netty-http`, `camel-platform-http`) by adding a `muteException` option defaulting to `true`. `camel-cxf` had no equivalent option at all until this ticket.
- **Does the affected range include our pinned version?** `AFFECTED` — confirmed: `components/camel-cxf/camel-cxf-soap/.../CxfConsumer.java` at git tag `camel-4.8.8` has no `muteException` reference anywhere — the mitigation is entirely absent, not merely defaulted off.
- **Component in use?** `camel-cxf-soap` is in `used_components` → **USED**. (`CxfConsumer` lives in `camel-cxf-soap`, confirmed by file path — not the umbrella `camel-cxf` artifact, which does not exist as a separate published module.)
- **Severity:** No CVSS published. **Estimated LOW** — requires an *undeclared* failure (not a CXF `Fault`, a `@WebFault`-annotated exception, or a `<soap:Fault>` body — those remain returned in full even after the fix, since "for a SOAP service some faults are the contract") to reach the consumer; impact is disclosure of an internal exception message/class name (and, per the commit, a `continuationTimeout` expiry message) to the SOAP caller, not code execution or data access.
- **Verdict: AFFECTS US** (present in a used component; severity is low and this is closer to "missing hardening default" than an actively exploited bug — reasonable to schedule opportunistically rather than urgently).
- Sources: [apache/camel@fd4fd273e](https://github.com/apache/camel/commit/fd4fd273e4d1d36c1341cc8cf08405decd8c755c) (PR [#25742](https://github.com/apache/camel/pull/25742)), committed 2026-08-28T12:12:18+02:00 by Andrea Cosentino. Jira: `CAMEL-24477` (`https://issues.apache.org/jira/browse/CAMEL-24477`, unreachable this run). Prior related fix: `CAMEL-23651` (introduced `muteException` for the HTTP consumers; not present in `state/seen.json`, predates this watch).
- **Official fix:** Add a `muteException` `@UriParam` (`label="consumer"`, **default `true`**) to `CxfEndpoint`/`CxfConsumer`. `checkFailure()` is reworked to separate the "exception path" (muted when undeclared) from the "body path" (a `Throwable`/`<soap:Fault>` `CxfPayload` set as the message body, always returned in full); the stand-in fault has its stack trace cleared. First fixed release: **not yet released** — `main` only (`4.23.0-SNAPSHOT`); no `camel-4.8.x` backport upstream.
  - Changed files: `CxfConsumer.java`, `CxfEndpoint.java`, `CxfEndpointConfigurer.java`, `CxfEndpointUriFactory.java`, generated `cxf.json` catalogs (×2), generated `CxfEndpointBuilderFactory.java` (DSL), plus `CxfConsumerContinuationTimeoutTest.java` (updated) and new `CxfConsumerMuteExceptionTest.java`.
  - **Backport assessment:** **Moderate risk — do not treat as a drop-in patch.** Unlike the three findings above, this is a genuine feature addition with a public-API surface change (new endpoint option, retired `extractThrowable()`, regenerated catalog/DSL artifacts) rather than a pure bug fix, and 4.8.8's `CxfConsumer.java`/`CxfEndpoint.java` have not been diffed line-by-line against `main` for structural drift across the ~14 releases in between. Recommend a human review of: (a) whether `CxfEndpointConfigurer`/`CxfEndpointUriFactory`/the generated catalog and DSL builder in 4.8.8 have compatible shapes to extend, (b) whether defaulting `muteException=true` on an already-GA 4.8.x line is an acceptable behavior change for our deployment (callers currently receiving detailed SOAP faults would stop doing so), versus backporting with the option defaulted `false` (safer default-preserving posture, opt-in hardening) instead of matching upstream's `true` default. Port `CxfConsumerMuteExceptionTest.java` once the option is wired in.
