### CVE-2026-66906 — confirmed AFFECTS US, with a full backport plan (camel-azure-storage-blob)

- **Verdict: AFFECTS US (confirmed).** Severity: **HIGH** *(estimated — CWE-22 path traversal / arbitrary file write via attacker-influenced blob name or a compromised/misconfigured storage account; no local RCE primitive identified, but unconstrained local file overwrite from a remote-controlled name is a serious integrity/availability issue)*.
- **Official fix:** [`CAMEL-23942`](https://github.com/apache/camel/commit/55fcbaf8bc1936cae90abdea5adecbc43e57340e) ("contain Azure Storage Blob/DataLake fileDir downloads within the configured directory", PR #24542, 2026-07-08), first released in **Camel 4.22.0**. Adds `AzureFileNameHelper.resolveWithinDirectory()`: normalizes the configured `fileDir` and the target path and requires `normalizedTarget.startsWith(normalizedDir)`, else throws `IllegalArgumentException`.
- **Further hardening (unreleased):** [`CAMEL-24548`](https://github.com/apache/camel/commit/299fd780945c0bc2b0f38eced56e16a91f0d5f86) ("Harden cloud storage download containment", landed 2026-09-01 on `main`, **not yet in any tagged release**) closes a symlink bypass in the `CAMEL-23942` check: the original check only normalized the *lexical* path, so a symlink placed inside `fileDir` that resolves outside it could still smuggle a write outside the directory. The new `resolveExistingPathSegments()` walks up to the nearest existing ancestor, calls `toRealPath()` to resolve any symlinks, and re-checks containment against the resolved path.
- **Affected range vs. our version:** the public advisory (per the mail-archive announcement) states the affected range as **4.19.0 before 4.22.0** — which on its face excludes our pinned **4.8.8**. However, direct inspection of the `camel-4.8.8` tag shows `BlobOperations.downloadBlobToFile()` builds the download target as `new File(fileDir, client.getBlobName())` **with no containment check of any kind** — not even the basic lexical `startsWith` check that `CAMEL-23942` introduced in 4.22.0. This is the *same vulnerable pattern* the advisory describes, just further back in history than GHSA/NVD's range analysis reached (their tooling likely stopped at the 4.19.0 branch point rather than checking all the way back to 4.8.8). **Verdict: AFFECTED**, based on our own source read, independent of and more conservative than the published range.
- **Component analysis:** `camel-azure-storage-blob` **is** in `used_components` → **USED**. (`camel-azure-storage-datalake` and `camel-google-storage`, also touched by the same upstream commits, are not — see the correction table above.)
- **Backport assessment:** `CAMEL-23942`'s change is small and self-contained (new `AzureFileNameHelper` class + a two-line call-site change in `BlobOperations.downloadBlobToFile()` / `DataLakeFileOperations`'s equivalent). Our pinned 4.8.8 `BlobOperations.java` has no equivalent helper class at all and no `import` conflicts — **the patch does not apply as a diff (4.8.8 predates the refactor that introduced the check-call-site shape used by the 4.22.0 patch) but the fix is trivial to port by hand**: add an `AzureFileNameHelper`-equivalent utility and call it immediately before `client.downloadToFileWithResponse(fileToDownload.toString(), ...)` in `BlobOperations.downloadBlobToFile()`, using `fileDir` and `client.getBlobName()` as inputs, throwing `IllegalArgumentException` on a containment failure. Recommend porting the **`CAMEL-24548`** symlink-aware version directly (skip the intermediate `CAMEL-23942`-only lexical check) since it is barely larger and closes a bypass the lexical-only check doesn't. Port `AzureFileNameHelperTest`'s coverage (basic traversal + the two new symlink tests) alongside; note the test suite depends on `@TempDir`-based `Files.createSymbolicLink`, which should work unmodified against 4.8.8's JUnit5 test infra.
- **Sources:** [CVE-2026-66906 announcement](http://www.mail-archive.com/announce@apache.org/msg11770.html) · [CAMEL-24548 Jira resolved notice](http://www.mail-archive.com/issues@camel.apache.org/msg131323.html) · fix commit [`55fcbaf8bc`](https://github.com/apache/camel/commit/55fcbaf8bc1936cae90abdea5adecbc43e57340e) (`CAMEL-23942`, 4.22.0) · hardening commit [`299fd7809`](https://github.com/apache/camel/commit/299fd780945c0bc2b0f38eced56e16a91f0d5f86) (`CAMEL-24548`/`CAMEL-24549`, unreleased) · confirmed against `camel-4.8.8` tag, `components/camel-azure/camel-azure-storage-blob/src/main/java/org/apache/camel/component/azure/storage/blob/operations/BlobOperations.java`.
