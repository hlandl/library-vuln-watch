## Findings

### CAMEL-24725 — apply the shared deserialization filter in KeyValueRepositoryHelper
- **Is this a vulnerability?** `SUSPECTED` — a hardening fix (adds JEP-290 `ObjectInputFilter` coverage) with no CVE/GHSA assigned, caught via the GitHub repository sweep.
- **Detail:** `KeyValueRepositoryHelper` (itself new in the unreleased 4.23, `CAMEL-24463`) deserialized stored values with a plain `ObjectInputStream` and no `ObjectInputFilter`, unlike every other deserialization call site in Camel. Fixed by routing all `deserialize(...)` overloads through the shared `DeserializationFilterHelper`, and exposing a `deserializationFilter` option on the affected persistent backends (`camel-cassandraql`, `camel-hazelcast`, `camel-infinispan`, `camel-jpa`, `camel-kafka`, `camel-redis`, `camel-sql`) plus the helper itself in `core/camel-support`.
- **Affected range vs. our version:** N/A — `KeyValueRepositoryHelper` and its per-backend `*KeyValueRepository` classes do not exist in our pinned 4.8.8 (confirmed via the commit's own note: "main only: the helper has not shipped in a release"; the feature was introduced by `CAMEL-24463`, also unreleased).
- **Component analysis:** `core/camel-support` and `components/camel-kafka` (2 of the 7 touched backends) **are** `used_components`, but the specific classes this fix touches (`KeyValueRepositoryHelper`, `KafkaKeyValueRepository`) are new code that ships only in the not-yet-released 4.23 line — they are not present in our 4.8.8 jars. The other 5 touched backends (`camel-cassandraql`, `camel-hazelcast`, `camel-infinispan`, `camel-jpa`, `camel-redis`, `camel-sql`) are not `used_components` either way.
- **Severity:** LOW *(estimated)* — no CVE, and the vulnerable code doesn't exist in our runtime.
- **Verdict: NOT RELEVANT** (feature not present in pinned version).
- Sources: [Jira CAMEL-24725](https://issues.apache.org/jira/browse/CAMEL-24725) (not independently fetched — Jira REST blocked, see Source health), [commit 998a60666f](https://github.com/apache/camel/commit/998a60666f72e53d62b51c5cab249f3be00ed860).
- No backport assessment performed (NOT RELEVANT; also nothing to backport onto — the target code doesn't exist in 4.8.8).

### CAMEL-24730 — camel-spiffe: inbound headers could override the validated audience/operation
- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA assigned yet, caught via the GitHub repository sweep (commit message reads as a genuine authentication-bypass fix, not just hardening).
- **Detail:** `SpiffeProducer` read both the operation and the audience from message headers in preference to the endpoint configuration. For `validateJwtSvid`, the audience *is* the check — so a header-controlled audience let a token minted for another service validate successfully, and a header-controlled operation could turn a validator endpoint into a minter that returned the workload's own JWT-SVID. Fixed by making `validateJwtSvid` use only the configured audience, and gating the operation-from-header behavior behind a new `allowOperationHeader` option (default `false`, marked `security = "insecure:dev"`).
- **Affected range vs. our version:** N/A — `camel-spiffe` is new in the unreleased 4.23.0 (per the commit message) and does not exist in our pinned 4.8.8 component set.
- **Component analysis:** `camel-spiffe` is **not** in `used_components`, and doesn't exist in our version regardless.
- **Severity:** HIGH *(estimated)* — would be an authentication bypass if it existed in our deployment, but it doesn't.
- **Verdict: NOT RELEVANT** (component not used; also does not exist in our pinned version).
- Sources: [Jira CAMEL-24730](https://issues.apache.org/jira/browse/CAMEL-24730), [commit 1d2cba763](https://github.com/apache/camel/commit/1d2cba7637072aece5aca8f83a6cdb904e08e1e8).

### CAMEL-24292 — camel-sql, camel-sql-stored: gate query/template header override behind opt-in
- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA assigned, but this is the most severe-looking of today's finds: the commit message explicitly describes the prior behavior as letting a header- or body-supplied stored-procedure template be dereferenced as a `file:`/`http:`/`classpath:` resource, i.e. **SSRF / local file read** if an application forwards attacker-influenced headers into a `camel-sql`/`camel-sql-stored` route.
- **Detail:** `camel-sql` (`CamelSqlQuery`) and `camel-sql-stored` (`CamelSqlStoredTemplate`) no longer let an inbound header override the endpoint-configured query/template by default. New `allowQueryFromHeader`/`allowTemplateFromHeader` options (default `false`, marked `security = "insecure:dev"`) restore the old behavior when explicitly opted in.
- **Affected range vs. our version:** Unclear whether the underlying insecure-by-default behavior is present in 4.8.8 (the commit doesn't say this is new-in-4.23 code, unlike the camel-spiffe/camel-opa items above — this looks like a long-standing behavior being hardened) — but moot per below.
- **Component analysis:** Neither `camel-sql` nor `camel-sql-stored` is in `used_components`.
- **Severity:** MEDIUM/HIGH *(estimated)* — SSRF/file-read via header injection is a real-world exploitable pattern, but irrelevant to us since the component isn't deployed.
- **Verdict: NOT RELEVANT** (component not used).
- Sources: [Jira CAMEL-24292](https://issues.apache.org/jira/browse/CAMEL-24292), [PR #26268 / commit 6daeefed7](https://github.com/apache/camel/commit/6daeefed722014fd3e429479c4e480228fe54b8a).
- No backport assessment performed (component not used).
