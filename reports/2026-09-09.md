### CAMEL-24427 — camel-servlet: fileNameExtWhitelist enforced against the wrong string, silently accepts any file extension

- **Is this a vulnerability?** `SUSPECTED` — a "silent fix" per the methodology's silent-fix rule: no CVE/GHSA assigned as of this run, but it is a real security-control bypass, not a cosmetic change. Fixed together with an unrelated `camel-jetty` binding fix in the same PR (`camel-jetty` is not a `used_component`, so that half is out of scope here).
- **What's broken:** `camel-servlet`'s `AttachmentHttpBinding.populateAttachments()` computed the extension to check against `fileNameExtWhitelist` from `Part.getName()` — the **multipart field name** (e.g. `"file"`, `"upload"`) — instead of `Part.getSubmittedFileName()` — the **client-supplied file name** (e.g. `"payload.jsp"`). A field name carries no extension, so `FileUtil.onlyExt(fileName)` returns `null`, the `if (ext != null)` guard is never entered, and `accepted` stays `true` unconditionally — **the whitelist is a complete no-op** whenever the multipart field is named without a dot in it, which is the overwhelmingly common case (`file`, `upload`, `attachment`, …). A second, independent bug in the same method used a substring `contains()` match rather than an exact per-extension match, so even when a field name did happen to carry an extension, a whitelist of `"txt"` would also accept `"evilx.txt"`-style near-misses via substring luck (less severe, but compounds the primary bug).
- **Does the affected version range include our pinned version?** `AFFECTED` — confirmed by direct source read, not by trusting the published range (there is no published range yet; this is unreleased). `git show camel-4.8.8:components/camel-servlet/src/main/java/org/apache/camel/component/servlet/AttachmentHttpBinding.java` shows the **identical** vulnerable line `String fileName = part.getName();` used for the whitelist check, and the same substring-`contains()` comparison. Nothing about this bug is version-range-gated by unrelated refactoring — the method is essentially unchanged since well before 4.8.8.
- **Is an affected component in `used_components`?** `USED` — `camel-servlet` is explicitly listed.
- **Severity:** No CVSS published (no CVE yet). Estimated **HIGH**: this defeats a security control the application owner explicitly configured (`fileNameExtWhitelist`) specifically to restrict which file types can be uploaded through a `camel-servlet` multipart endpoint; if that control is relied on anywhere in our routes to keep out executable/script file types, uploads of any extension currently pass through unfiltered. Actual exploitability depends on what a route does with the resulting attachment (e.g. whether it's later written to a web-accessible path), which this watch cannot see from the source alone — noting as *(estimated)*, not measured.
- **Official fix / backport assessment:** [PR #26189](https://github.com/apache/camel/pull/26189), commit [`fd120518ec`](https://github.com/apache/camel/commit/fd120518ecbd591b05853434225587d2bd76b2fd) (first released in 4.23.0, currently `main`-only — the `camel-4.8.x` maintenance branch head is unchanged at `5a31b932322777b8eb5f091cf9c6f016a62fe896`, same as every run since 2026-07-23, so no backport has landed upstream). For our pinned 4.8.8, only the `camel-servlet` half of the diff applies (`components/camel-servlet/src/main/java/org/apache/camel/component/servlet/AttachmentHttpBinding.java`); the `camel-jetty` half is out of scope (component not used). The fix is a **small, self-contained, clean-apply backport candidate**:
  - Change the extraction source: `String fileName = part.getName();` → `String fileName = part.getSubmittedFileName();` (the line that feeds the whitelist check only — the existing, unrelated `am.addAttachmentObject(part.getName(), attachment)` call for the attachment key is untouched by the upstream fix and must stay keyed on the field name).
  - Replace the substring `whiteList.contains(ext)` test with the upstream's exact-match-per-comma-separated-token loop (`isExtWhitelisted(whitelist, ext)` in the fix).
  - Optional hardening also in the same upstream commit: log the client-controlled file name through `HttpHelper.sanitizeLog(...)` before the `LOG.debug(...)` call. **Note for backport:** `HttpHelper.sanitizeLog` does not exist in pinned 4.8.8's `camel-http-common` (`HttpHelper.java`) — confirmed absent by direct source read — so this piece would need its own small helper added, or the fix trimmed to the two lines above and the log-injection hardening deferred/tracked separately.
  - Code has **not drifted**: the pre-fix method body in `main` and the pinned 4.8.8 body are structurally identical (same variable names, same control flow), so the diff applies near-verbatim. Tests to port: the new `MultipartUploadFileNameExtWhitelistTest` (camel-servlet) — it does not depend on any 4.23-only test infra.
- **Sources:** [PR #26189](https://github.com/apache/camel/pull/26189) · [commit `fd120518ec`](https://github.com/apache/camel/commit/fd120518ecbd591b05853434225587d2bd76b2fd) · upstream note added to [`camel-4x-upgrade-guide-4_23.adoc`](https://github.com/apache/camel/commit/fd120518ecbd591b05853434225587d2bd76b2fd) · JIRA: `https://issues.apache.org/jira/browse/CAMEL-24427` (not fetchable this run — see Source health; URL follows the standard Camel JIRA browse pattern for the ticket key found in the commit trailer).

### CAMEL-24425 — camel-azure-storage-blob: sasToken option not recognized as a credential by the property-masking layer

- **Is this a vulnerability?** `SUSPECTED` — silent fix, no CVE/GHSA assigned as of this run. Information-disclosure class: a real credential printed in clear where other credentials on the same class are masked.
- **What's broken:** `BlobConfiguration.sasToken` (an Azure Storage **Shared Access Signature** token — a bearer credential that grants access to the storage account for its validity window) was declared with a bare `@UriParam`, unlike its sibling fields `accessKey` / `sourceBlobAccessKey` on the same class, which already carry the secret annotation. Because it was unmarked, the generated keyword `"sastoken"` was missing from `org.apache.camel.util.SensitiveUtils`'s sensitive-keys list, so `SensitiveUtils.containsSensitive("sasToken")` returned `false` — meaning anywhere Camel's property-masking layer is consulted (e.g. route/endpoint parameter dumps in trace logging, `camel-management` MBean attribute exposure, generated catalog docs) the SAS token value would be rendered in clear instead of masked, unlike the other credential fields on the same configuration class.
- **Does the affected version range include our pinned version?** `AFFECTED` — confirmed by direct source read. Pinned 4.8.8's `components/camel-azure/camel-azure-storage-blob/.../BlobConfiguration.java` (note: module path in 4.8.8 is nested under `camel-azure/`, not the flattened `camel-azure-storage-blob/` path used on `main` today) declares `sasToken` as a bare `@UriParam`, identical to pre-fix. `core/camel-util/.../SensitiveUtils.java` in pinned 4.8.8 has no `"sastoken"` entry in its keyword set (confirmed by direct grep of the tagged source) — the same gap as the pre-fix code on `main`.
- **Is an affected component in `used_components`?** `USED` — `camel-azure-storage-blob` is explicitly listed.
- **Severity:** No CVSS published. Estimated **MEDIUM**: exploitation requires an attacker to already have read access to somewhere Camel's masked-property views are exposed (application/trace logs, JMX/management endpoint, or catalog output built from a live configuration) — it is not remotely exploitable on its own — but if reached, it discloses a live storage-access credential. This is the same class of issue as the confirmed `camel-azure-storage-blob`/`camel-azure-storage-datalake` path-traversal findings already on record from 2026-08-25 (`CVE-2026-66906` et al.), i.e. this component has now surfaced two independent real hardening gaps in six weeks.
- **Official fix / backport assessment:** [PR #26185](https://github.com/apache/camel/pull/26185), commit [`c72ea16877`](https://github.com/apache/camel/commit/c72ea16877adcf808f1604fdcc1412b3480d69f0) (first released in 4.23.0, unreleased; `camel-4.8.x` branch unchanged). Backport is **small but touches more files than CAMEL-24427** because several are generated artifacts:
  - Core hand-written change: add `"sastoken"` to the two keyword lists (plain set + regex alternation) in `core/camel-util/src/main/java/org/apache/camel/util/SensitiveUtils.java`, and add `@Metadata(label = "security", secret = true)` (or equivalent annotation used by the sibling `accessKey` field) to `sasToken` in `BlobConfiguration.java` at 4.8.8's nested path (`components/camel-azure/camel-azure-storage-blob/...`).
  - The remaining changed files in the upstream commit (`azure-storage-blob.json` catalog files ×2, `BlobEndpointUriFactory.java`, `AzureStorageBlobComponentBuilderFactory.java`, `BlobEndpointBuilderFactory.java`) are **generated** from the annotation change via Camel's `camel-package-maven-plugin` — a backport should regenerate these with the same build-time tooling 4.8.8 uses (`mvn camel-package:generate-endpoint-schema` / the module's own `apt`-generated-sources build step) rather than hand-editing, to avoid drift from whatever the 4.8.8-era generator emits for other fields on the same class.
  - Test to port: `SensitiveUtilsTest`'s new assertion that `containsSensitive("sasToken")` is `true`.
  - No apparent code drift in the core files; the generated-file regeneration is the only real backport risk (build tooling must match the 4.8.8-era plugin version).
- **Sources:** [PR #26185](https://github.com/apache/camel/pull/26185) · [commit `c72ea16877`](https://github.com/apache/camel/commit/c72ea16877adcf808f1604fdcc1412b3480d69f0) · JIRA: `https://issues.apache.org/jira/browse/CAMEL-24425` (not fetchable this run — see Source health).
