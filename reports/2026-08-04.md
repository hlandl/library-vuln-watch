## Outstanding item resolved upstream: CAMEL-24293

- **Status as of today**: the fix merged to `main` on **2026-07-30** as
  `cae63dd7a3a40e7fa39f987eef4d37a8a0790397` ("Strip path segments from externally-derived filenames
  before setting CamelFileName", [PR #25218](https://github.com/apache/camel/pull/25218)). It was
  missed by the 2026-07-31 and 2026-08-01 sweeps — both ran `git log --since` windows that should
  have covered it; the discrepancy is unexplained and is flagged under Source health as a
  methodology gap to review, not evidence the fix is newer than it looks (the commit's author and
  committer dates both read 2026-07-30T18:55:04+02:00).
- **Confirmed NOT backported to `camel-4.8.x`**: direct read of
  `camel-4.8.x:components/camel-zipfile/.../ZipFileDataFormat.java` today still shows
  `exchange.getMessage().setHeader(FILE_NAME, entry.getName())` (raw, unstripped entry name) at the
  unmarshal call site, and `ZipIterator.java` line 137 still does the same in the
  `.split(new ZipSplitter())` path. `git merge-base --is-ancestor` confirms the fix commit is not an
  ancestor of `camel-4.8.x`. The `camel-4.8.x` branch tip is unchanged since 2026-07-23
  (`5a31b932322777b8eb5f091cf9c6f016a62fe896`).
- **The fix, and how it applies to our line**:
  - `ZipFileDataFormat.java`: `entry.getName()` → `FileUtil.stripPath(entry.getName())` when setting
    the `CamelFileName` header from an unmarshalled entry.
  - `ZipIterator.java` (the `.split()`/iterator path): same treatment for the header set from
    `zipFileName` in the split-message path.
  - The full (unstripped) entry name remains available on a dedicated header (`zipFileName`) for
    routes that need to reconstruct archive directory structure.
- **Backport assessment: LOW difficulty, should apply cleanly in intent though not as a literal
  cherry-pick.** `main`'s `camel-zipfile` has been refactored to use Apache Commons Compress
  (`ZipArchiveEntry` / `ArchiveStreamFactory`) instead of `java.util.zip.ZipEntry`/`ZipInputStream`,
  which `camel-4.8.x` still uses — so `git cherry-pick` will conflict on both files. However:
  - `org.apache.camel.util.FileUtil.stripPath(String)` (the helper the fix relies on) **already
    exists** in `camel-4.8.x`'s `core/camel-util` — no new utility code needs to be ported.
  - The mechanical change needed on `camel-4.8.x` is the same one-line pattern at two call sites:
    wrap `entry.getName()` with `FileUtil.stripPath(...)` in `ZipFileDataFormat.unmarshal()` (current
    line ~109) and in `ZipIterator`'s split/iterator path (current line ~137, sets both
    `Exchange.FILE_NAME` and `zipFileName`/leaves `zipFileName` as the full name).
  - `camel-tarfile` has the identical unstripped-`entry.getName()` pattern in `TarFileDataFormat.java`
    (`camel-4.8.x` line ~115) and was fixed the same way upstream, but **`camel-tarfile` is not in
    `used_components`** — out of scope for us, noted for completeness only.
  - Tests to port alongside: `ZipFileNameStripPathTest` and the iterator/splitter regression cases
    added in the same PR (per Guillaume Nodet's review feedback on #25218) — these are new test
    classes on `main`, not modifications of existing ones, so they can be copied over with import/API
    adjustments for the `java.util.zip`-based 4.8.x code.
- **CVE/GHSA status**: still unknown — `camel.apache.org/security/`, NVD, and Jira remain unreachable
  from this environment (see Source health), so this cannot be confirmed directly today. No matching
  advisory was found in the (partial — see Source health) local scan of the
  `github/advisory-database` 2026 tree.
- **Recommendation**: this is now the top-priority backport item — the fix is small, upstream-tested,
  and mechanically clear; it should not need to wait for a CVE/GHSA assignment given the maintenance
  branch has been carrying this exposure for five days with a public, merged fix already describing
  the exact defect.

## Findings

### CAMEL-24299 — `XmlStreamDetector` leaves DTD processing enabled

- **Is this a vulnerability?** SUSPECTED — a security-motivated hardening commit with no assigned
  CVE/GHSA.
- **Affected version range vs. our pinned version**: the weakness (StAX `XMLInputFactory` created
  without `SUPPORT_DTD=false`) predates this fix and is present in `camel-4.8.8` (confirmed:
  `camel-4.8.x`'s `core/camel-xml-io-util/.../XmlStreamDetector.java` does not set `SUPPORT_DTD`).
- **Component analysis**: `core/camel-xml-io-util` **is** in `used_components`. However, reachability
  from our actual routes is unclear: the class's own javadoc describes its purpose as supporting
  `jbang run camel@camel run`-style quick XML root-element detection, and an attempt to enumerate
  non-test call sites across the current `main` tree did not complete (network-cost timeout on a
  full-tree `git grep` against the partial clone — see Source health) so absence of a runtime
  call site is **not confirmed**, only unconfirmed either way.
- **Severity**: LOW *(estimated)* — `IS_SUPPORTING_EXTERNAL_ENTITIES=false` was already set (blocks
  classic XXE file-read/SSRF), so the residual exposure is entity-expansion (“billion laughs”-style)
  DoS via internal DTD entities during the pre-scan, contingent on this detector actually being
  invoked on attacker-controlled input somewhere in our deployment.
- **Verdict**: **NEEDS REVIEW** — a human should confirm whether `XmlStreamDetector` is invoked
  anywhere in our routes/tooling on untrusted XML (vs. only via `camel-jbang`, which we don't use).
  If it is genuinely unreachable, this can be downgraded to NOT RELEVANT.
- **Official fix**: `apache/camel@a746e8ea958ef2451a2b3505cddaba676e512fbe`
  ([PR #25279](https://github.com/apache/camel/pull/25279)) — adds
  `factory.setProperty(XMLInputFactory.SUPPORT_DTD, false)` next to the existing
  external-entities-disabled setting. Two-line change, `core/camel-xml-io-util` only.
- **Backport assessment**: trivial if warranted — the same one property-setting line applies
  unchanged to `camel-4.8.x`'s copy of `XmlStreamDetector.java` (not yet confirmed present as
  ancestor via `merge-base`; file content on the 4.8.x branch still lacks the line). Low priority
  pending the reachability question above.
