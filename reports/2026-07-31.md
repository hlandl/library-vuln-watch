## Findings

### CAMEL-24293 — camel-zipfile / camel-tarfile / camel-platform-http-vertx: Zip Slip / Tar Slip via unstripped `CamelFileName`

- **Is this a vulnerability?** **SUSPECTED** — no CVE/GHSA assigned yet (commit landed on `main`
  2026-07-30, one day ago). The upstream commit message and the accompanying upgrade-guide entry
  unambiguously describe it as a path-traversal ("Zip Slip / Tar Slip") hardening fix, not a
  feature: *"the `CamelFileName` header was previously set to the raw archive entry name, which
  for a crafted archive can contain path segments (e.g. `../../etc/passwd`). If a downstream route
  wrote the message to disk using that header, the entry name could escape the intended
  directory."*
  - **Root cause**: `ZipFileDataFormat.unmarshal()` and `ZipIterator` (camel-zipfile), and the
    tar/`TarFileDataFormat`/`TarIterator` equivalents (camel-tarfile), plus
    `VertxPlatformHttpConsumer` (camel-platform-http-vertx, multipart upload filename) all set
    `Exchange.FILE_NAME` directly from attacker-influenced input (archive entry name / uploaded
    filename) with no sanitization. A route that unmarshals an untrusted zip/tar and then writes
    the extracted message to disk (e.g. `.unmarshal().zipFile() ... .to("file:///output")`, which
    by default writes using `CamelFileName`) can be made to write outside the intended output
    directory by a crafted entry name.
  - **The fix**: wrap the raw name in `FileUtil.stripPath(...)` before setting `Exchange.FILE_NAME`
    at each of these five call sites, so the control header only ever carries a leaf filename. The
    full original entry name remains available on a dedicated, non-control header
    (`CamelTarFileEntryName` for tar, `zipFileName` for zip) for routes that intentionally rebuild
    the archive's directory structure.
- **Does the affected range include our pinned version?** **AFFECTED.** Verified directly against
  the `camel-4.8.8` tag: `ZipFileDataFormat.java` line 109 and `ZipIterator.java` line 137 both
  still do `exchange.getMessage().setHeader(FILE_NAME, entry.getName())` / `current.getName()`
  unstripped — the vulnerable pattern is present. The `camel-4.8.x` maintenance branch head
  (`5a31b932322777b8`) has the identical code; no backport has landed there.
- **Is an affected artifact in `used_components`?** **USED** — `camel-zipfile` is explicitly listed
  in `used_components`. `camel-tarfile` and `camel-platform-http-vertx` (the other two components
  touched by the same commit) are **not** in `used_components`, so only the `camel-zipfile` half of
  this fix is in scope for our deployment, but that's sufficient to make this AFFECTS US.
- **Severity**: **HIGH *(estimated)*** — no published CVSS (no CVE yet). Reasoning: this is a
  classic CWE-22 path-traversal / arbitrary-file-write primitive (the "Zip Slip" pattern), network
  -reachable if the ingested zip arrives over any inbound transport (HTTP upload, FTP, mail
  attachment, etc.) ahead of the `unmarshal().zipFile()` step, and the impact is file-system
  integrity (write to an attacker-chosen path) if a downstream route writes the message to disk
  keyed on `CamelFileName` — a common Camel idiom. Estimated in the CVSS 3.1 `AV:N/AC:L/PR:N/UI:N`
  High range (comparable to previously-disclosed Camel header-injection/path CVEs already in
  `state/seen.json`, e.g. `CVE-2026-47323`, `CVE-2026-33454`), pending an actual assignment.
- **Official fix**: commit
  [`cae63dd7a3a40e7fa39f987eef4d37a8a0790397`](https://github.com/apache/camel/commit/cae63dd7a3a40e7fa39f987eef4d37a8a0790397)
  (PR [apache/camel#25218](https://github.com/apache/camel/pull/25218), merged 2026-07-30 by
  Andrea Cosentino). Files changed: `VertxPlatformHttpConsumer.java`, `TarFileDataFormat.java`,
  `TarIterator.java`, `ZipFileDataFormat.java`, `ZipIterator.java`, plus new regression tests
  (`TarFileNameStripPathTest.java`, `ZipFileNameStripPathTest.java`) and a `4.22` upgrade-guide
  entry. **Not yet in any released version** — the upgrade-guide filename
  (`camel-4x-upgrade-guide-4_22.adoc`) implies the first fixed release will be the `4.22` line;
  **not backported to `camel-4.8.x`** as of this run.
- **Backport assessment**: **Low risk / clean apply expected for the in-scope half of this fix.**
  - `camel-4.8.8`'s `ZipFileDataFormat.java` and `ZipIterator.java` are structurally unchanged from
    `main` at the two relevant call sites — same class/package layout, same field and method names.
  - `FileUtil.stripPath(...)` (the helper the upstream fix uses) **already exists** in
    `camel-4.8.8`'s `core/camel-util` (used elsewhere in that same file), so the backport for
    `camel-zipfile` is a minimal two-line change: wrap `entry.getName()` in
    `ZipFileDataFormat.unmarshal()` and `current.getName()` in `ZipIterator` with
    `FileUtil.stripPath(...)`, exactly as upstream did — no drift, no missing dependency.
  - **Test to port**: `ZipFileNameStripPathTest.java` (new upstream regression test) — the
    equivalent test does not yet exist on `camel-4.8.x`.
  - **Watch out for a fallout the upstream fix itself hit**: `camel-4.8.8`'s existing
    `ZipFileDataFormatTest.java` (line 307) already reconstructs a `ZipEntry` from the
    `Exchange.FILE_NAME` header inside one test — this is the same pattern that broke upstream's
    empty-directory extraction test once `FILE_NAME` became a stripped leaf name. Check whether
    that test uses an entry name containing a path segment; if so it will need the same treatment
    upstream applied (switch to reading the full name from the `zipFileName` header instead).
  - `camel-tarfile` and `camel-platform-http-vertx` are **not used components** for us — their
    halves of the fix are out of scope for backport, noted only for completeness since they're part
    of the same upstream commit.
