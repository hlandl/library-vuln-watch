## Findings

### CAMEL-24440 — camel-crypto: per-message IV when inlining, and uniform authentication failures

- **Is this a vulnerability?** `SUSPECTED` — a genuine, non-trivial security-hardening fix found via the GitHub repo sweep (no CVE/GHSA assigned as of this run; merged to `main` 2026-09-25T11:25:50+02:00, PR labeled `bug` and `port/camel-4.22.x`). Three distinct issues fixed in `CryptoDataFormat`/`HMACAccumulator`:
  1. **Forced IV reuse:** `marshal()` previously threw `"Inlining cannot be performed, as no initialization vector was specified"` whenever `shouldInlineInitializationVector` was set without a statically configured vector — which pushed route authors into configuring and **reusing one static IV for every message**, defeating the entire purpose of inlining (CWE-323-style, weakens CBC/CTR-mode confidentiality).
  2. **Padding-oracle side channel:** a tampered ciphertext produced two distinguishable outcomes — `"Given final block not properly padded"` (from `CipherInputStream`) vs. `"Expected mac did not match actual mac"` (from the MAC check) — letting an attacker who can submit ciphertext and observe which message comes back use that oracle to recover plaintext byte-by-byte (classic CBC padding-oracle, CWE-203/CWE-696). The fix reports both as a single `"Message authentication failed"` and additionally stops including both MAC values (attacker-computed vs. expected) in hex in the failure message, which previously handed the caller a value (the freshly computed HMAC over the plaintext) they could not otherwise obtain.
  3. **Unbounded allocation:** the inlined IV length was read directly off the incoming message and used to size an allocation with no bound; the fix rejects inlined vectors outside 0–1024 bytes.
- **Does the affected version range include our pinned version?** Not evaluated — dropped at the component-use check (see below). For the record, `camel-crypto`'s `CryptoDataFormat`/`HMACAccumulator` classes have existed with essentially this design since early Camel versions, so if the component were in use the pinned 4.8.8 code would very likely need direct verification, but this was not performed since it's moot.
- **Is an affected artifact in `used_components`?** `NOT-USED` — `camel-crypto` is **not** present in `config/libraries.yaml`'s `used_components` list (checked exhaustively: no `camel-crypto` entry).
- **Severity:** No CVSS published. Estimated **HIGH** *(estimated)* if in scope — padding-oracle attacks against CBC-mode ciphertext are a well-established, automatable technique (e.g. POODLE/Vaudenay-style) that can lead to full plaintext recovery given enough oracle queries; moot here since the component isn't shipped.
- **Verdict: NOT RELEVANT** (component not used).
