## Findings

### CAMEL-24421 — `camel-spring-redis`: default JDK serializer built with no deserialization filter

- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA assigned yet. The upstream commit message
  is explicit that this closes a gap: every other component doing JDK deserialization in the
  codebase (camel-consul, camel-leveldb, camel-mina, camel-netty, camel-netty-http,
  camel-vertx-http, camel-jms, camel-sjms, camel-http-common, camel-cassandraql) already resolves
  an `ObjectInputFilter` before deserializing; `camel-spring-redis`'s
  `RedisConfiguration.createDefaultSerializer()` was the one path left without one, so
  `JdkSerializationRedisSerializer`'s read path ran through Spring's
  `ConfigurableObjectInputStream` unfiltered. This is the same vulnerability class (CWE-502) as
  several already-tracked Camel CVEs (e.g. the netty/hazelcast/consul deserialization-filter
  fixes already in `state/seen.json`).
- **Affected range vs. our version?** `AFFECTED` (by code pattern) — our pinned 4.8.8 predates
  this hardening across the whole codebase, so the same gap plausibly exists in 4.8.8's
  `camel-spring-redis`, moot given the component check below.
- **Component in use?** `camel-spring-redis` is **not** in `used_components` → **NOT-USED**.
- **Severity:** High *(estimated)* — if reachable (an attacker with write access to the backing
  Redis instance), this class of bug is RCE via crafted serialized payload; not applicable here
  since the component isn't shipped.
- **Verdict: NOT RELEVANT** (component not used).
- Source: [apache/camel@8db602a5e](https://github.com/apache/camel/commit/8db602a5ee105403fa40c1b821157c8d9d0c1977)
  ("CAMEL-24421", PR [#25587](https://github.com/apache/camel/pull/25587)), merged 2026-08-24. Not
  yet in any released version; `camel-4.8.x` branch head unchanged.

### CAMEL-24422 — `camel-docling`: message body strings were implicitly interpreted as URLs or local file paths

- **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA assigned yet. `DoclingProducer.getInputPath()`
  previously inferred meaning from a String body's prefix (`http://`/`https://` → fetched as a
  remote URL; leading `/` or embedded `\` → read from the local filesystem) with no way for the
  route author to opt out — a classic SSRF/arbitrary-file-read primitive if the body content is
  attacker-influenced (e.g. relayed from an untrusted source). The fix gates both interpretations
  behind new `allowUrlSource`/`allowFilePathSource` options, both defaulting to `false`.
- **Affected range vs. our version?** `AFFECTED` (by code pattern) in principle; moot per below.
- **Component in use?** `camel-docling` is **not** in `used_components` → **NOT-USED**.
- **Severity:** Medium *(estimated)* — SSRF/local-file-read impact depends entirely on whether a
  route feeds attacker-controlled body content to this data format; not applicable here.
- **Verdict: NOT RELEVANT** (component not used).
- Source: [apache/camel@8b95ef190](https://github.com/apache/camel/commit/8b95ef19002a86ed530563a6df0772140ddb5cd0)
  ("CAMEL-24422", PR [#25596](https://github.com/apache/camel/pull/25596)), merged 2026-08-24. Not
  yet in any released version.

### CVE-2026-6857 / GHSA-xfxp-ppx7-cqrp — `camel-infinispan` unsafe deserialization (RCE)

- Surfaced this run via Red Hat's `RHSA-2026:17668` (WebSearch substitute for the blocked NVD/RH
  feeds — see Source health). `DefaultExchangeHolderUtils.deserialize(byte[])` builds a
  `ClassLoadingAwareObjectInputStream` with no `ObjectInputFilter`; the ProtoStream remote
  aggregation repository routes Infinispan cache bytes straight into it, so anyone able to write
  to the backing Infinispan cache (Hot Rod port 11222 or its REST API) can plant a crafted
  serialized object and trigger RCE on the next `get`/`recover`. CVSS 7.5, CWE-502. Fixed in
  4.14.7 / 4.18.2 / 4.20.0.
- **Dedup note:** this CVE ID is an alias of **GHSA-xfxp-ppx7-cqrp**, already recorded in
  `state/seen.json` on 2026-07-15 (verdict `NOT_RELEVANT`) — **not a new finding**; the CVE alias
  is added to `state/seen.json` this run purely so future sweeps recognize it immediately.
- **Component in use?** `camel-infinispan` is **not** in `used_components` → **NOT-USED**, confirmed
  again this run.
- **Verdict: NOT RELEVANT** (component not used; previously assessed).

### CVE-2026-41635 — Apache MINA `AbstractIoBuffer.resolveClass()` classname-allowlist bypass (RCE)

- Also surfaced via `RHSA-2026:17668`, which bundles this MINA CVE alongside the Camel CVEs above
  because Camel's Red Hat distribution ships MINA as a dependency. `resolveClass()` has a branch
  (static classes/primitives) that skips the `acceptMatchers` classname filter entirely before
  calling `Class.forName()`, letting an attacker who can reach `IoBuffer.getObject()` execute
  arbitrary code. CVSS 9.8. Fixed upstream in MINA 2.0.28 / 2.1.11 / 2.2.6.
- **Scope:** this is a vulnerability in **Apache MINA itself**, not Camel code — `config/libraries.yaml`
  explicitly excludes third-party transitive dependencies (CXF, MINA, Jackson, …) from this
  watch, since those are handled by the regular SBOM/CVE scanning process. `camel-mina`/`camel-mina2`
  are also not in `used_components`.
- **Verdict: NOT RELEVANT** (out of scope for this watch). Recorded in `state/seen.json` so it
  isn't re-surfaced by future RHSA/WebSearch sweeps; **flagging for the regular SBOM/CVE process**
  in case any in-use component pulls MINA transitively.

### CAMEL-24401 — `camel-jms`: temporary `replyTo` could get stuck in a permanent resolution loop

- **Is this a vulnerability?** `NOT-SECURITY`. `TemporaryQueueReplyManager` used a one-shot
  `refreshWanted` flag that could be cleared before the replacement temporary queue was published,
  leaving `InOut` producers stuck logging "Failed to resolve replyTo destination" after a JMS
  connection fault — a reliability/self-recovery bug triggered by an operational fault condition
  (broker fault), not by attacker-controlled input, and not an access-control, injection, or
  deserialization issue.
- **Component check:** `camel-jms` **is** in `used_components`, but moot given the NOT-SECURITY
  classification.
- **Verdict: NOT RELEVANT** (dropped: not a vulnerability).
- Source: [apache/camel@d1f0dd80b](https://github.com/apache/camel/commit/d1f0dd80bda7d7204f0a7bf638660df4b37d4fb5)
  ("CAMEL-24401", PR [#25531](https://github.com/apache/camel/pull/25531)), merged 2026-08-24.
