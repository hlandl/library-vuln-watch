## Findings

### CAMEL-24371 — camel-a2a: WebhookUrlValidator address classification and host matching

- **Is this a vulnerability?** `SUSPECTED`. No CVE/GHSA has been assigned. Commit [`54041cce5`](https://github.com/apache/camel/commit/54041cce545322f7ff1bb362ecc02999b3d96ba0) (merged via [PR #25406](https://github.com/apache/camel/pull/25406), 2026-08-09) fixes an SSRF-adjacent inconsistency in `WebhookUrlValidator`: an IP-literal host was checked against a string-prefix blocklist while a name-based host was classified via `InetAddress` predicates, and the two paths disagreed — `isSiteLocalAddress` only recognizes the deprecated `fec0::/10` block, not the `fc00::/7` unique-local range that replaced it, so the same address could be accepted or rejected depending on how it was written; conversely, any hostname beginning with `fc`/`fd` (e.g. `fcm.googleapis.com`) was wrongly rejected by the literal-prefix pre-check. Both paths now resolve the host and classify it with one shared raw-byte classifier. This is exactly the class of fix this watch's "silent fix" sweep exists to catch (per `AGENT.md` step 2's GitHub repo sweep).
- **Does the affected range include our pinned version (4.8.8)?** `N/A` — `camel-a2a` did not exist in Camel 4.8.8 (it's a newer component); the question is moot.
- **Is an affected component in `used_components`?** `NOT-USED`. `camel-a2a` is not present in `config/libraries.yaml`'s `used_components` list.
- **Severity:** MEDIUM *(estimated — SSRF-class host-validation bypass, but gated by component non-use)*.
- **Verdict:** **NOT RELEVANT** (component not used).
- **Sources:** [Commit 54041cce5](https://github.com/apache/camel/commit/54041cce545322f7ff1bb362ecc02999b3d96ba0) · [PR #25406](https://github.com/apache/camel/pull/25406).
- **Official fix / backport assessment:** Not performed — component not in use, per methodology step 5's scope (only `AFFECTS US` / high-severity `NEEDS REVIEW` get a backport assessment).

### CAMEL-24379 — camel-as2: client ignored custom HostnameVerifier

- **Is this a vulnerability?** `SUSPECTED`. No CVE/GHSA assigned. Commit [`7286241dc`](https://github.com/apache/camel/commit/7286241dc548857c413170ccd0910e2efa0f03f4) (2026-08-11) fixes a TLS hostname-verification bypass: `DefaultClientTlsStrategy` defaulted to `HostnameVerificationPolicy.BOTH`, so the JDK trust manager enforced hostname verification during the TLS handshake *before* a configured custom `HostnameVerifier` (e.g. `NoopHostnameVerifier`) ran — silently defeating the intent of setting a custom verifier. Fixed by switching to `HostnameVerificationPolicy.CLIENT`, delegating verification entirely to the configured verifier. Also a "silent fix" candidate per the repo-sweep source.
- **Does the affected range include our pinned version (4.8.8)?** `UNCLEAR` — the `AS2ClientConnection`/`DefaultClientTlsStrategy` code predates this fix by a long margin (Apache HttpClient 5's `HostnameVerificationPolicy` API), so 4.8.8 likely contains the same defect, but this was not independently verified line-by-line against the 4.8.8 tag.
- **Is an affected component in `used_components`?** `NOT-USED`. `camel-as2` is not present in `used_components`.
- **Severity:** MEDIUM *(estimated — TLS hostname-verification bypass is normally higher, but it only matters if a caller has deliberately configured a non-default `HostnameVerifier`, and the component isn't in use here anyway)*.
- **Verdict:** **NOT RELEVANT** (component not used).
- **Sources:** [Commit 7286241dc](https://github.com/apache/camel/commit/7286241dc548857c413170ccd0910e2efa0f03f4) (closes [#25446](https://github.com/apache/camel/pull/25446)).
- **Official fix / backport assessment:** Not performed — component not in use.
