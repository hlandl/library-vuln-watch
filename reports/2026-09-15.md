## Findings

### CAMEL-24717 — camel-opa: bearerToken exposed in health-check id
- **Is this a vulnerability?** `SUSPECTED` — a silent hardening fix with no CVE/GHSA assigned, caught via the GitHub repository sweep (commit subject/diff, not a keyword-matched security ticket title).
- **Detail:** The `camel-opa` component's producer health check built its health-check id using the endpoint configuration, which included the configured `bearerToken` verbatim — so the credential could leak into health-check output/logs/monitoring endpoints. Fixed by excluding the token from the id (commit `caf68b54f26e2a732664db75099fe7ac52564dd6`, merged 2026-09-14, not yet in any tagged release).
- **Affected range vs. our version:** N/A for the credential-exposure mechanism itself — `camel-opa` (Open Policy Agent integration) does not exist as a component in our pinned 4.8.8 (confirmed present in current `main` at `components/camel-opa`; this is a comparatively new component in the Camel component catalog).
- **Component analysis:** `camel-opa` is **not** in `config/libraries.yaml`'s `used_components` list.
- **Severity:** LOW *(estimated)* — credential exposure limited to health-check/monitoring surfaces, no CVE published.
- **Verdict: NOT RELEVANT** (component not used; also does not exist in our pinned version).
- Sources: [Jira CAMEL-24717](https://issues.apache.org/jira/browse/CAMEL-24717) (not independently fetched — Jira REST blocked, see Source health), [commit caf68b54f2](https://github.com/apache/camel/commit/caf68b54f26e2a732664db75099fe7ac52564dd6).
- No backport assessment performed (NOT RELEVANT, not high-severity NEEDS REVIEW).

## Carry-over check

Re-checked the three open `NEEDS_REVIEW` carry-overs via `WebSearch` (`CAMEL-24296`, `CAMEL-24298`, `CAMEL-24299`, all `camel-core`/related components, all `used_components`). All three commits predate the shallow-clone window (merged before 2026-09-11) so were not visible in this run's git sweep; targeted searches surfaced incremental detail not previously recorded:

- **CAMEL-24296**: confirmed to be part of the shared `DeserializationFilterHelper` / JEP-290 `ObjectInputFilter` hardening work "alongside CAMEL-23815" — i.e., the mechanism that lets Camel restrict deserialized classes to an allow-list. This is consistent with the note already recorded against `CVE-2026-42527` (2026-08-25 entry): our pinned 4.8.8 predates this `ObjectInputFilter` mechanism entirely — it has **no** deserialization allow-list filter of this kind at all, so this ticket describes infrastructure that doesn't exist yet in our version rather than a fix we could backport as a discrete patch. Still no CVE/GHSA assigned. **No verdict change** — remains `NEEDS_REVIEW` (open question: whether the *absence* of any ObjectInputFilter in 4.8.8 should itself be escalated as a standing gap, independent of this specific ticket — flagged for human judgement, not this watch's scope to decide unilaterally).
- **CAMEL-24298**: confirmed to be the ticket that added a **URI-scheme allow-list** for the `recipientList`/`toD` (Dynamic-Send-To) EIP family — found via a related bug report (`CAMEL-24576`) that references `CAMEL-24298`'s allow-list mechanism (`setAllowedSchemes`) not reaching a subscription's `destinationUri` in `camel-dynamic-router`. This is a genuine hardening feature (scheme restriction against dynamically-computed recipient/URI destinations — mitigates unintended-protocol / SSRF-style risk when route destinations are built from untrusted data). `camel-core` (which implements `recipientList`/`toD`) is a `used_component`. Still no CVE/GHSA assigned to `CAMEL-24298` itself. **No verdict change** — remains `NEEDS_REVIEW`; worth a closer look at whether our pinned 4.8.8 has any equivalent scheme restriction on `recipientList`/`toD` at all (unconfirmed this run — would require reading the 4.8.8 `RecipientList`/`SendDynamicProcessor` source directly, not yet done).
- **CAMEL-24299**: confirmed to be `camel-core` setting `SUPPORT_DTD=false` in `XmlStreamDetector`, for consistency with the other XML parsers in the codebase — an **XXE-hardening** change (disabling DTD processing prevents a class of XML External Entity attacks during stream-based format sniffing). Notably this was **backported to multiple actively-maintained lines**: released in 4.22.0, and backported to 4.18.4 and 4.14.9 — i.e., ASF judged this security-relevant enough to backport across maintenance branches even without cutting an individual CVE for it. `camel-core` is a `used_component`. **No verdict change** — remains `NEEDS_REVIEW`; given the multi-branch backport pattern this is the strongest of the three carry-overs for eventual promotion to `AFFECTS_US` once the actual commit/diff is located (not found this run — GitHub PR/commit search for `CAMEL-24299` did not surface a direct link; recommend a follow-up with a broader (non-shallow) clone or once `api.github.com` search access is restored).

No CVE/GHSA id was confirmed assigned to any of the three this run. All three remain `NEEDS_REVIEW`, carried forward to the next run with the added detail above.
