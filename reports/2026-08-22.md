## Findings

### CAMEL-24419 — `camel-mail`: `MimeMultipartDataFormat` unmarshal copies external MIME headers onto the Exchange with no filtering in 4.8.8

- **Is this a vulnerability?** SUSPECTED — no CVE/GHSA assigned as of this run (GHSA sweep,
  `camel.apache.org/security/` substitute via GitHub advisories, and targeted WebSearch all
  turned up nothing beyond the 7 already-known Camel advisories). The upstream commit message
  frames it explicitly as closing a header-injection gap, matching the same vulnerability
  family as the already-reported **CVE-2026-33454** (`camel-mail` inbound header injection,
  CVSS 9.4, reported 2026-07-15, `AFFECTS US`) and the still-open **CAMEL-23522** (`NEEDS REVIEW`
  since 2026-07-15).
- **Affected range vs. our version?** **AFFECTED — confirmed by direct code inspection, and
  worse than the gap this commit actually closes.** The upstream fix (commit `c2bcb2481`)
  swaps `MimeMultipartDataFormat`'s `headerFilterStrategy` field from a plain
  `DefaultHeaderFilterStrategy` (added by the unrelated CAMEL-23891) to `MailHeaderFilterStrategy`,
  so the `headersInline` unmarshal path finally filters the same `mail.smtp.`/`mail.smtps.`/`Camel*`
  namespace the mail *consumer* already filters. Checked our pinned tag directly
  (`git show camel-4.8.8:components/camel-mail/.../MimeMultipartDataFormat.java`): **the
  `headerFilterStrategy` field/import doesn't exist in 4.8.8 at all** — CAMEL-23891 (which
  introduced it) postdates our pin. In 4.8.8, `unmarshal()`'s `headersInline` branch is:
  ```java
  if (headersInline) {
      mimeMessage = new MimeBodyPart(stream);
      camelMessage = exchange.getMessage();
      MessageHelper.copyHeaders(exchange.getIn(), camelMessage, true);
      Enumeration<?> headersEnum = mimeMessage.getNonMatchingHeaders(STANDARD_HEADERS);
      while (headersEnum.hasMoreElements()) {
          Object ho = headersEnum.nextElement();
          if (ho instanceof Header) {
              Header header = (Header) ho;
              camelMessage.setHeader(header.getName(), header.getValue());   // <-- no filter call at all
          }
      }
  }
  ```
  Every non-standard MIME header from the parsed body part — not just the `mail.smtp.`/`mail.smtps.`
  namespace this commit targets, but also `Camel*`/`org.apache.camel.`-prefixed names — is copied
  straight onto the Exchange, unconditionally. This is a strictly larger gap than the one the
  upstream commit closes (which assumes a header filter is already present and just needed the
  right namespace list).
- **Component in use?** `camel-mail` is in `used_components` → **USED**.
- **Severity:** HIGH *(estimated)*. Requires a route to use the `mimeMultipart` data format's
  `unmarshal()` with `headersInline=true` against attacker-influenced MIME content (e.g. mail
  retrieved from an inbox reachable by an untrusted sender, or any other multipart source fed to
  this data format). Where that applies, an attacker fully controls arbitrary Exchange headers —
  including `Camel*`-prefixed routing headers and `mail.smtp.*`/`mail.smtps.*` JavaMail session
  properties if the message is later relayed — the same header-injection primitive rated
  CVSS 9.4/Critical for the consumer-side gap in CVE-2026-33454. Rated one notch below that
  precedent (High rather than Critical) because exploitation needs the explicit
  `mimeMultipart`+`headersInline=true` route configuration rather than being reachable through the
  default mail consumer path.
- **Sources:** commit
  [`c2bcb2481`](https://github.com/apache/camel/commit/c2bcb24814a806ced928e612ce5da1a6e3658234)
  on `apache/camel` `main` (2026-08-21, 23:07 CEST), PR
  [#25568](https://github.com/apache/camel/pull/25568) ("CAMEL-24419: camel-mail - filter the mail
  session property namespace on MimeMultipart unmarshal"), referenced Jira key CAMEL-24419 (Jira
  itself unreachable this run to confirm ticket state directly — see Source health). Related prior
  findings already in `state/seen.json`: CVE-2026-33454 / GHSA-2vqf-x7g4-7c2g (AFFECTS US,
  2026-07-15) and CAMEL-23522 (NEEDS REVIEW, 2026-07-15).
- **Official fix / release status:** Landed on `main` only (2026-08-21); ships in 4.23.0 per the
  commit's own upgrade-guide entry. Not backported to any maintenance branch —
  `camel-4.8.x` branch head is unchanged (`5a31b932322777b8eb5f091cf9c6f016a62fe896`, same as every
  prior run since 2026-07-23) and no `camel-4.14.x`/`camel-4.18.x`/`camel-4.22.x` backport was
  found in the merged-PR sweep.
- **Backport assessment:** **Not a clean cherry-pick** — the upstream patch is a two-line class
  swap that assumes infrastructure (the `headerFilterStrategy` field, `copyNonStandardHeaders`/
  `applyFilterToExternalHeaders`) that does not exist in our 4.8.8 code; that infrastructure was
  added later by CAMEL-23891, which is itself unreleased/unbackported. Recommended approach for
  our fork, in order:
  1. Backport `MailHeaderFilterStrategy`'s inbound enhancement from CAMEL-23522 first (adds
     `setInFilterStartsWith` for `Camel*`/`camel*` **and** `mail.smtp.`/`mail.smtps.` prefixes —
     4.8.8's copy of this class only has the outbound filter, `setOutFilterStartsWith`). This is
     the same prerequisite already flagged as open in the 2026-07-15 CAMEL-23522 write-up.
  2. In `MimeMultipartDataFormat.unmarshal()`'s `headersInline` branch, replace the unconditional
     `camelMessage.setHeader(header.getName(), header.getValue())` call with a filter check against
     the (now-hardened) `MailHeaderFilterStrategy` instance, mirroring
     `applyFilterToExternalHeaders`'s semantics (don't set the header if the strategy says filter).
  3. Port the new regression test `unmarshalInlineHeadersFiltersMailSessionPropertyHeaders` from
     `MimeMultipartDataFormatTest.java` (adjusted for 4.8.8's lack of `copyNonStandardHeaders` — the
     assertion targets are the same, only the call site differs), plus whatever inbound-filter test
     accompanies the CAMEL-23522 backport in step 1.
  - No renames/refactors complicate the target file itself (`unmarshal()`'s structure at the
    relevant hunk is otherwise stable), but this is a 3-commit chain to port correctly, not a
    single cherry-pick — flag for review rather than a fire-and-forget backport.

## Other commits reviewed and ruled out this run

- **CAMEL-24411** (`a3a98e4c9`, 2026-08-21) — `camel-oauth`'s `OAuthBearerTokenProcessor` /
  `OAuthCodeFlowProcessor` / `OAuthCodeFlowCallback` returned normally from `process()` on paths
  where the caller was *not* authenticated, so the rest of the route still ran with no
  `setRouteStop`/`CamelAuthorizationException`/`RoutePolicy` ever halting the exchange — a real
  authentication-bypass-shaped bug (would be High/Critical if it reached us). `camel-oauth` is
  **not** in `used_components` → out of scope, but flagged here since a route composed the same
  way (`.process(someAuthProcessor).setBody(...)` with no explicit stop) could reproduce the same
  class of issue outside this specific component; worth a defense-in-depth check of any in-house
  processors built on the same pattern, though that's outside this watch's scope (Camel-artifact
  code only, per `config/libraries.yaml`).
- **CAMEL-24413** (`27836f4c1`, 2026-08-21) — `ReplicatedHazelcastAggregationRepository` didn't
  call `HazelcastSerializationFilterHelper.applyDefault(Config)` because it overrides `doStart()`
  without calling `super.doStart()`, so it never got the Java-deserialization allow-list every
  sibling repository has had since CAMEL-23414. `camel-hazelcast` is not in `used_components`.
- **CAMEL-24370** (`5daaebbe6` + doc-only follow-up `c9cb9c8f9`, 2026-08-21) — `camel-netty`'s
  `ObjectDecoder`/`DatagramPacketObjectDecoder` only installed an `ObjectInputFilter` when an
  explicit `deserializationFilter` pattern was configured; the single-argument constructor path
  passed `null` and applied no filter at all. Now always resolves a filter via
  `DeserializationFilterHelper` (explicit pattern → JVM-wide `jdk.serialFilter` → Camel's shared
  allow-list). `camel-netty` is not in `used_components`.
- **CAMEL-24349** (`bdebd92f8`, 2026-08-21) — `camel-google-functions`' `createFunction` threw a
  bare `NullPointerException` instead of naming the missing header; a usability fix, not a
  vulnerability. Component not in `used_components` either way.
