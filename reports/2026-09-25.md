## Findings

### CAMEL-24433 — camel-mail: attachment file name not sanitised on unmarshal, not quoted on marshal

- **Is this a vulnerability?** `SUSPECTED` — a silent security-hardening fix found via the GitHub repo sweep (no CVE/GHSA assigned as of this run; the fix landed on `main` only hours before this run, 2026-09-24T07:39:32Z). Two distinct issues in the same commit:
  1. **Unmarshal (path traversal, CWE-22):** `MimeMultipartDataFormat.getAttachmentKey()` took the MIME part's file name, decoded it, and used it as-is as the Camel attachment key/name — a sender-chosen value that could carry path components (e.g. `../../evil.sh`) straight through to any code that later uses the attachment name to write a file.
  2. **Marshal (MIME header injection, CWE-93):** `MailBinding.addAttachmentsToMultipart()` built the outgoing `Content-Type` header by string concatenation — `contentType + "; name=" + attachmentFilename` — so an attachment name containing a semicolon or quote (itself possibly relayed from an inbound message) could inject additional MIME parameters (e.g. a second `boundary=`), corrupting the message structure.
- **Does the affected version range include our pinned version?** `AFFECTED` — no public range is published (no CVE yet), but I fetched both files at the `camel-4.8.8` tag directly and confirmed the pinned code is byte-for-byte the pre-fix pattern:
  - `MailBinding.java:680-681` (4.8.8): `String value = contentType + "; name=" + attachmentFilename; messageBodyPart.setHeader("Content-Type", value);` — identical to the vulnerable line removed by the fix.
  - `MimeMultipartDataFormat.java:317` (4.8.8): `return MimeUtility.decodeText(key);` with no `FileUtil.stripPath()`/control-character stripping — identical to the vulnerable pattern removed by the fix.
- **Is an affected artifact in `used_components`?** `USED` — `camel-mail` is explicitly listed in `config/libraries.yaml`.
- **Severity:** No CVSS published. Estimated **MEDIUM** *(estimated)* — the marshal-side header injection needs an attacker-influenced outbound attachment filename (e.g. relayed from an untrusted upstream message) to corrupt MIME structure; the unmarshal-side path traversal needs a downstream consumer of the returned attachment key to use it for a file-system write (classic zip-slip style risk) — exploitability therefore depends on how the returned attachment name is used further down our routes, but the vulnerable input path itself requires no special privilege (any inbound mail sender, or any upstream message reaching a mail producer).
- **Verdict: AFFECTS US.**
- **Sources:**
  - Fix commit: https://github.com/apache/camel/commit/4848699ace04af38b6568d2fda3a766c9f2b916f
  - Fix PR: https://github.com/apache/camel/pull/26661 (merged 2026-09-24)
  - Jira: https://issues.apache.org/jira/browse/CAMEL-24433 (not reachable this run — Jira REST blocked, see Source health; ticket key taken from the commit message)
  - No CVE/GHSA record found for this ticket as of this run (checked via WebSearch).
- **Official fix + backport assessment:**
  - Changed files: `components/camel-mail/src/main/java/org/apache/camel/component/mail/MailBinding.java`, `components/camel-mail/src/main/java/org/apache/camel/dataformat/mime/multipart/MimeMultipartDataFormat.java`, plus two new/updated test files (`MailAttachmentFileNameQuotingTest.java`, `MimeMultipartDataFormatTest.java`).
  - **Applies cleanly to 4.8.8.** Both files are structurally identical at the point of the fix (same method names, same surrounding code):
    - `MailBinding`: 4.8.8 already imports `jakarta.mail.internet.*` (no javax→jakarta migration needed); only needs the new `import jakarta.mail.internet.ContentType;` plus the 3-line change from string concatenation to `ContentType.setParameter("name", ...)`.
    - `MimeMultipartDataFormat`: 4.8.8 does not yet import `org.apache.camel.util.FileUtil`, but that class and its `stripPath()` method already exist unchanged in 4.8.8's `camel-util` module (used elsewhere, e.g. `MailBinding.extractAndNormalizeFileName()`) — adding the import and the `key.replaceAll("[\n\r\t]", "_")` + `FileUtil.stripPath(key)` calls is a direct, low-risk port.
  - **Tests to port:** `MailAttachmentFileNameQuotingTest.hostileAttachmentNameIsQuotedInTheContentTypeHeader` and the two new cases in `MimeMultipartDataFormatTest` (`unmarshalAttachmentNameIsReducedToALeafName`, `unmarshalContentIdKeyKeepsSlashesBecauseItIsNotAPath`) — all self-contained, no fixture changes needed beyond the two new test-resource files (`multipart-traversal-name.txt`, `multipart-contentid-with-slash.txt`).
  - No backport to any Camel release branch exists yet upstream (fix is `main`-only, targeting the unreleased 4.23.0).
