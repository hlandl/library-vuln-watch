### CAMEL-24141 — Aggregate EIP background task can be permanently killed by one bad exception
- **Is this a vulnerability?** SUSPECTED — a real resource-exhaustion issue; no CVE/GHSA
  published for it as of this run.
- **Description:** `AggregateProcessor.AggregationIntervalTask.run()` has no `try/catch`
  around its body (unlike the sibling `RecoverTask.run()`, which at least wraps its work in
  `try/finally`). It is registered with a `ScheduledExecutorService` via
  `scheduleAtFixedRate`/`scheduleWithFixedDelay`. Per the standard library contract, if a
  scheduled `Runnable` throws an unchecked exception, that task's future executions are
  silently cancelled — no error is logged by the executor itself, and no exception ever
  reaches Camel's own error handlers. A single transient failure while iterating
  `aggregationRepository.getKeys()` or completing one aggregation group (e.g. a
  repository hiccup, a `ConcurrentModificationException`, or an aggregation-repository
  implementation that throws) permanently disables interval-based completion for that
  aggregator for the remaining lifetime of the route — every subsequent completion that
  was supposed to fire on the `completionInterval`/`completionTimeout` schedule simply never
  runs again, silently, with no restart. This is a route-level denial of the aggregation
  EIP's completion guarantee, triggerable by an attacker who can induce one exception in the
  repository/aggregation path (or by an ordinary transient failure).
- **Affected range vs. our version:** **AFFECTED — confirmed directly against our pinned
  source.** Fetched `AggregateProcessor.java` at the `camel-4.8.8` tag;
  `AggregationIntervalTask.run()` there has the identical shape — no exception handling
  around the key-iteration/completion body, only lock/finally for the mutex, nothing that
  would catch and swallow (and thus survive) an unchecked exception thrown mid-iteration.
- **Component in use?** Aggregate EIP lives in `camel-core-processor`/`camel-core`, both in
  `used_components` → **USED**.
- **Verdict: AFFECTS US.**
- **Severity:** Medium *(estimated — no CVSS published. Impact is availability: silent,
  permanent loss of interval/timeout-based aggregation completion for the affected route
  until a restart; requires an exception to occur inside the scheduled task body, which can
  happen from an unreliable aggregation repository, not from arbitrary remote input, so this
  is not directly remotely triggerable in the common in-memory-repository case)*.
- **Sources:**
  - PR (fix): https://github.com/apache/camel/pull/24821
  - Commit: `93950e50adf0c62b7d24f012bac70e2f0a9f39dc` ("CAMEL-24141: Aggregate EIP - guard
    background tasks against exceptions")
  - Jira: CAMEL-24141 *(link only — `issues.apache.org` unreachable this run)*
  - Pinned-version source checked directly:
    https://github.com/apache/camel/blob/camel-4.8.8/core/camel-core-processor/src/main/java/org/apache/camel/processor/aggregate/AggregateProcessor.java
- **Official fix:** Wraps `AggregationIntervalTask.run()` and `RecoverTask.run()` bodies in
  `try/catch(Exception)` with logging, and makes `aggregateCompletionCounter()` null-safe.
  New tests verify the scheduler survives a thrown exception from a background task. No
  tagged Camel release contains this fix yet (merged to `main` 2026-07-17, targeted at the
  4.22.0 milestone); no backport to a maintenance branch exists as of this run.
- **Backport assessment:** Should apply with **low** effort. The method name and structure
  (`AggregationIntervalTask`/`RecoverTask` inner classes of `AggregateProcessor`) are
  unchanged between 4.8.8 and `main` — this is an additive, localized fix (wrap the existing
  body in try/catch, add a log line) with no reordering or renamed symbols to fight.
  Recommend porting the new scheduler-survival test(s) alongside.

### CAMEL-24166 — camel-zipfile: zip-bomb protection silently bypassed in iterator/splitter mode
- **Is this a vulnerability?** SUSPECTED — a real, verified security-control bypass; no
  CVE/GHSA published for it as of this run.
- **Description:** `ZipFileDataFormat` exposes a `maxDecompressedSize` option (default 1 GB)
  specifically to guard against decompression bombs — archives that expand to a
  disproportionately large size and exhaust memory/disk. This limit is enforced via
  `IOHelper.copy()` on the non-iterator code path, but when `usingIterator=true` (the
  standard way to stream/split a multi-entry zip, e.g. `.split().tokenize()`-style
  processing of an uploaded archive), `ZipFileDataFormat` constructs a `ZipIterator` and
  never passes `maxDecompressedSize` to it. `ZipIterator` itself has no size-limiting logic
  at all — it wraps the raw `ZipInputStream` directly
  (`answer.setBody(new ZipInputStreamWrapper(zipInputStream))`) with no bound on how much
  data a consumer can read out of a single entry. Any route that unzips
  attacker-influenced/uploaded archives in iterator or splitter mode — the common pattern
  for handling multi-file archives — gets **no** decompression-bomb protection regardless of
  the configured `maxDecompressedSize`, even though the option is set and appears to be in
  effect.
- **Affected range vs. our version:** **AFFECTED — confirmed directly against our pinned
  source.** Fetched `ZipIterator.java` and `ZipFileDataFormat.java` at the `camel-4.8.8` tag
  (correct path is `dataformat/zipfile/...`, not `component/zipfile/...`): `ZipIterator`'s
  constructor/entry-reading path has no size-limit parameter or bounded-stream wrapping
  whatsoever, and `ZipFileDataFormat` passes only `allowEmptyDirectory` to the iterator it
  constructs — `maxDecompressedSize` is read from configuration but only ever used in the
  non-iterator `IOHelper.copy()` path, exactly matching the upstream description of the bug.
- **Component in use?** `camel-zipfile` is in `used_components` → **USED**. (Note:
  `camel-tarfile`, fixed by the same PR for the equivalent tar case, is a separate Maven
  artifact **not** in `used_components` — the tar half of this fix is not relevant to us,
  only the zip half.)
- **Verdict: AFFECTS US.**
- **Severity:** Medium–High *(estimated — no CVSS published. A decompression-bomb guard
  that is supposed to be active is silently inert whenever `usingIterator=true`; impact is
  denial of service (memory/disk exhaustion) from a maliciously crafted small archive if any
  route unzips externally-supplied archives in iterator/splitter mode. Actual exploitability
  depends on whether such a route exists in our deployment — this report does not have
  visibility into route configuration, only into the component code)*.
- **Sources:**
  - PR (fix): https://github.com/apache/camel/pull/24817
  - Commit: `aa68003` ("CAMEL-24166: Enforce maxDecompressedSize in iterator/splitter mode
    for zip and tar")
  - Jira: CAMEL-24166 *(link only — `issues.apache.org` unreachable this run)*
  - Pinned-version source checked directly:
    https://github.com/apache/camel/blob/camel-4.8.8/components/camel-zipfile/src/main/java/org/apache/camel/dataformat/zipfile/ZipIterator.java
    and
    https://github.com/apache/camel/blob/camel-4.8.8/components/camel-zipfile/src/main/java/org/apache/camel/dataformat/zipfile/ZipFileDataFormat.java
- **Official fix:** `ZipIterator` now receives and enforces `maxDecompressedSize` via the
  existing `IOHelper.copy()` 5-argument overload; `ZipFileDataFormat` propagates the
  configured limit into the iterator it creates. New tests
  (`testUnzipMaxDecompressedSizeWithIterator`) assert `CamelExecutionException` is thrown
  once the configured limit is exceeded with `usingIterator=true`. No tagged release
  contains this fix yet (merged to `main` 2026-07-17, targeted at 4.22.0); no maintenance
  backport exists as of this run.
- **Backport assessment:** **Low-to-moderate** effort. `ZipIterator`'s constructor and
  `ZipFileDataFormat`'s iterator-construction call site both exist in 4.8.8 with matching
  names/signatures (only the package path differs by directory, not by class/method
  structure), so the fix should apply with minor adjustment: add a `maxDecompressedSize`
  constructor parameter/field to `ZipIterator`, wrap entry reads through the bounded
  `IOHelper.copy()` (already present and used on the non-iterator path in 4.8.8, so no new
  dependency is needed), and pass the configured value from `ZipFileDataFormat`. Recommend
  porting the new iterator-mode test case; the tar-side changes in the same upstream PR can
  be skipped since `camel-tarfile` is not one of our used components.

### CAMEL-24164 — camel-jaxb: `CamelJaxbPartClass` header pollutes a shared mutable field across exchanges
- **Is this a vulnerability?** SUSPECTED — a real, verified data-integrity bug; no CVE/GHSA
  published for it as of this run (upstream traces the bug's origin to CAMEL-5723, 2017).
- **Description:** `JaxbDataFormat` — a single instance normally shared across all exchanges
  flowing through one route's marshal/unmarshal step — has an instance field `partClass`.
  Both `unmarshal()` and `toElement()` read the `CamelJaxbPartClass` header off the *current*
  exchange and, if present, reassign the shared `this.partClass` field rather than using a
  local variable. Two consequences follow directly from this: (1) **stickiness** — once any
  single message carries the header, the field never reverts to unset, so every subsequent
  message *without* the header on the same route step silently reuses whatever class was
  last configured by an unrelated message; and (2) **cross-exchange contamination under
  concurrency** — two messages processed concurrently (or near-concurrently) with different
  `CamelJaxbPartClass` values can race on the shared field, so a message can be
  unmarshalled/marshalled using a class type intended for a completely different, unrelated
  exchange. In a multi-tenant or mixed-payload route, this can produce incorrect
  deserialization (wrong type applied to a message) or leak structural/class information
  between what should be isolated message flows.
- **Affected range vs. our version:** **AFFECTED — confirmed directly against our pinned
  source.** Fetched `JaxbDataFormat.java` at the `camel-4.8.8` tag: it declares
  `private Class<?> partClass;` and both `unmarshal()` and `toElement()` contain the exact
  vulnerable pattern — reading `JaxbConstants.JAXB_PART_CLASS` off the exchange header and
  assigning straight into the shared `partClass` field.
- **Component in use?** `camel-jaxb` is in `used_components` → **USED**.
- **Verdict: AFFECTS US.**
- **Severity:** Medium *(estimated — no CVSS published. Requires a route step that
  processes messages both with and without the `CamelJaxbPartClass` header — or with
  different header values — either concurrently or in sequence, which is a plausible but not
  universal routing shape; impact is incorrect unmarshalling / potential cross-exchange
  information exposure, not remote code execution by itself)*.
- **Sources:**
  - PR (fix): https://github.com/apache/camel/pull/24813
  - Commit: `17c2419` ("CAMEL-24164: camel-jaxb - Fix CamelJaxbPartClass header state
    pollution")
  - Jira: CAMEL-24164 *(link only — `issues.apache.org` unreachable this run; upstream notes
    this as a regression path dating back to CAMEL-5723, 2017)*
  - Pinned-version source checked directly:
    https://github.com/apache/camel/blob/camel-4.8.8/components/camel-jaxb/src/main/java/org/apache/camel/converter/jaxb/JaxbDataFormat.java
- **Official fix:** Replaces the `this.partClass = ...` mutations in both `unmarshal()` and
  `toElement()` with a local `effectivePartClass` variable, so no exchange's header value can
  leak into another exchange's processing. New test
  `JaxbPartClassHeaderStatePollutionTest` validates isolation across consecutive exchanges
  with and without the header. No tagged release contains this fix yet (merged to `main`
  2026-07-17, targeted at 4.22.0); no maintenance backport exists as of this run.
- **Backport assessment:** **Low** effort — a clean, self-contained, localized fix. Both
  `unmarshal()` and `toElement()` exist with the same names/shared-field pattern in 4.8.8, so
  the backport is a mechanical substitution (shared field reads/writes → local variable) with
  no structural drift to navigate. Recommend porting
  `JaxbPartClassHeaderStatePollutionTest` alongside.
