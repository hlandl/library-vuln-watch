## Findings

### CAMEL-24990 — Multicast, Split and Recipient List EIPs: fix bugs found in a deep review
- **Verdict**: NOT RELEVANT (not a security issue; the one data-isolation-adjacent bug requires camel-jpa, which is not a `used_component`)
- Merged commit fixes three bugs in `MulticastProcessor`/`RecipientListProcessor`/`Splitter`: (1) a streaming-split early-termination path that ran `onPrepare` on unrouted parts and could read an entire endless stream on timeout; (2) `RecipientListProcessor` reused a singleton `TRANSACTION_CONTEXT_DATA` map across all exchanges, so a later transaction could reuse an already-closed `EntityManager` from an earlier one — but this only manifests when `camel-jpa` populates that map, and `camel-jpa` is not in `used_components`; (3) a producer/endpoint leak on invalid recipient resolution.
- Source: [PR #26846](https://github.com/apache/camel/pull/26846), merged 2026-09-27.

### CAMEL-24996 — CopyOnWriteHeadersMap.entrySet() bypassed copy-on-write, letting header edits leak between copied messages
- **Verdict**: NOT RELEVANT — confirmed via direct source read that our pinned 4.8.8 has no such class at all
- Upstream (4.21.0/4.22.0 era) introduced a `CopyOnWriteHeadersMap` optimization for message copies (used by Split/Multicast); its `entrySet()` returned live entries of the *shared* backing map, so `entry.setValue()` mutated headers without triggering the copy-on-write, letting a header change on one split/multicast branch bleed into sibling messages and the original. This would be a real cross-message data-isolation bug if the mechanism existed in our version.
- Checked `core/camel-support/src/main/java/org/apache/camel/support/` at the `camel-4.8.8` tag: no `CopyOnWriteHeadersMap.java` file exists (404), and no `Header`/`Map`-named class implements this pattern — 4.8.8 predates the copy-on-write headers optimization entirely, so the vulnerable code path does not exist in our pin.
- Source: [PR #26852](https://github.com/apache/camel/pull/26852), merged 2026-09-26.

### CAMEL-24894 — camel-docling: output path handling hardened against path traversal
- **Verdict**: NOT RELEVANT — `camel-docling` is not in `used_components`
- `CamelDoclingOutputFilePath` was passed to the docling CLI without the normalization/containment checks already applied to input paths. Fix adds an `outputBaseDirectory` option, lexical `..`/`.` normalization, and containment validation (CWE-22-style path traversal in an AI-document-processing component we do not ship).
- Source: [PR #26737](https://github.com/apache/camel/pull/26737), merged 2026-09-25.
