None of this run's new tickets carry a CVE or GHSA identifier. Two are security-flavored hardening

- **CAMEL-24445** — `camel-pqc`: `PQCProducer` reused a single `java.security.Signature` instance
  across all exchanges. `Signature` is stateful and not thread-safe, so concurrent exchanges on
  the same producer could interleave sign/verify state — a verification could observe another
  exchange's in-flight state, and a valid signature replayed while another verification was in
  flight could be accepted. Fixed by building a fresh `Signature` per exchange when the producer
  created it itself (falls back to synchronized sharing only when the user supplied their own
  instance, which cannot be safely recreated).
  - **Is this a vulnerability?** `SUSPECTED` — no CVE/GHSA attached; a genuine CWE-362-class
    concurrency bug with security consequences (signature-verification confusion under load), not
    a cosmetic fix.
  - **Component in use?** `camel-pqc` is **not** in `used_components` → **NOT-USED**.
  - **Verdict: NOT RELEVANT** (component not used). Not investigated further (range check /
    backport) per methodology — only `AFFECTS_US` and high-severity `NEEDS_REVIEW` findings get a
    fix/backport writeup.
  - Source: [apache/camel@91d5bdac511](https://github.com/apache/camel/commit/91d5bdac51182fda8515e5b200e8aa842ccd1bc6) (closes [#25825](https://github.com/apache/camel/pull/25825)), committed 2026-08-27T17:26:30+02:00 by Andrea Cosentino.

- **CAMEL-24509** — `camel-mina`: `MinaPayloadHelper.setIn/setOut` unmarshalled an inbound
  `DefaultExchangeHolder` payload whenever the decoded object happened to be one, without checking
  the endpoint had `transferExchange` enabled — `DefaultExchangeHolder.unmarshal` rebuilds the
  whole `Exchange` (id, body, headers, out message, properties) from the payload.
  `camel-jms` already gates the equivalent call behind `isObjectMessageEnabled()` +
  `checkDeserializedClass()`; `camel-mina` had neither. The commit itself notes this is "defence
  in depth rather than a reachable hole": the object codec's accept-list refuses an arbitrary
  class by default (`objectCodecPattern` unset), so a holder only reaches the helper once an
  operator has explicitly widened that pattern. `objectCodecPattern` is now also marked
  `security = "insecure:serialization"` to flag that risk in the component catalog.
  - **Is this a vulnerability?** `SUSPECTED` — CWE-502-adjacent (unchecked deserialization gating),
    but the upstream commit message itself assesses it as defense-in-depth given the default-deny
    accept-list, not a directly reachable hole.
  - **Component in use?** `camel-mina` is **not** in `used_components` → **NOT-USED**.
  - **Verdict: NOT RELEVANT** (component not used).
  - Source: [apache/camel@9c30b32b69d](https://github.com/apache/camel/commit/9c30b32b69dc7f2aa8f35f202e750ba17976c9e0) (PR [#25788](https://github.com/apache/camel/pull/25788)), committed 2026-08-27T11:19:42+02:00 by Andrea Cosentino.
